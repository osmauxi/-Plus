# 怪物寻路墙端持续驱离修复记录

> 用途：持续记录“怪物在墙体端部被密度 Flow 持续带离正常绕行方向”这一项问题的现场证据、方案审查、实现范围和复测结果。
> 范围：保留当前整体集群、密度避让和 Separation 表现；不借此调整整个寻路算法，不处理与本问题无关的集群形态、攻击停止距离或性能优化。
> 当前基线：`7c606da`，2026-10-25，第二版拓扑进展下限已完成实现，等待场景复测。

## 1. 问题定义

本次只处理以下现象：

1. 怪物群到达墙体端部后，密度成本改变 Flow 方向。
2. 部分怪物不是沿墙端绕回玩家，而是继续向远离正常拓扑路径的方向移动。
3. 外移怪物又把密度影响带到外层，形成持续向外传播的驱离链路。

以下现象不作为本次缺陷：

- 怪物为了绕过墙体而短时间远离玩家直线方向。
- 怪物在高密度区域横向分流。
- 墙端形成密集队列或整体集群形状不够规整。
- 合法的拓扑 Flow 与“直接朝玩家”方向不同。

判断依据必须是“密度 Flow 是否违背不含怪物密度的拓扑 Flow”，不能直接拿怪物到玩家的直线方向判断。墙体存在时，直线方向本来就可能不可走。

## 2. 2026-10-25 Unity MCP 现场快照

### 2.1 复现环境

- 场景：`GameRunTimeScene`。
- 怪物：1,024 只，全部存在有效 Flow。
- 玩家位置：世界坐标约 `(4.29, -26.83)`。
- 现场状态：用户确认当前暂停帧是典型复现；采样期间保持暂停。
- 对照方法：保留相同的 Walkable、连接掩码、动态障碍、额外 Cost 和玩家 Source，仅移除 `DensityCost`，临时重建一份拓扑参考 Flow。该对照只用于诊断，没有写入场景或运行时状态。

### 2.2 当前 Flow、Separation 与最终速度

| 指标 | 结果 | 结论 |
|---|---:|---|
| 最终速度反向于当前密度 Flow | 0 / 1,024 | 当前典型帧不是 Separation 把最终速度直接扭反 |
| 当前 Flow 反向于玩家直线方向 | 343 / 1,024 | 该数字混有正常绕墙，不能单独作为缺陷 |
| 距不可走格两格内的怪物 | 666 / 1,024 | 当前样本确实覆盖大量墙边怪物 |
| 墙边当前 Flow 反向于玩家直线方向 | 116 / 666 | 仍然可能是合法绕墙 |
| 墙边最终速度反向于玩家直线方向 | 71 / 666 | 最终移动基本服从当前 Flow |

原始 Separation 在不少墙边怪物上与 Flow 相反，但与导航速度合成、限速及墙体约束后，最终速度仍然顺着当前 Flow。因此，单纯裁剪 Separation 的反向分量不能解决本次问题。

### 2.3 密度 Flow 与拓扑参考 Flow

| 指标 | 结果 |
|---|---:|
| 当前密度 Flow 与拓扑参考 Flow 反向 | 113 / 1,024 |
| 两者偏差超过 45° | 206 / 1,024 |
| 距不可走格两格内，两者反向 | 3 |
| 距不可走格两格内，两者偏差超过 45° | 6 |

这个结果说明两件事：

1. 密度 Cost 确实能够把 Flow 改到与稳定拓扑路径相反，具备产生持续外驱的条件。
2. 不能全局禁止这种变化。当前有 113 只怪物方向反转，而真正贴近墙体、符合本次问题范围的只有少量个体；全局纠正会改变已经认可的集群分流。

### 2.4 代表格路径对照

以下路径长度以 Grid 移动步长计，斜向步长为约 1.414。

| 起始格 | 当前密度 Flow | 拓扑参考 Flow | 现场意义 |
|---|---:|---:|---|
| `(17, 40)` | 15.5 格 | 15.5 格 | 墙端拥挤，但当前绕行与拓扑参考一致，不应修正 |
| `(40, 52)` | 22.1 格 | 22.1 格 | 同上，属于合法绕墙 |
| `(52, 29)` | 24.1 格 | 24.1 格 | 同上，不能因为短时远离玩家就判错 |
| `(33, 16)` | 31.1 格 | 21.8 格 | 首步方向与参考方向相差 90°，密度路径明显变长 |
| `(53, 34)` | 39.6 格 | 29.5 格 | 首步左右方向相反，最大离玩家距离由 137.8 增至 166.9 |

`(53, 34)` 是本次问题的有效例子：当前密度 Flow 首步为 `(0.7, -0.7)`，拓扑参考 Flow 为 `(-0.7, -0.7)`。当前路径先向墙外侧继续扩张，比参考路径多约 10 个 Grid 步长，并把最大离玩家距离增加约 29 个世界单位。

## 3. 已审查并排除的修改

### 3.1 不修改 Separation 强度、半径或全局上限

原因：现场最终速度没有反向于当前 Flow。此类修改会改变所有密集区域的集群形态，却不能阻止密度 Flow 自己改向。

### 3.2 不全局移除 Separation 的反向分量

原因：这只能保证最终速度服从当前 Flow；当 Flow 已经被密度成本带向墙外时，怪物仍会按错误 Flow 外移。

### 3.3 不全局降低 `MaxDensityCost`、`CostPerInfluence` 或影响半径

原因：这些参数决定当前已经认可的拥堵分流能力。全局降权会重新引入怪物压成一团的问题，修改范围远大于墙端缺陷。

### 3.4 暂不修改密度平滑下降速度

原因：当前三个主要拥挤墙端格在“有密度”和“无密度”的路径完全一致，说明并非所有墙端外移动作都来自残留 Cost。只加快下降无法可靠区分合法绕墙和错误外驱，同时会改变整张图的密度时序。

### 3.5 不使用玩家直线方向做纠偏

原因：直线可能穿墙。纠偏基准必须是同一拓扑上的无密度 Flow，否则会把正常绕墙误判成反向。

### 3.6 不做全局双流场切换

拓扑参考 Flow 只作为墙边异常校验，不替代当前密度 Flow。正常格、无方向冲突的墙边格以及普通集群区域继续完全使用当前算法。

## 4. 首版最小修复方案（已实测）

本节保留首版设计及其判断边界，当前后续方案以第 9 节为准。

### 4.1 建立只读拓扑参考 Flow

在 `MonsterSimulation` 中增加一份拓扑参考 `MultiSourceFlowField`：

- Walkable、连接掩码、动态阻挡、普通额外 Cost 与正式 Flow 保持一致。
- 唯一差异是参考 Flow 不读取怪物 `DensityCost`。
- 只在 Topology、普通 `AdditionalCost` 或玩家 Source 被正式接受时重建。
- 普通密度 Cost 更新不重建参考 Flow。

这份数据不是第二套寻路决策系统，只提供“没有怪物密度反馈时，当前格应沿哪条合法拓扑路线前进”的稳定基准。

### 4.2 只拦截墙边反向 Flow

读取某格正式 Flow 时，同时读取拓扑参考方向。仅同时满足以下条件时纠正：

1. 当前格位于不可走格的两格影响范围内；
2. 两份方向都有效；
3. `Dot(densityDirection, topologyDirection) <= 0`，即密度 Flow 相对拓扑路径已经没有正向进展，夹角达到或超过 90°。

满足条件时，本轮直接使用拓扑参考方向；否则继续使用原密度 Flow。

选择直接回退而不是再增加混合权重，原因是：

- 当前现场符合条件的怪物很少，回退范围明确；
- 不新增需要调参的角度、速度或混合系数；
- 90° 内的横向分流全部保留；
- 对完全相反方向的处理可预测，便于 A/B 和回滚。

### 4.3 暂不增加跨 Tick 状态

首版不为怪物增加“正在脱离墙端”状态、计时器或滞后锁定。先验证在墙端切断反向 Flow 是否已经能阻止外驱链向外传播。只有复测证明怪物离开两格范围后仍继续被同一链路带走，才考虑最小持续状态；不能预先引入。

### 4.4 Separation 和移动约束保持原样

修正后的导航方向仍按现有顺序进入：

```text
Flow 方向 -> 导航速度 -> Separation -> 最大速度限制 -> ConstrainMovement -> Integrate
```

本次不改 `ApplySeparation`、`ConstrainMovement`、攻击状态机和停止距离。

## 8. 2026-10-25 首版实测与方案修订

### 8.1 人工观察

- 怪物初次接触墙体时，贴墙纵向分流比基线明显。
- 随着集群绕过墙端，一部分怪物逐渐转为持续斜后方移动。
- 极少出现正对玩家方向的 180° 反向，主要是斜后方扩散。
- 外围看似空旷，但 Flow Integration 仍然很高，容易被理解成历史 DensityCost 恢复过慢。

### 8.2 暂停帧 MCP 数据

当前暂停帧包含 1,024 只怪物，其中 969 只有有效的正式 Flow 和拓扑参考 Flow。

| 指标 | 结果 |
|---|---:|
| 当前被首版墙边规则纠正的格 | 44 |
| 站在纠正格中的怪物 | 113 |
| 密度 Flow 相对拓扑 Flow 没有正向进展 | 241 |
| 密度 Flow 相对拓扑 Flow 只有弱正向进展 | 136 |
| 最终速度背离玩家直线方向 | 230 |
| 其中斜后方 90°–135° | 196 |
| 其中强反向 135°–180° | 34 |
| 已离开两格墙区但仍背离玩家直线 | 108 |

这说明首版规则在墙边已经生效，但外驱链离开两格墙区后失去约束。当前剩余问题不是首版判断没有命中，而是判断被墙体距离过早关闭。

### 8.3 “密度恢复太慢”假设检查

使用当前 1,024 只怪物的实际位置，按 `DensityKernel` 的两格 Chebyshev 核、权重和上限重新计算即时目标 Cost，再与运行时平滑后的 `DensityCost` 对比：

| 指标 | 结果 |
|---|---:|
| 运行时 DensityCost 总量 | 33,210 |
| 当前分布即时目标 Cost 总量 | 33,330 |
| 运行时高于即时目标的格 | 471 |
| 这些格的平均超额 | 2.12 |
| 超额达到 10 的格 | 1 |
| 站在超额达到 10 的格上的怪物 | 0 |
| 即时目标为 0、运行时仍有残留的格 | 32 |

结论：当前典型帧不存在足以解释大规模斜后方移动的历史高值残留。运行时总量甚至略低于即时目标，说明大范围高成本主要由怪物当前分布持续产生，而不是平滑下降没有追上。

截图中约 700–850 的数字是 Flow Integration，即从当前格到 Source 的累计路径成本，不是单格 `DensityCost`；单格密度上限仍然是 40。外围格自身即使没有怪物，也会受到两格范围内其他怪物的实时影响，并且积分值还会累计后续整条路径上的 Cost，因此不能通过积分数字直接判断该格保留了多少历史密度。

### 8.4 密度阈值模拟

在不修改运行时的前提下，分别从即时 Influence 中扣除 4、6、8、10、12 的“自由容量”后重建临时 Flow。结果没有减少无正向进展方向，反而从 240 增加到 296–337，并改变了 190–410 只怪物的方向。

因此下一版不增加密度阈值，不修改 `MaxDensityCost`、`CostPerInfluence`、影响半径或平滑系数。此类全局参数会重新改变已经认可的集群表现，而且不能稳定解决当前方向传播。

## 9. 第二版修改方案（已实现）

### 9.1 将“墙边纠正”收敛为“拓扑进展下限”

继续使用首版已经建立的拓扑参考 Flow，但移除“两格墙体范围”条件。判断只保留：

```text
Dot(densityDirection, topologyDirection) <= 0
```

含义是：密度仍可选择与拓扑方向夹角小于 90° 的横向绕行，但不能选择完全横向或反向、对合法拓扑路径没有任何正向进展的方向。

命中时继续直接使用拓扑参考方向，不增加新的混合系数。Separation 随后仍会提供局部横向位移，所以不会把所有怪物强制压成同一条线。

按当前暂停帧估算：

- 现有规则纠正 113 只墙边怪物。
- 新规则会额外接管 128 只已经离墙、但仍无拓扑进展的怪物。
- 仍有正向分量的 136 只弱进展怪物不会被修改。
- 当前方向与拓扑方向一致的 592 只怪物不会被修改。

### 9.2 同步修正命名和 Gizmos

现有命名已经不再准确，本次同步完成直接重命名：

- `WallFlowCorrectionRadiusCells`：删除。
- `IsWallFlowCorrectionCell`：改为 `IsFlowProgressCorrectionCell`。
- Gizmos “墙边方向纠正格”：改为“方向进展纠正格”。
- 红色线框继续表示实际会被运行时纠正的格。
- 绿色拓扑参考方向和粉色密度方向保持不变。

不新增状态机、计时器、墙端识别器或新的配置资产。

### 9.3 明确不修改的部分

- `DensityKernel` 的上升/下降平滑。
- 密度 Cost 上限、单位影响成本和影响半径。
- Flow Field Cost 重建间隔。
- Separation 强度、半径和合成方式。
- `ConstrainMovement`、攻击状态和停止距离。

### 9.4 下一轮验收

仍使用同一 1,024 怪场景：

1. 初次贴墙时仍保持当前版本已经改善的纵向分流。
2. 红色纠正格应能随外驱链延伸到离墙区域，不再在两格位置突然中断。
3. 斜后方集群应在进入无拓扑进展状态时转回绿色参考方向。
4. 粉色密度方向与绿色参考方向夹角小于 90° 时不得触发纠正。
5. 观察是否重新出现压成一团；若出现，优先检查直接回退是否过强，而不是先改密度参数。
6. 用 MCP 复测 `noPositiveProgress`、实际纠正怪物数和离墙后背离数量，并与本节数据对照。

### 9.5 实施记录

- 已删除两格墙体范围判断，方向纠正不再随怪物离墙而中断。
- `ShouldUseTopologyReferenceDirection` 只判断两份方向有效且点积小于等于 0。
- 已将运行时 API 和 Gizmos 设置统一改名为“方向进展纠正”。
- 未修改 Density、Separation、Flow Cost 重建间隔及其他移动逻辑。
