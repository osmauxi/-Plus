# 资源与数据管线：工程检查表与故障定位

## 1. 方法/架构介绍

资源系统最难排查的问题通常不是某一行 API，而是初始化顺序或所有权链断裂。当前项目的正确启动依赖可以概括为：

```text
Addressables 初始化 / Catalog 更新
  → 热更程序集与 AOT 元数据就绪
  → 注册 MessagePack GeneratedResolver
  → 加载 Config Label
  → ConfigRegister 完成全部强类型表注册
  → 加载 LobbyScene
  → Lobby 脚本在 Awake/Start 中读取 Config
  → 根据 Config 地址加载模型和图标
```

检查时应从上游向下游定位，而不是看到 Avatar 没有出现就立刻修改 Avatar 脚本。

## 2. 源码展示

### 2.1 Config 必须先于 LobbyScene

当前热更启动边界中的关键顺序：

```csharp
RegisterMessagePackResolver();
ConfigManager.Instance.Init();

await LoadingUI.Show("正在进入大厅...");
await ConfigManager.Instance.LoadAllConfigsAsync();
await Addressables
    .LoadSceneAsync("LobbyScene", LoadSceneMode.Single)
    .Task.AsUniTask();
```

这段代码位于 GameProcess 启动边界，但这里只关注它对 Config 和 Lobby 的时序保证，不展开其他游戏流程。

### 2.2 Lobby 消费 Config 的最早位置

`ItemSelectPresenter.Awake()` 会立即执行：

```csharp
var skinTable =
    ConfigManager.Instance.GetTable<Config_Lobby_Skins>();
```

`LobbyOverviewCoordinator.Start()` 会创建默认玩家：

```csharp
int skinId = ConfigManager.Instance
    .GetTable<Config_Lobby_Skins>()
    .Keys.Min();
```

因此不能进入 LobbyScene 后才开始加载 Config。

### 2.3 资源加载失败必须保留地址和 ID

```csharp
bool loadSucceeded = await TryCompleteLoadAsync(
    handle,
    $"角色 CharacterId={state.CharacterId}");
```

有效日志至少应包含：

- 资源类型；
- Config ID；
- Address；
- 展位或 UI 对象；
- Addressables OperationException。

## 3. 源码解释

### 初始化顺序为什么是硬依赖

Config 类的 C# 类型存在，不代表对应字典已经加载。`GetTable<T>` 读取的是运行时 `_allConfigs`，只有 `ConfigRegister.ParseAndRegister` 执行后才有内容。

同理，Config 中存在 Address，不代表 Catalog 中存在该资源；Addressables Group、Label 和内容构建也必须完成。

### 为什么问题要沿数据链排查

以“角色模型没有生成”为例：

```text
LobbyPlayerState.CharacterId 是否有效？
  → Config_Lobby_Skins 是否注册？
  → CharacterId 是否能查到记录？
  → ModleName 是否为空或拼错？
  → Catalog 是否包含该 Address？
  → 依赖 Bundle 是否可下载？
  → 预制件是否含 CharacterSocketProvider？
  → 异步请求是否被新 Revision 判定为过期？
```

每一层都可能表现为最终“模型没出现”，但修复位置完全不同。

## 4. 底层拓展说明

### 4.1 Addressables 检查表

- Address 与 Config 字符串完全一致，包括大小写。
- Config `.bytes` 带 `Config` Label。
- 模型和图标资产已 Mark Addressable。
- 远端 Catalog 与 Bundle 属于同一次内容发布。
- `LoadAssetAsync` 与 `InstantiateAsync` 使用正确泛型类型。
- 每个成功、失败、取消、过期路径都有对称 Release。
- 不用 `Destroy` 代替 `ReleaseInstance`。

### 4.2 UniTask 检查表

- 普通异步方法返回 `UniTask`，只在 Unity 回调边界使用 `async void`。
- `.Forget()` 的方法内部捕获预期异常，或向 `Forget` 提供异常处理器。
- 每个 `await` 后考虑对象是否已销毁、绑定是否已变化、请求是否已过期。
- 取消等待后仍释放 Addressables 句柄。
- 有依赖的步骤顺序等待，无依赖且确有收益的步骤再 `WhenAll`。

### 4.3 Config 与 MessagePack 检查表

- Excel 第一列是唯一 `int` ID。
- 表头变更后按 1→2→3→4 完整生成。
- 不手改 `Generated/*.cs`、`ConfigRegister.cs`、`MessagePackGenerated.cs`。
- 数字 `[Key]` 不随意重排或复用。
- `GeneratedResolver` 在首次反序列化前注册。
- 新 `.bytes` 名称与 `ConfigRegister` case 一致。
- 必需表非空，默认 ID 确实存在。
- 构建机数值解析使用固定 Culture。

### 4.4 NGO 检查表

- 同步字段已加入 `NetworkSerialize` 与 `Equals`。
- 修改 NetworkList 中的结构体后重新赋值回索引。
- ServerRpc 使用 `SenderClientId` 确认请求者。
- 服务器重新校验 Config ID 和房间状态。
- Host 与 Client 使用兼容的网络结构与 Config 版本。
- `StandIndex` 在范围内且唯一。
- Persistent ID 不作为正式安全认证凭据。

### 4.5 本地存储检查表

- 使用 `Application.persistentDataPath`。
- 缺文件和坏文件有明确恢复路径。
- 读取后和写入前执行 Normalize。
- 版本变更有迁移规则。
- 关键文件使用临时文件和备份替换。
- 不把服务器权限或付费状态只保存在本地。

### 4.6 常见症状定位表

| 症状 | 优先检查 |
| --- | --- |
| 所有 Config 都是 null | Resolver 注册、Config Label、加载是否先于场景 |
| 只有一张表缺失 | `.bytes` 名称、Label、ConfigRegister case |
| Editor 正常，IL2CPP 崩溃 | MPC 生成文件、Resolver 注册、AOT 泛型引用 |
| 快速切换后显示旧模型 | Revision 是否在每个 await 后检查 |
| 滚动列表图标串位 | Bind 版本号、OnDisable、旧句柄释放 |
| 内存随切换持续上涨 | Load/Instantiate 与 Release/ReleaseInstance 是否配对 |
| 客户端改装备但其他人不更新 | ServerRpc 是否写回 NetworkList 索引 |
| 单机显示正常、联网展位错位 | StandIndex 快照、列表顺序是否被误当作展位顺序 |
| 改键重启后丢失 | Override JSON 是否保存并在资产启用前恢复 |

## 5. 应用示例

### 示例：新增一张表后的验收方法

可以在开发工具中加入一次性校验：

```csharp
public static void ValidateLobbyConfig()
{
    var skins = ConfigManager.Instance
        .GetTable<Config_Lobby_Skins>();
    var weapons = ConfigManager.Instance
        .GetTable<Config_Lobby_Weapons>();
    var items = ConfigManager.Instance
        .GetTable<Config_Lobby_Items>();

    if (skins.Count == 0 || weapons.Count == 0 || items.Count == 0)
        throw new InvalidDataException("Lobby 必需配置表不能为空");

    foreach (Config_Lobby_Weapons weapon in weapons.Values)
    {
        if (string.IsNullOrWhiteSpace(weapon.ModleName))
            throw new InvalidDataException(
                $"WeaponId={weapon.WeaponID} 缺少模型地址");

        if (string.IsNullOrWhiteSpace(weapon.IconName))
            throw new InvalidDataException(
                $"WeaponId={weapon.WeaponID} 缺少图标地址");

        if (weapon.WeaponEquipAnim is < 0 or > 1)
            throw new InvalidDataException(
                $"WeaponId={weapon.WeaponID} 的动画值无效");
    }
}
```

验收顺序：

1. 清空旧生成产物并重新生成。
2. 重新导出 MessagePack bytes。
3. 重新生成 MPC Formatter。
4. 构建 Addressables 内容。
5. 启动后确认 Config 校验通过。
6. 连续快速切换资源，观察是否串位或泄漏。
7. Host/Client 分别修改装备，确认所有客户端快照一致。
8. 退出场景并检查句柄、事件和控制台错误。

当这八步形成固定流程后，资源与数据问题会从运行时偶发故障，提前转化为编辑器或启动阶段的确定性错误。
