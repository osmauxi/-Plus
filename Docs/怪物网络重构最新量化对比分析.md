### 0.4 固定 Tick 预算与网络发送 GC

Gameplay Tick 预算来自 `NetworkSimulationConfig.TickRate`，当前默认值为 30，因此一个逻辑 Tick 的墙钟预算是 `1 / 30 = 33.333 ms`。`GameplayNetworkTickDriver.Advance` 每帧把 `Time.unscaledDeltaTime` 累加到 `_accumulatedSeconds`，用 `floor(accumulated / interval)` 计算到期 Tick 数，再以 `MaxTicksPerFrame = 4` 为上限连续调用 `clock.AdvanceOneTick()`。它会扣除所有到期时间；超过 4 个的部分记入 `DroppedTimeSeconds`，所以系统不会无限追赶，但会进入持续多 Tick/帧和逻辑时间丢弃状态。

最新 `Gameplay.TickDriver.Dispatch` Marker 已验证这一机制：三次 Host 的 Dispatch 平均约 60～63 ms/帧，897 个 Tick 分布在 405～420 个渲染帧上，约 2.2 Tick/帧。固定 Tick 预算不是渲染帧率目标，而是每秒必须完成的逻辑推进速率；当单 Tick 加上 PlayerLoop 其他工作超过 33.333 ms 后，驱动器就会在下一帧派发多个 Tick，形成长帧放大。

最新完整 Profiler 的 GC 列还确认了 `SendUnnamedMessage` 的实际分配：`GroupSnapshot.Write` 的 GC 为 0，`GroupSnapshot.Send` 与 `Monster.Network.SendUnnamedMessage` 每次发送约分配 126 B。当前 Host 约 1,214 条发送消息/s，对应约 153 KB/s 的托管分配；在 Host 平均约 13.5 帧/s 的运行中，这一项约占每帧 16.6 KB 总 GC 分配中的主要部分。该分配发生在 NGO/消息入队链路内部，当前没有证据表明 Unnamed 路由已经消除了它；它只说明每次发送的额外分配是固定的。减少发送调用次数或把更多群组合并进同一条消息，会按约 126 B/次线性降低这部分 GC。当前数据尚未提供旧 `SendNamedMessage` 在同一 Catalog 下的 GC 对照，因此不能宣称 Unnamed 相比 Named 已经减少了多少，只能确认它目前仍是网络 GC 的重要来源。

## 4. GC 需要单独追踪

GC 是本轮最明显的负向信号：

- 5012 Host 平均从 2,327 B/帧升到 3,406 B/帧，Client 从 1,691 B/帧升到 2,454 B/帧。
- 10024 Host 平均为 8,925 B/帧，历史参照为 2,888 B/帧。
- 10024 Client 平均为 6,460 B/帧，历史参照为 2,105 B/帧。
- 当前 10024 每次 30 秒采样触发 Gen0/1/2 各 11～17 次，旧参照只有 3～5 次。

GC 数据不能直接证明某一个新增方法造成了分配。当前应先用逐帧 `gcAllocatedBytes` 对齐长帧，再按分组生命周期、传输统计和客户端收包时间段区分启动期扩容、周期性业务分配和测试工具自身分配。需要特别观察组创建、成员表变化、`List.Sort`、网络统计字典和消息回调是否在稳定阶段仍产生托管分配。下一次压测应增加稳定期每帧 GC 的 P50、P95、最大值和 Gen0 时间，避免只看 30 秒总平均。

## 5. 当前结论和下一步量化

当前网络重构已经完成了第一项可量化目标：在 1024、2048、5012 和 10024 档位把应用层网络载荷降到旧链路的约一半到四分之三，10024 仍保持 Replica 和 VAT Slot 全量就绪。客户端群组解码和应用在 10024 三次压测中约为 `GroupApply 0.258 ms/帧`、`GroupDecode 0.095 ms/帧`，远低于旧链路的 `Presentation Apply 0.451 ms/帧` 和 `Presentation Decode 0.268 ms/帧`。

当前还不能宣布整体性能收益已经完成，因为 Host 帧时主要没有跟随网络下降，GC Alloc 在高数量级明显上升。下一轮应保持同一 Catalog 和同一 Player，优先补充以下数据：

1. 10024 至少 5 次重复，分开记录 Host `PublishGroups`、`GroupBuild`、GC 和消息数。
2. 记录每 Tick 群组数量、内中外层数量、总成员数、32 KiB 预算延期次数和最大延期 Tick。
3. 按消息名记录 `GroupMembership`、`GroupInitialSnapshot`、`GroupSnapshot` 的消息数与载荷，区分可靠首帧流量和周期 Pose 流量。
4. 在稳定运行 10 秒后单独统计 GC，确认分配来自启动扩容还是持续热路径。
5. 完成 Host 直读权威表现后，重新测量 Host `ApplyLocal`、`Publish` 和 GC，才能判断表现层去 Replica 对 Host 的实际收益。
