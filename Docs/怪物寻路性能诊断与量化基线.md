# 怪物寻路性能诊断与量化基线

> 用途：记录怪物房间卡顿的可复现基线、证据链和后续优化结果，为技术复盘与简历量化提供可信数据。  
> 当前状态：已完成根因定位、计算内核优化、Source 重建策略、怪物快照双缓冲、Flow Field / Density / Separation AOT 迁移，并将约千个怪物 Animator + SkinnedMeshRenderer 替换为 VAT；已完成 Animator 极限 A/B 与 VAT 实装后的同规模 Player 压力复测。本文保留各阶段真实 Profiler 数据；不同怪物规模或帧等待状态下只直接比较独立 Marker，整体帧时间仅用于压力表现评估。

## 1. 问题表现

- 进入普通游戏场景时运行基本正常，怪物房间开始生成并模拟怪物后出现明显周期性卡顿。
- Editor 中表现为帧率瞬间下降约 20 帧，随后恢复。
- Windows Player 中体感更严重，周期性停顿接近 20–30 FPS 的单帧体验。
- CPU Usage 中同时能看到主线程、渲染线程及部分工作线程出现长条，最初容易误判为渲染、画质、GC 或多线程负载问题。

## 2. 测试环境与采样口径

- 平台：Windows x64 Player。
- 构建方式：Development Build，启用 Autoconnect Profiler。
- 后续性能包默认采用最小可用构建链路：只编译并同步发生变化的 HotFix DLL；仅在资源或内容目录变化时更新必要的 Addressables；复用现有 Library、HybridCLR 生成物和 Player 构建缓存。除非明确要求刷新 AOT 元数据或建立全新基线，否则不执行 HybridCLR `Generate/All`、不清缓存、不做完整 Baseline 重建。
- Deep Profiling：关闭，避免其显著放大热更新代码开销。
- Profiler 连接目标：独立 Player，而非 Editor。
- 采样窗口：连续 300 帧。
- 网络模拟频率：30 Tick/s。
- 房间导航网格：70 × 70，共 4,900 个 Cell。
- 统计原则：区分真实计算时间、线程等待、GC Alloc 和真正的 GC Collection。

后续复测必须保持场景、怪物数量、玩家数量、构建类型、画质、分辨率和采样窗口一致，否则数据不可直接横向比较。

典型 50.73 ms 卡顿帧的线程状态：

- 主线程：`GameplayNetworkTickDriver.Update()` 约 48.35 ms。
- Render Thread：约 48.88 ms 处于 `Gfx.WaitForGfxCommandsFromMainThread`，实际是在等待主线程。

因此 CPU Usage 中多个线程同时出现长条并不代表它们都在高负载工作。当前关键路径是主线程同步计算，其余线程主要是被迫等待。

## 4. GC 表现与结论

### 4.1 寻路尖峰不是 GC 导致

绝大多数 45–51 ms 寻路尖峰帧只有约 694 B 的整帧托管分配，且该分配主要来自网络更新等常驻逻辑，并未在寻路调用下观察到相应的大额 `GC.Alloc`。

采样中的增量 GC 通常约 0–0.003 ms。偶发完整 `GC.Collect` 约 0.52–0.84 ms，并且出现在普通帧，而不是周期性的 45–51 ms 寻路尖峰帧。

因此当前问题应准确描述为：

> 怪物导航的周期性主线程 CPU 尖峰，而不是寻路 GC 尖峰。

后续简历和技术复盘不应将这次优化错误描述成“消除了寻路 GC”。若优化过程中同时做到零分配，只能作为附加结果单独记录。

### 4.2 需要排除的独立 GC 噪声

Player 中还观察到 `VoiceManager.Update()` 偶发约 229–339 KB 的托管分配。该分配与语音采集、托管 Opus 编码和发送链路有关，最大分配帧本身通常仍在约 6–9 ms，不是怪物房间周期卡顿的根因。

语音 GC 必须作为独立问题统计，不能计入寻路优化收益。

后续修复并复测后，512 怪样本中 Voice 总分配仅 160 B，`VoiceManager.Update()` 平均 0.169 ms、最大 0.563 ms。历史上的 200 KB 级 Voice 分配已经不再出现。

## 5. 根因证据链

### 5.1 每 6 个网络 Tick 更新一次怪物密度

[`MonsterNavigationDensitySystem.cs`](../Assets/_HotUpdate/Scripts/GameProcess/Map/Spatial/MonsterNavigationDensitySystem.cs) 中配置：

```csharp
private const uint UpdateIntervalTicks = 6;
```

网络频率为 30 Tick/s，因此密度更新周期为：

```text
6 / 30 = 0.2 秒
```

Profiler 中尖峰同样约每 0.2 秒出现一次，与源码周期一致。

### 5.2 密度平滑持续修改导航版本

密度系统每次更新都会重新构建 Influence 和 Cost：

```csharp
BuildInfluence(world, grid, groundY);
BuildCost(grid, count);
return grid.ReplaceDensityCost(_outputCost);
```

Cost 使用持续平滑：

```csharp
_smoothedCost[i] = Mathf.Lerp(
    _smoothedCost[i],
    targetCost,
    SmoothFactor);
```

只要任意量化后的密度 Cost 发生变化，`RuntimeNavigationGrid.Version` 就会增加。即使怪物位置变化很小，平滑值也可能连续多轮变化。

### 5.3 原始版本变化触发完整 Flow Field 重建

[`MonsterSimulation.cs`](../Assets/_HotUpdate/Scripts/GameProcess/Monster/Simulation/MonsterSimulation.cs) 每个怪物 Tick 先更新密度，再检查 Flow Field：

```csharp
_densitySystem.Update(world, _navigationGrid, tick, groundY);
UpdateFlowField(players, groundY);
```

当网格版本变化时：

```csharp
bool navigationChanged =
    _lastNavigationVersion != _navigationGrid.Version;

if (!sourcesChanged && !navigationChanged)
    return;

_hasFlowField = _flowField.Build(
    _navigationGrid,
    _flowSources);
```

[`MultiSourceFlowField.cs`](../Assets/_HotUpdate/Scripts/Navigation/MultiSourceFlowField.cs) 随后对 4,900 个 Cell 执行：

```csharp
BuildIntegrationField(grid);
BuildDirectionField(grid);
```

完整流程包含 Dijkstra 扩散、小顶堆 Push/Pop、每格八方向邻居检查、可行走判断、额外 Cost 查询以及方向场生成。

以上代码为最初定位时的历史逻辑。当前版本已经拆分 Topology、Source 和 Cost 重建原因，并分别通过 `Monster.FlowField.Rebuild.Topology/Source/Cost` Marker 统计。

### 5.4 Player 中被 HybridCLR 解释执行进一步放大

Editor 中托管代码由 Mono JIT 编译后执行。当前 Windows Player 使用 IL2CPP，但 `HotFix.Gameplay` 与 `HotFix.Navigation` 被登记为 HybridCLR 热更新程序集，相关代码在 Player 中主要由解释器执行。

该算法具有大量紧密循环、接口调用、分支和 Heap 操作，属于解释执行开销容易被放大的类型。这解释了为什么相同逻辑在 Editor 中只是明显掉帧，而在 Player 中会形成 45–51 ms 的尖峰。

HybridCLR 是放大因素，但不是唯一根因。Editor 同样掉帧证明全量重建算法本身也需要优化。

## 6. 优化方向

### 6.1 第一优先级：消除不必要的周期性全量重建

- 将墙体、门、动态阻挡等“拓扑版本”与怪物密度 Cost 版本拆开。
- 玩家目标 Cell 或导航拓扑变化时，立即重建 Flow Field。
- 不再因为密度平滑值的微小变化每 0.2 秒重建完整 Flow Field。
- 优先让现有 Separation 或局部 Steering 处理怪物拥挤，避免把短时局部密度直接写入全局路径 Cost。
- 如果密度必须影响全局路径，增加有效变化阈值并显著降低重建频率，或将计算摊分到多个帧。

### 6.2 第二优先级：将纯计算内核放入 AOT/Burst

仅把 `MultiSourceFlowField` 类移入 AOT 不一定足够，因为它仍会高频通过接口调用热更侧的 `RuntimeNavigationGrid.IsWalkable()` 和 `GetAdditionalCost()`。

更合理的边界是把以下内容一起放入 AOT 计算程序集：

- 导航网格原始数组；
- Integration Field；
- Direction Field；
- 小顶堆；
- 高频可行走和 Cost 查询。

热更层只负责提交输入和读取结果，避免在 4,900 × 8 次邻居检查中反复跨越解释器边界。

### 6.3 验证方式

在不启用 Deep Profiling 的情况下，为以下阶段增加独立 `ProfilerMarker`：

- Density Update；
- Flow Field Build；
- Separation Build；
- Monster Slot Simulation；
- Presentation Capture。

这样既能保持较低采样扰动，又能在 Player 中直接得到每个阶段的耗时和调用频率。

表现层后续优化优先级：

1. 优先建立 GPU 动画或批量动画方案，以 `Animators.Update` 6.501 ms/帧、`WriteProperties` 约 1025 次/帧和蒙皮 1.311 ms/帧作为优化前基线。
2. `ApplyAuthority` 可进一步尝试只对活跃/发生姿态变化的 Slot 写 Transform 和 Animator 参数，目标基线为 1.742 ms/Tick；需要保留碰撞体与子弹物理在 Tick 后读取最新位置的现有时序。
3. 不应把 `ApplyAuthority` 与 `Animators.Update` 直接视作同一段重复耗时：前者是脚本侧提交状态，后者是引擎侧动画图求值。二者可能存在因果关系，但处于不同 PlayerLoop 阶段。

### 7.6 阶段 E：Flow Field 计算内核迁入 AOT

本轮保持 `MonsterSimulation`、重建策略、Density、Separation、70 × 70 网格和 Flow Field 算法不变，只将 `MultiSourceFlowField`、`IntCostMinHeap` 与纯数据结构迁入 `AOT_Core`。HotUpdate 仍负责准备 `Walkable`、`ConnectionMask`、`TraversalCost` 和 Source 坐标，并以数组引用零复制传给 AOT 内核。IL2CPP 生成物 `AOT_Core.cpp` 中已确认存在 `Build`、`AddSources` 和 `BuildIntegrationField` 的原生函数。

### 7.8 阶段 E 尖峰内部复核

#### 7.8.1 动画尖峰来自等待工作线程完成

真实最慢帧中，`Animators.WriteJob` 为 6.461 ms，其子级 `WaitForJobGroupID` 为 6.427 ms，进一步落到 `Idle` 5.924 ms。也就是说主线程并不是用 6 ms 执行动画写回代码，而是在动画同步点等待工作线程完成。

同帧 31 个 Job Worker 上的动画工作量如下。表内为并行工作线程耗时之和，只用于识别工作量来源，不能与主线程耗时直接相加：

| 工作线程 Marker | 合计工作量 | 调用数 |
|---|---:|---:|
| `Animator.ProcessAnimations` | 7.702 ms | 975 |
| `Animator.WriteTransforms` | 6.141 ms | 1025 |
| `Animator.ProcessGraph` | 5.249 ms | 960 |
| `Director.PrepareFrameJob` | 4.688 ms | 927 |
| `AnimationClipPlayable.EvaluateClip` | 2.584 ms | 1919 |

`AnimationClipPlayable.EvaluateClip` 在 145 / 300 帧中超过 1500 次，这组帧平均约 1937 次调用；其余 155 帧平均约 1006 次。高调用组的 `Animators.Update` 平均 6.597 ms，低调用组为 5.995 ms，约高 10.0%；整帧平均只高 0.435 ms。这说明多 Clip/混合求值提高了常驻成本，但 10.586 ms 的极端帧仍主要取决于 Job 完成时间与同帧其它线程负载，而不是简单的调用数翻倍。

表现层后续优化优先级据此调整为：减少活跃 Animator 数量或改为 GPU/实例化动画；其次减少不必要的多 Clip/混合求值；最后才是继续压缩已经只有 1.684 ms/Tick 的 `ApplyAuthority` 托管循环。当前样本只能证明 CPU 动画同步瓶颈，GPU Timing 缺失，不能把结论扩展为 GPU 已经饱和。

此前依据极限 A/B 预估完整 GPU Animation 可回收约 6.5 ms/帧；当前直接 Marker 净收益约 7.16 ms，约为预估值的 110%。多出的部分不能全部宣称为 VAT 内核收益，因为当前样本的渲染提交、Job 等待和帧等待状态也发生了变化。可以可靠表述为：**VAT 达到并略超过原先的 CPU 收益量级预估，同时把仍需播放动画的 1024 个怪物维持在约 0.969 ms/帧的托管更新成本。**

与完全静止的 Animator 关闭对照相比，VAT 新增 0.969 ms/帧逐实例驱动，但移除了约 1.55 ms/帧 SkinnedMesh 更新，直接动画相关预算仍净减少约 0.59 ms/帧。这说明当前 VAT 不只是接近静止白模上限，在 CPU 侧还因普通 MeshRenderer 替换 SkinnedMeshRenderer 获得了额外收益。

VAT 同时使 `Monster.View.ApplyAuthority` 从 1.786 降至 1.120 ms/Tick（-37.3%）。Collider 延迟同步保持 0.587 ms/Tick，与 A/B 样本的 0.585 ms 基本一致，因此 Collider 和权威 Transform 时序没有被移除；下降主要来自不再逐怪调用 Animator 参数接口。当前新的表现层 CPU 热点是 1024 个独立 `MonsterViewHandle.Update` 与每帧 `MaterialPropertyBlock` 更新，后续可考虑集中调度或实例数据缓冲，但应先补采 GPU Timing、Batches、SetPass 和 GPU 帧时间。

#### 7.10.3 当前尖峰与 GC

当前最大帧 13.690 ms，其中 TickDriver 6.927 ms、Entity 2.636 ms、`ApplyAuthority` 1.548 ms、Collider 同步 0.883 ms、VAT Update 0.797 ms、Finish Frame Rendering 3.767 ms；Animator 只有 0.082 ms。300 帧中没有任何一帧超过 16.67 ms，尖峰已从 Animator Job 等待转移为固定 Tick 与渲染提交的偶发叠加。

VAT 样本总 GC Alloc 为 211,720 B / 300 帧，平均 706 B/帧、最大 734 B/帧；`MonsterViewHandle.Update` 为 0 B。主要来源仍是 `NetworkPostLateUpdate` 固定 654 B/帧和 `UnityTransport` 固定 40 B/帧。`GarbageCollector.CollectIncremental` 平均 0.0007 ms、最大 0.0022 ms，没有形成 CPU 尖峰。

本轮仍没有 GPU Timing。VAT 将骨骼求值和蒙皮从 CPU 转移到顶点着色器纹理采样，CPU 结果不能证明 GPU、显存带宽或批次已经最优；后续必须在相同镜头和分辨率下补采 GPU Profiler / RenderDoc，并验证 Graphics Instancing 是否在真实 Player 中形成预期批次。

## 8. 怪物网络快照 GC 分析

### 8.1 GameplayNetworkTickDriver 的职责

`GameplayNetworkTickDriver` 是会话唯一的固定步长驱动器。它在每个 Unity `Update` 中累计 `unscaledDeltaTime`，按 30 Tick/s 推进 `NetworkSimulationClock`，并限制每帧最多追赶 4 个 Tick。

它不只执行网络收发。`clock.AdvanceOneTick()` 会同步触发注册到 Tick 的玩家、武器和怪物权威模拟，因此 Profiler 中显示在 `GameplayNetworkTickDriver.Update()` 下的时间和分配是整条固定 Tick 调用树的 Inclusive 数据。

怪物服务注册关系：

```csharp
_network.Clock.TickCompleted += TickAuthority;
```

每 2 Tick，`TickAuthority` 生成一份完整怪物表现快照：

```csharp
if (tick % (uint)_presentationIntervalTicks != 0)
    return;

MonsterPresentationFrame frame = AuthorityRoom.CaptureFrame(tick);
ApplyPresentationFrameLocal(frame);
_transport.SendPresentation(frame);
```

因此 Profiler 把下游 `CaptureFrame` 的分配归属到 `GameplayNetworkTickDriver.Update()`，不代表 TickDriver 自身的计时器或循环每次分配了 8 KB。

### 8.2 约 8.3 KB 的直接来源

当前 Capture 先创建两块数组：

```csharp
var mask = new byte[(world.SlotCount + 7) / 8];
var states = new MonsterPackedState[world.AliveCount];
return new MonsterPresentationFrame(serverTick, world.SlotCount, mask, states);
```

`MonsterPresentationFrame` 构造函数随后为了防御外部修改，再分配并复制一份：

```csharp
_activeMask = new byte[maskLength];
_activeStates = new MonsterPackedState[activeCount];
```

512 怪时：

- 512 个 `MonsterPackedState` 按当前托管布局约占 4,096 B；
- Capture 和构造函数各有一份，约 8,192 B；
- 两份 64 B ActiveMask 共约 128 B；
- 再加数组头、`MonsterPresentationFrame` 对象和对齐开销，得到约 8.3–8.5 KB 的新增分配。

最新样本中 115 个逻辑 Tick 对应 57 个大额分配帧，正好符合每 2 Tick 一次快照。大额帧整帧 GC Alloc 平均约 9.25 KB；扣除网络和引擎常驻的约 0.73–0.79 KB 后，怪物快照净增约 8.46 KB。

### 8.3 GC 横向对比

| GC 来源 | 阶段 B 普通规模 | 阶段 C 512 怪 | 阶段 D 大规模怪物 + 双缓冲 | 阶段 E AOT 新基线 | 阶段 G VAT |
|---|---:|---:|---:|---:|---:|
| `GameplayNetworkTickDriver.Update` | 20,880 B | 486,896 B | 3,880 B | 3,520 B | 1,400 B |
| `NetworkPostLateUpdate` | 195,546 B | 195,546 B | 195,546 B | 196,200 B | 196,200 B |
| `UnityTransport` | 12,000 B | 11,960 B | 12,000 B | 12,000 B | 12,000 B |
| Voice | 1,520 B | 160 B | 2,040 B | 360 B | 40 B |
| 总分配 | 236,648 B / 300 帧 | 706,314 B / 299 帧 | 225,206 B / 300 帧 | 223,022 B / 300 帧 | 211,720 B / 300 帧 |
| 平均每帧 | 789 B | 2,362 B | 751 B | 743 B | 706 B |

阶段 C 最大单帧分配约 9.33 KB，没有达到 10 KB。`GarbageCollector.CollectIncremental` 最大仅 0.0022 ms，Flow Field Build 和 Integration Field 均为 0 B。因此：

> 阶段 C 的约 9 KB 周期现象是 GC Alloc 尖峰，不是 GC Collection 暂停；它会增加长期运行中的回收频率，但不是当时 20–25 ms CPU 尖峰的直接原因。

这不代表阶段 C 的 8.3 KB 可以忽略。怪物快照约 15 次/s，按净增 8.46 KB 估算约产生 127 KB/s、7.6 MB/min 的托管垃圾；即使单次分配本身只消耗很短时间，它仍会持续填充托管堆，最终迫使 GC 更频繁地开始回收。该问题随后通过所有权转移和双缓冲解决，阶段 D 已实测快照链路 0 B。

`GC.Alloc`记录“本帧新申请了多少托管内存”，`GarbageCollector.CollectIncremental`记录“回收器本帧为处理已有垃圾执行了多久”，两者不是同一件事。本样本的0.0022 ms只是最慢一次增量回收切片耗时：Unity将一次回收中的标记工作拆到多帧执行，以较多的小切片换取更少的单帧长暂停。若关闭增量GC或堆压力触发无法摊开的完整回收，回收时间可能集中到单帧。当前结论应表述为“分配压力明确存在，但这段样本尚未出现由回收器造成的明显卡顿”。

### 8.4 可压缩空间

1. **防御性双拷贝已经消除。** `MonsterPresentationFrame` 已改为内部所有权转移构造，直接接管 Capture 或 Decode 的缓冲区。
2. **怪物快照双缓冲已经实施并完成 Player 复测。** 怪物服务和接收 Transport 分别持有独立双缓冲，使用 `CaptureInto` / `ReadPresentationInto` 覆盖已有数组。阶段 D 中 `Capture`、`Serialize`、`Presentation.Apply` 均为 0 B；`GameplayNetworkTickDriver.Update` 从 486,896 B 降至 3,880 B（-99.2%），约 8.3 KB 的周期快照分配已消失。总分配从 706,314 B / 299 帧降至 225,206 B / 300 帧（约 -68.1%）。Frame 只保证到下一次同方向快照开始写入前有效，事件订阅者不得长期持有其数组引用。
3. **降低快照频率。** `_presentationIntervalTicks` 从 2 调到 3 或 4，可将频率从 15 次/s 降至 10 或 7.5 次/s。双缓冲后这不再是 GC 优化项，只能继续降低 Capture/Serialize CPU 与网络带宽，并会增加表现插值跨度。
4. **按变化量或兴趣范围发送。** 可同时减少带宽和序列化 CPU，但属于更大规模的网络协议优化，不应作为第一步。

阶段 D 的剩余 225,206 B 主要来自固定的 `NetworkPostLateUpdate/UpdateFunction.Invoke` 195,546 B（约 86.8%）；其次为 `UnityTransport.Update` 12,000 B、`NetworkBehaviourUpdate` 5,840 B、DebugUpdater 4,930 B 和 TickDriver 3,880 B。Voice 合计 2,040 B / 300 帧，已不再存在 200 KB 级周期分配。增量 GC 共 0.240 ms、最大 0.0016 ms/帧，仍不是 CPU 尖峰来源。

阶段 E 继续验证了这一结果：快照链路 `Capture`、`Serialize`、`Presentation.Apply` 和 Flow Field 均为 0 B，TickDriver 总分配进一步降到 3,520 B；整段总分配为 223,022 B，平均 743 B/帧、P95 774 B、P99 814 B。原始最大值 1,704 B 出现在唯一一次窗口焦点切换帧，其中 `Application.InvokeFocusChanged` 额外分配 970 B，并非游戏逻辑周期分配。常态来源仍是 `NetworkPostLateUpdate/UpdateFunction.Invoke` 196,200 B（88.0%）、`UnityTransport` 12,000 B、`NetworkBehaviourUpdate` 5,280 B 和 DebugUpdater 4,692 B；Voice 仅 360 B。增量 GC 总计 0.230 ms、最大 0.0014 ms/帧，未形成 CPU 尖峰。

阶段 G VAT 样本进一步确认 1024 次/帧的 `MonsterViewHandle.Update` 不产生托管分配。300 帧总分配 211,720 B、平均 706 B/帧、最大 734 B；其中 `NetworkPostLateUpdate` 196,200 B、`UnityTransport` 12,000 B、`NetworkBehaviourUpdate` 2,080 B、TickDriver 1,400 B、Voice 40 B。TickDriver 总量低于阶段 E 主要因为更高帧率下 300 帧覆盖的现实时间更短、逻辑 Tick 更少，不能表述为单 Tick GC 再次下降；各路径仍是固定 40 B 级分配。增量 GC 最大 0.0022 ms，VAT 没有引入新的周期 GC。

## 9. 简历量化表述

可基于当前真实数据表述为：

> 使用 Unity Profiler 对 Windows Player 怪物房间卡顿建立分阶段量化基线，定位 30 Hz 权威模拟中密度 Cost 与 Source 变化触发的 70 × 70 多源 Flow Field 全量重建；通过将导航热循环改为直接数组内核、缓存连接掩码和邻居偏移，并为玩家 Source 引入距离阈值与 Tick 迟滞，使 Integration Field 平均耗时由 38.40 ms 降至 9.42 ms（-75.5%），单次 Build 最大耗时由 41.53 ms 降至 10.45 ms（-74.8%），普通样本中 33 ms 以上卡顿帧由 4 帧降至 0；在 512 怪压力测试中，将完整重建次数由 12 次降至 5 次、摊销成本由 0.448 ms/帧降至 0.166 ms/帧，并保持寻路阶段 0 B GC。

网络部分可以独立表述为：

> 通过 Profiler 分配归属和 30 Hz Tick 周期交叉验证，定位 512 怪全量表现快照每 2 Tick 产生约 8.5 KB 托管分配，确认其来自 Capture 与不可变 Frame 构造的双数组复制，而非固定 Tick 驱动器本身，为后续所有权转移和缓冲区复用提供量化依据。

完成态可以更新为：

> 将怪物全量表现快照改为所有权转移与发送/接收双缓冲复用，在更高怪物规模的 300 帧 Player 压测中，使 `GameplayNetworkTickDriver.Update` 托管分配由 486,896 B 降至 3,520 B（-99.3%），消除每次快照约 8.3 KB 的周期分配，并将整段样本总分配由 706,314 B 降至 223,022 B（-68.4%）。

AOT 迁移可以独立表述为：

> 将 70 × 70 多源 Flow Field 计算内核从 CLR 热更新解释执行迁入 IL2CPP AOT，在相同 5 次重建、相同 Source/Cost 构成的 Player 压测中，使 `FlowField.Build` 平均耗时由 9.829 ms 降至 0.832 ms（-91.5%）、最大耗时由 10.108 ms 降至 0.990 ms（-90.2%），Build 帧平均由 29.745 ms 降至 20.530 ms，并保持寻路链路 0 B GC。

表现层基线可以表述为：

> 为约 1025 个活跃动画对象补充权威端表现同步 Marker，在大规模怪物 Player 压测中将逐对象姿态提交量化为平均 1.684 ms/Tick、最大 2.387 ms、0 B GC，延迟 Collider 同步平均 0.536 ms/Tick；同时确认 `Animators.Update` 平均 6.286 ms/帧，极端帧因等待动画 Job 达 10.586 ms，蒙皮更新平均 0.790 ms/帧，据此将后续优化重点从已经低于 1 ms 的 Flow Field Build 转向 GPU/实例化动画与 Density 重算。

VAT 完成态可以表述为：

> 针对约 1024 个怪物 Animator 的 CPU Job 同步瓶颈，先以 `Animator.enabled = false` 建立极限 A/B，量化出约 4.9 ms/帧关键路径收益和 1.58 ms/帧残余 SkinnedMesh 成本；随后落地位置/法线纹理 VAT 与普通 MeshRenderer，将 `Animators.Update` 从 6.651 ms 降至 0.065 ms（-99.0%）、Skinned Mesh Update 从 1.566 ms 降至 0.025 ms（-98.4%），在新增 0.969 ms/帧 VAT 实例驱动后，直接动画相关 CPU 预算仍由 8.217 ms 降至 1.060 ms（-87.1%），300 帧中 16.67 ms 以上帧由 119 帧降至 0，并保持 VAT 更新 0 B GC。

## 10. 当前结论

1. 原始怪物房间卡顿来自周期性完整 Flow Field 重建，并受到 Player 热更新解释执行方式放大。
2. 直接数组内核、连接缓存和 Source 迟滞先将算法成本与重建频率压低；迁入 IL2CPP AOT 后，`FlowField.Build` 平均 9.829 ms 降至 0.832 ms、最大 10.108 ms 降至 0.990 ms，Flow Field 已不再是阶段 E 的 CPU 尖峰来源。
3. 共享流场成本没有随怪物数量线性增长，大规模怪物压力下仍保持 0 B GC，扩展性设计得到验证。
4. VAT 已使怪物 Animator 和 SkinnedMesh 路径基本退出：`Animators.Update` 6.651 → 0.065 ms/帧，Skinned Mesh Update 1.566 → 0.025 ms/帧；新增的 1024 次 `MonsterViewHandle.Update` 平均 0.969 ms/帧，直接动画相关 CPU 预算净降约 7.158 ms/帧（-87.1%）。
5. Density 与 Separation AOT 后，Density 重算平均 2.618 → 0.735 ms（-71.9%），`SeparationBuild` 平均 2.218 → 0.256 ms/Tick（-88.5%）。VAT 样本中二者分别约 0.733 ms/次和 0.231 ms/Tick，保持新基线。
6. 怪物快照双缓冲已将 TickDriver 分配从 486,896 B 降至 3,520 B（-99.3%），原约 8.3 KB 周期快照分配已消失；当前主要 GC 来源是 `NetworkPostLateUpdate/UpdateFunction.Invoke` 的固定分配。
7. 阶段 G 的 300 帧最大值为 13.690 ms，且没有任何帧超过 16.67 ms；当前 CPU 尖峰主要来自固定 Tick、Entity、`ApplyAuthority`、Collider 同步与渲染提交的偶发叠加，Animator Job 等待已经退出尖峰来源。
8. 阶段 G 总 GC Alloc 为 211,720 B、平均 706 B/帧、最大 734 B；VAT 更新 0 B，增量回收最大 0.0022 ms。主要分配仍来自 `NetworkPostLateUpdate` 的固定 654 B/帧，而不是怪物表现。
9. 当前新的 CPU 优化候选是 1024 个独立 `MonsterViewHandle.Update` 和逐实例 `MaterialPropertyBlock` 更新；但本样本没有 GPU Timing，VAT 的 GPU 纹理采样、顶点成本、显存带宽和实际实例批次仍需专项验证，不能仅凭 CPU Profiler 宣称整体 GPU 成本也已降低。
