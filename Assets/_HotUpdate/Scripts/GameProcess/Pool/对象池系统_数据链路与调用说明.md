# 对象池系统：数据链路与调用说明

> 适用模块：`LocalObjectPool`、`LocalVFXPool`、`SyncObjectPool`  
> 核心依赖：`ConfigManager`、Addressables、Unity `ObjectPool<T>`、UniTask  
> 设计目标：**数据驱动、按需加载、阶段级释放、支持热更新与后续 Mod 扩展。**

---

## 1. 总体设计

三个对象池虽然负责的对象不同，但资源生命周期保持一致：

```text
Excel 配置
    ↓
生成 Config C# 类型
    ↓
MessagePack 二进制配置
    ↓
Addressables 发布
    ↓
LobbyScene：ConfigManager 加载并反序列化
    ↓
GameRuntime：Pool.InitializeAsync()
    ↓
读取对应配置表，建立 PoolEntry
    ↓
Unprepared
    ↓ PreparePoolAsync
Addressables 加载 Prefab
    ↓
创建 ObjectPool
    ↓
Prewarm
    ↓
Prepared
    ↓
Rent / Play / Spawn
    ↓
Return / DespawnAndReturn
    ↓
ReleasePool / ReleasePools
    ↓
Pool.Clear + Addressables.Release
```

三个池的职责：

| 模块 | 对象类型 | 主要接口 | 额外职责 |
|---|---|---|---|
| `LocalObjectPool` | 普通 `GameObject` | `Prepare / Rent / Return / Release` | 通用本地对象复用 |
| `LocalVFXPool` | 本地表现特效 | `Prepare / Play / Return / Release` | VFX、Particle、Trail、Rigidbody 等运行时状态清理 |
| `SyncObjectPool` | `NetworkObject` | `Prepare / Spawn / DespawnAndReturn / Release` | NGO NetworkPrefab 动态注册与 Handler 接管 |

---

## 2. 为什么注册数据从 Inspector 移到 ConfigManager

旧模式中，Pool 的注册信息直接序列化在 GameRuntimeScene 的 Inspector 中：

```text
GameRuntimeScene
    ↓
LocalObjectPool
    ↓
Inspector Pool List
```

这种方式的问题是：即使 Addressables 下载了新的资源，Scene 中已经序列化的 Pool List 也不会自动增加新的注册项。

现在改为：

```text
Excel
    ↓
ConfigManager
    ↓
Pool.InitializeAsync()
```

因此配置更新后，只要新的配置数据在进入 GameRuntime 前已经被 `ConfigManager` 加载，对象池初始化时就能自动识别新的 Pool。

例如线上新增：

```text
Room_Forest_C
```

只需要更新：

```text
配置表
+
Room_Forest_C 的 Addressable 资源
```

不需要重新打开 GameRuntimeScene 修改 Inspector。

## 3. 配置层、定义层、运行时层

### 3.1 Excel / ConfigManager

配置表负责描述静态数据：

```text
PoolId
PrefabAddress
InitialCapacity
MaxSize
GroupName
```

三个 Pool 分别读取：

```text
Config_LocalObjectPool
Config_LocalVFXPool
Config_SyncObjectPool
```

### 3.2 PoolItemConfig

`PoolItemConfig` 是配置层与对象池之间的只读适配对象：

```csharp
public sealed class PoolItemConfig
{
    public string Id { get; }
    public string PrefabAddress { get; }
    public int InitialCapacity { get; }
    public int MaxSize { get; }
}
```

它回答：

> 这个 Pool 的定义是什么？

### 3.3 PoolEntry

`PoolEntry` 是对象池私有的运行时状态。

典型内容：

```text
Config

Prefab
Addressables Handle

ObjectPool

RentedCount / PlayingCount

IsPrepared
IsPreparing
PrepareCompletion
```

它回答：

> 这个 Pool 现在处于什么状态？

因此：

```text
Config = 静态定义
PoolEntry = 运行时状态
```

两者不要混在一起。

## 4. Initialize 与 Prepare 必须分离

### InitializeAsync

只做：

```text
ConfigManager.GetTable<T>()
    ↓
校验配置
    ↓
建立 PoolEntry
```

不加载 Prefab。

初始化结束后：

```text
Pool 已注册
但资源尚未加载
```

### PreparePoolAsync

真正需要某个 Pool 时才执行：

```text
Addressables.LoadAssetAsync
    ↓
获得 Prefab
    ↓
CreateRuntimePool
    ↓
Prewarm
```

因此：

```text
Registered != Prepared
```

这样不会因为进入 GameRuntime 就一次性把所有地图、敌人和特效资源拉入内存。

---

## 5. Prepare 的共享异步设计

同一个 Pool 可能被多个系统同时请求：

```text
MapBuilder ─────┐
EnemySpawner ───┼─> PreparePoolAsync("Enemy_Wolf")
OtherSystem ────┘
```

正确行为不是加载三遍，而是：

```text
第一次调用
    ↓
创建 PrepareCompletion
    ↓
启动唯一 PrepareEntryAsync

后续调用
    ↓
等待同一个 PrepareCompletion
```

调用方自己的 `CancellationToken` 只取消：

```text
“我不等了”
```

而不是取消：

```text
“所有人共享的资源加载”
```

真正的 Prepare 绑定 Pool 自身的 `_lifetimeCts`，只有 Pool Shutdown 才终止它。

## 6. Addressables、Prefab 与实例的三个层级

要区分：

```text
AssetBundle
    ↓
资源容器

Prefab Asset
    ↓
Addressables Handle 持有的资源

GameObject / NetworkObject Instance
    ↓
ObjectPool 中复用的运行时实例
```

`ReleasePool` 主要做两件事：

```text
Pool.Clear()
    ↓
销毁闲置实例

Addressables.Release(handle)
    ↓
降低 Prefab 及其依赖资源的引用
```

Bundle 是否真正卸载，不由 Pool 直接决定。

Pool 不应该主动：

```csharp
assetBundle.Unload(...);
```

而应该只释放自己持有的 Addressables Handle。

---

## 7. Prewarm 的作用

例如：

```text
InitialCapacity = 10
```

Prepare 时主动执行：

```text
Get × 10
Release × 10
```

从而提前建立 10 个实例。

作用是把：

```text
Instantiate
组件扫描
初始化
```

从战斗高频阶段提前到加载阶段。

因此：

```text
Prepare = 异步资源准备阶段
Rent / Play / Spawn = 同步高频阶段
```

## 8. LocalObjectPool 使用示例

### 8.1 准备

```csharp
await LocalObjectPool.Instance.PreparePoolAsync("Room_Forest_A", cancellationToken);
```

批量准备：

```csharp
await LocalObjectPool.Instance.PreparePoolsAsync(requiredPoolIds, cancellationToken);
```

### 8.2 租借

```csharp
GameObject room = LocalObjectPool.Instance.Rent("Room_Forest_A", position, rotation, parent);
```

`Rent` 不会隐式触发 Addressables 加载。

如果没有 Prepare：

```text
直接抛出异常
```

这是刻意设计的。

### 8.3 返还

```csharp
LocalObjectPool.Instance.Return(room);
```

调用方不需要再传 PoolId。

Pool 通过：

```text
InstanceId
    ↓
_entryByInstanceId
    ↓
PoolEntry
```

找到它原本属于哪个池。

### 8.4 释放

```csharp
LocalObjectPool.Instance.ReleasePool("Room_Forest_A");
```

只有：

```text
RentedCount == 0
```

才允许 Release。

## 9. LocalVFXPool 使用示例

### Prepare

```csharp
await LocalVFXPool.Instance.PreparePoolAsync("Explosion", cancellationToken);
```

### Play

```csharp
GameObject effect = LocalVFXPool.Instance.Play("Explosion", position, rotation, 1.5f);
```

### Return

```csharp
LocalVFXPool.Instance.Return(effect);
```

VFXPool 在实例第一次创建时缓存：

```text
ParticleSystem[]
TrailRenderer[]
VisualEffect[]
Rigidbody[]
VFXImpactScaler[]
IPoolable[]
```

后续 Play / Return 不重复扫描组件。

## 10. IPoolable

池对象可选择实现：

```csharp
public interface IPoolable
{
    void OnRentFromPool();
    void OnReturnToPool();
}
```

典型用途：

### OnRentFromPool

```text
重置生命值
重置刚体速度
创建新的 CancellationTokenSource
重新注册事件
恢复临时状态
```

### OnReturnToPool

```text
取消事件订阅
停止异步任务
清理临时状态
停止计时器
```

组件只在实例创建时扫描一次，之后使用缓存数组。

## 11. RentedCount / PlayingCount 的意义

全局：

```text
_rentedInstanceIds
```

负责检测：

```text
重复 Rent
重复 Return
```

每个 `PoolEntry`：

```text
RentedCount
PlayingCount
```

负责判断：

> 这个具体 Pool 能不能被 Release？

例如：

```text
Enemy_A：RentedCount = 3
Enemy_B：RentedCount = 0
```

此时：

```text
Enemy_A 不能 Release
Enemy_B 可以 Release
```

不会因为其他 Pool 仍在使用而阻止无关 Pool 的释放。

---

## 12. ReleasePools 为什么先检查再释放

批量释放采用两阶段：

```text
第一阶段
检查所有 Pool 是否都可释放

第二阶段
全部通过后统一 Release
```

避免：

```text
A 成功 Release
B 因为还有对象未返还而失败
C 尚未执行
```

导致资源集合处于“释放了一半”的状态。

---

## 13. 地图资源集合的典型调用

例如旧地图与新地图：

```text
Old = { Forest_A, Forest_B, Connection }
New = { Factory_A, Factory_B, Connection }
```

计算：

```text
Release = Old - New
Prepare = New - Old
Keep    = Old ∩ New
```

然后：

```csharp
LocalObjectPool.Instance.ReleasePools(releaseIds);
await LocalObjectPool.Instance.PreparePoolsAsync(prepareIds, cancellationToken);
```

这样：

```text
Connection
```

不会被无意义地卸载后马上重新加载。

---

## 14. Release 与 Shutdown 的区别

### ReleasePool

```text
销毁当前 Pool 实例
释放 Prefab Handle
保留 Pool Definition
```

之后：

```text
可以再次 Prepare
```

### ShutdownAsync

```text
结束 Pool 整个 GameRuntime 生命周期
取消后台 Prepare
处理遗留实例
释放全部资源
删除所有 Pool Definition
```

之后不能继续使用，除非重新 Initialize。

## 15. 热更新与 Mod 扩展

当前官方配置：

```text
Excel
    ↓
ConfigManager
    ↓
Pool Register
```

未来 Mod 可以复用同一入口：

```text
Mod Catalog / Mod Config
    ↓
解析新的 Pool Definition
    ↓
RegisterPoolDefinition(...)
    ↓
PreparePoolAsync(...)
```

推荐最终开放类似：

```csharp
public bool RegisterPoolDefinition(PoolItemConfig config);
public bool UnregisterPoolDefinition(string poolId);
```

这样对象池不需要知道配置来自：

```text
官方 Excel
热更新
DLC
Mod
```

只需要接收合法的 Pool Definition。

---

## 16. 三个 Pool 的共同不变量

1. `Initialize` 只登记定义，不加载 Prefab。
2. 未 Prepare 的 Pool 禁止 Rent / Play / Spawn。
3. 同一个 Pool 同时只存在一个真实 Prepare。
4. Pool 内实例禁止业务层直接 `Destroy`。
5. Release 前必须没有租出实例。
6. Addressables Handle 的持有周期与 Prepared 状态一致。
7. `ReleasePool` 保留定义，`Shutdown` 删除定义。
8. Pool 只负责当前进程资源生命周期，跨客户端资源 Ready 属于上层流程。

## 17. 当前结构总结

最终的数据链：

```text
Excel
    ↓
MessagePack
    ↓
Addressables Config
    ↓
ConfigManager
    ↓
PoolItemConfig
    ↓
PoolEntry
    ↓
Addressables Prefab
    ↓
Unity ObjectPool
    ↓
Runtime Instance
```

核心原则可以概括为：

> **稳定的是 Pool 管理逻辑，变化的是配置与资源。**

> **配置决定“有什么”，Prepare 决定“什么时候加载”，Pool 决定“实例怎么复用”，Release 决定“什么时候不再需要”。**
