# 怪物空间网格模块横向盘点与统一快照映射

执行阶段和验收步骤分别见：[怪物四叉树核心 AOT 迁移执行方案](怪物四叉树核心AOT迁移执行方案.md)、[怪物统一空间快照执行方案](怪物统一空间快照执行方案.md)。

> 状态说明（2026-10-28）：统一预移动快照的第一版代码已接入。本文第 2～6 节保留迁移前后的职责对照和目标架构；具体已删除数组、`FineCellOfSlot`、`ActiveSlots` 复用以及本轮未合并的后移动遍历，以《怪物统一空间快照执行方案》的“当前实现记录”为准。

## 1. 这份盘点要解决什么问题

当前项目里出现了多个名字相近的 Grid、Cell、Bucket 和 Spatial Index。它们并不是同一类数据：有的描述房间静态地形，有的描述动态阻挡，有的描述怪物占用，有的描述路径成本，还有的只负责邻居配对。

统一空间快照的目标是收拢“怪物当前位置到空间桶的归属”这一份事实，减少重复遍历和重复建桶；它不要求把导航拓扑、Flow Field、Unity Physics 碰撞体和怪物占用强行合并到同一个数组。

## 2. 当前模块横向对比

|---|---|---|---|---|---|---|
| `RuntimeNavigationGrid` | 固定二维导航 Grid | `RoomSpatialData` 的静态地图 | `RoomSpatialData.CellSize`，压测场为导航 Cell | `_staticWalkable`、`_dynamicBlocked`、`_additionalCost`、`_densityCost`、`_walkableCache`、`_connectionMask`、`_combinedCost` | 动态阻挡或 Cost 版本变化时按需刷新 | 保留为导航层；只让它消费共享 Density 计数，不接管怪物实体桶 |
| `RuntimeNavigationObstacleSystem` | 动态阻挡 Cell 写入器 | 场景中的 `RuntimeNavigationObstacle`/`BoxCollider` | 导航 Cell 的 AABB 覆盖范围 | `_blockerCounts`、`ObstacleState.Cells`、`IsBlocking` | 移动障碍每 Tick 检查，开关阻挡时即时修改 | 保留在导航层；不放入怪物实体空间快照 |

| `NavigationTopologyKernel` | 八方向可通行连接掩码 | `RuntimeNavigationGrid._walkableCache` | 导航 Cell | `_connectionMask` | 拓扑版本变化时刷新 | 保留为导航层 AOT Kernel |

## 3. 各模块的真实职责

### 3.1 `RuntimeNavigationGrid`：导航事实，不是怪物实体索引

`RuntimeNavigationGrid` 建立在 `RoomSpatialData` 之上。静态地形通过 `_staticWalkable` 固化；动态障碍由 `_dynamicBlocked` 表示；额外代价和密度代价分别保存在 `_additionalCost` 与 `_densityCost`；`_walkableCache`、`_connectionMask` 和 `_combinedCost` 是给寻路 Kernel 使用的缓存。

它的版本语义是：

```text
TopologyVersion -> Walkable / ConnectionMask
CostVersion     -> CombinedCost
```

这套 Grid 关心“这个 Cell 能不能走、代价是多少”，不关心“当前有哪些怪物占据这个 Cell”。因此它应继续作为导航层所有者。统一空间服务可以向它提供 `CellCount` 产生的 Density 输入，但不能把导航数组当成实体空间桶。

### 3.2 `RuntimeNavigationObstacleSystem`：导航 Grid 的动态写入器

动态障碍系统读取场景中的 `RuntimeNavigationObstacle` 和 `BoxCollider`，把障碍物的世界包围盒转换成导航 Cell 的 `RectInt`。`_blockerCounts` 用来处理多面墙体重叠：一面墙移走时，不能清掉另一面墙仍占据的 Cell。

它维护的是地图拓扑事实，不是怪物移动事实。动态墙可以在 `PreSimulation` 改变导航 Grid，并在之后触发 `RuntimeNavigationGrid.TopologyVersion`；这条链路不应被实体空间快照替代。

### 3.3 `MonsterNavigationDensitySystem`：重复做了实体到导航 Cell 的投影

Density 每 6 个 Tick 扫描一次 `MonsterWorld`，对每个活跃 Slot 调用 `RoomSpatialUtility.WorldToCell`，写入 `DensityKernel.MonsterCounts`。随后 Kernel 在半径 2 的导航 Cell 范围内传播影响，进行平滑并生成 `_outputCost`，最后回写 `RuntimeNavigationGrid.ReplaceDensityCost`。

这里最适合接入统一空间快照的是第一段：

```text
当前：MonsterWorld 全量 Slot -> WorldToCell -> MonsterCounts
目标：SpatialSnapshot.CellCount -> DensityKernel.MonsterCounts
```

`_influence`、`_smoothedCost`、`_outputCost` 和权重数组仍属于 Density 算法，不应塞进实体空间服务。统一服务只提供当前 Cell 的怪物数量，Density 继续负责如何把数量变成导航 Cost。

### 3.4 `MonsterSeparationSystem`：已有 AOT 邻居桶，但桶的所有权仍在模块内

Separation 在 HotUpdate 侧收集 `_positions` 和 `_activeSlots`，在 AOT `SeparationKernel` 内按分离半径建立桶。当前桶边长就是分离半径，Kernel 预计算四个无重复的邻接方向，然后计算桶内和邻接桶之间的成对分离力。

它的空间部分和统一快照高度重合：

- Slot 的位置和 ActiveMask 来自同一个 `MonsterWorld`；
- 桶归属是一次 Slot→空间桶映射；
- 邻接桶是其他邻域查询也可能需要的候选关系。

迁移时可以保留 `SeparationKernel.CalculatePairs` 和 `_separation` 输出，只把 `BuildBuckets` 所需的桶头、Slot 链和邻接桶输入改为由房间空间服务提供。这样不会把分离力公式误塞进空间服务。

### 3.5 `MonsterSpatialIndex`：当前通用查询后端和 AOT 候选

四叉树直接基于 `MonsterWorld.Meta[].IsActive` 和 `Motion[].Position` 建立。它预分配最大深度节点数组，先建立 BaseDepth=4 的基础树，再将活跃 Slot 插入叶节点；热点叶节点超过 `SplitThreshold` 后继续细分，最多到 MaxDepth=6。

它维护的数组各有明确用途：

| 数组 | 用途 | 是否属于统一 Grid 的长期形态 |
|---|---|---|
| `_nodes` | 四叉树节点和区域边界 | 替换为 Grid 的 Cell 元数据 |
| `_queryStack` | 查询遍历临时栈 | 保留为查询临时缓冲，但改成 Cell/桶访问 |
| `_nextSlot` | Slot 链表 | 可以保留为共享 `nextSlot` |
| `_previousSlot` | O(1) 移除的反向链 | 可以保留，或由连续候选范围替代 |
| `_leafBySlot` | Slot 当前叶节点 | 对应共享 `cellOfSlot` |
| overflow 链 | 房间 Bounds 外的 Slot | 对应统一服务的 out-of-bounds/overflow 集合 |

目前 Weapon 的弹丸、范围、风暴云和连锁查询都通过房间入口消费它。四叉树 AOT 迁移可以先沿用这些数组和查询语义，不需要先改成 Grid。

### 3.6 `MultiSourceFlowField`：使用导航 Grid 的结果，不是实体空间桶

Flow Field 的 `_costs`、`_directions` 和 `_sourceIndices` 与怪物占用没有一一对应关系。它们表示每个导航 Cell 到玩家 Source 的路径结果，输入是导航层的 Walkable、ConnectionMask 和 TraversalCost。

Flow Field 已经有 AOT 迁移经验，应该继续保持独立。统一实体空间服务最多在未来提供玩家或怪物的 Cell 位置，不应把路径成本数组和实体 Slot 链表混在一起。

## 4. 统一 Grid 应该接管哪些内容

统一服务的核心对象可以定义为 `MonsterSpatialSnapshot`，它只拥有怪物实体在房间空间中的事实：

```text
MonsterWorld.Position / ActiveMask
          |
          v
一次 Slot -> FineCell 归属
          |
          +-- cellHead / nextSlot / cellOfSlot
          +-- cellCount
          +-- activeCellList
          +-- 可选 coarseCellCount
          +-- 可选 neighborCellLookup
```

推荐接管的内容：

1. 活跃 Slot 到空间 Cell 的归属；
2. Cell 的 Slot 链或连续候选范围；
3. CellCount 和粗粒度聚合计数；
4. 邻接 Cell 查询；
5. Slot 的死亡、迁移、新增增量；
6. `QueryCircle`、`QuerySweptCircle`、`QueryNearest` 等候选查询。

建议继续留在原模块的内容：

1. 静态地形、DynamicBlocked、ConnectionMask 和导航 Cost；
2. Flow Field 的 Dijkstra/堆/方向场；
3. Density 的 Influence、平滑和 Cost 输出；
4. Separation 的距离公式、重叠方向和 Separation 输出；
5. Weapon 的伤害、穿透、链式 visited 和窄相判断；
6. Unity Physics 的墙体碰撞和 `Physics.SyncTransforms()`。

## 5. 粒度如何统一，而不是复制多套 Grid

当前模块有三种明显粒度：

```text
导航 Cell       = RoomSpatialData.CellSize
Separation 桶   = SeparationRadius，当前约 3 米
四叉树叶节点    = 按密度自适应，约束在房间 Bounds 内
```

统一实现优先使用一套细粒度基础 Cell，再从同一次建桶结果生成粗粒度信息：

- Fine Cell：以怪物平均受击半径或查询密度选择尺寸；
- Coarse Cell：由 2×2、4×4 Fine Cell 聚合得到，服务 Density 和空区域判断；
- Neighbor Lookup：由 Fine Cell 坐标计算邻接范围，服务 Separation；
- Radius Query：根据查询半径计算 Cell AABB，服务 Projectile 和范围效果。

Separation 不一定需要强行使用导航 Cell。如果导航 Cell 是 1 米、分离半径是 3 米，可以在一次 Fine Cell 建桶后按 3×3 邻域读取候选；也可以在同一次建桶时生成 3 米级的 `coarseCellOfSlot` 和 `coarseCellCount`。关键是两个层级共享同一次 Position/Active 采集和一次基础归属过程，而不是分别从 `MonsterWorld` 扫描。

## 6. 推荐运行时链路

```text
WorldSimulation
  -> MonsterWorld 更新全部怪物位置
  -> MonsterSpatialSnapshot 标记 Dirty

MeleeCombat
  -> 结算近战及可能的 Active/Position 增量

SpatialSnapshot / CombatSimulation 首次查询
  -> Dirty 时一次 Build 或应用增量
  -> 生成 FineCell、CellCount、粗粒度计数和邻接元数据

CombatSimulation
  -> Projectile: QuerySweptCircle
  -> Range Effect: QueryCircle
  -> Lightning: QueryNearest / QueryCircle
  -> Damage/Push: 通过 RoomRuntime 更新 World 和 Snapshot 增量

DensityUpdate
  -> 直接读取 Snapshot.CellCount
  -> DensityKernel 负责传播、平滑和输出 Cost

SeparationBuild
  -> 读取 Snapshot 的桶/邻接候选
  -> SeparationKernel 负责成对距离和分离力
```

当前 `MonsterSpatialIndex` 是懒 Build；统一快照阶段可以先保留懒策略，再逐步增加显式 `PrepareSpatialSnapshot`。显式准备点应位于所有位置、死亡和击退变化完成之后，或者必须提供增量覆盖层。

### 6.1 同 Tick 内的死亡和击退

空间快照不能只保存位置，还需要处理 Active 和位置变化：

- `DamageMonster` 让怪物死亡：从 Cell 链表摘除，或写入 `RemovedSlots` 覆盖层；
- `PushMonster` 改变位置：从旧 Cell 摘除并插入新 Cell，或写入 `MovedSlots`；
- 新增 Slot：插入对应 Cell，不能等到下一 Tick 才让查询看见；
- 查询返回候选后仍需检查 Active，避免同 Tick 已死亡对象继续参与伤害。

当前四叉树已经通过 `Remove`、`Relocate` 和查询时的 `TryGetMonsterPosition` 保证了这些语义。未来 Grid 需要保留同样的边界，不能为了“一次建桶”而牺牲同 Tick 的命中正确性。

## 7. AOT 迁移现在是否可以开始

可以开始，但应把“开始核心 AOT 迁移”和“直接改生产架构”分开。当前四叉树已经有足够的量化指标用于确定迁移对象和验收指标：单次 Build、Build 频率、Query、候选数、访问节点数以及 Host Main Thread 都已记录。

不过 `20261026-162947-530d99d1` 是旧架构基线，其中还包含 Host 每 Tick 的旧表现同步路径。为了避免把表现层修正和 AOT 收益混在一起，正式 AOT 对照应先补一轮“当前代码、四叉树仍在 HotUpdate”的 5012 基线，然后再迁移 AOT 核心：

```text
旧压测记录
  -> 保存为历史问题基线

当前架构 + 四叉树 HotUpdate
  -> 新的 AOT 对照基线

当前架构 + 四叉树 AOT
  -> 测量解释执行放大比例

当前架构 + Grid AOT
  -> 测量数据结构和重复空间工作的收益
```

第一阶段建议只迁移 `MonsterSpatialIndex` 的纯数组内核，保留 `MonsterRoomRuntime`、`MonsterRuntimeService` 和 Weapon 查询接口不变。AOT 核心应接收：

- `PositionX[]` / `PositionY[]` 或连续 Position 数组；
- `ActiveMask[]`；
- `SlotCount`；
- 房间 Bounds；
- BaseDepth、MaxDepth、SplitThreshold；
- 调用方提供的节点、链表、Stack 和结果数组。

验收条件是命中候选集合、死亡/击退后的增量行为、候选排序约定和 Query 统计保持一致；性能比较再看 Build 和 Query 是否下降。AOT 迁移通过后，再决定是否把四叉树后端替换为共享 Grid。

## 8. 分阶段迁移清单

| 阶段 | 变化 | 保持不变的内容 | 目的 |
|---|---|---|---|
| A | 当前架构下补四叉树 HotUpdate 基线 | 查询 API、命中语义、压测配置 | 隔离之前 Host 表现修正的影响 |
| B | 四叉树纯内核迁入 `AOT_Core` | RoomRuntime、Weapon、MonsterWorld 接口 | 得到 AOT 对照 |
| C | `MonsterRuntimeService` 固定空间查询接口 | Weapon 精确过滤和伤害语义 | 隐藏后端替换 |
| D | Grid 快照后端接入同一接口 | 调用方 API | 比较 QuadTree AOT 与 Grid AOT |
| E | Density 改读共享 CellCount | Density Kernel 传播和平滑 | 删除一次全量 Slot→Cell 扫描 |
| F | Separation 使用共享桶/邻接候选 | Separation Kernel 距离公式 | 删除独立桶构建 |
| G | 清理重复数组、旧 Build 路径 | 导航拓扑和 Flow Field | 收拢空间事实所有权 |

## 9. 当前结论

- 当前四叉树已经具备开始 AOT 核心迁移的量化基础；
- 迁移前应补一轮当前架构下的 HotUpdate 基线，避免旧 `ApplyAuthority` 路径污染 AOT 对照；
- 统一 Grid 的核心对象是怪物实体空间快照，不是把导航 Grid、Flow Field 和实体桶合成一张数组；
- Density 最适合先消费共享 `CellCount`，Separation 最适合先复用共享桶和邻接候选；
- 四叉树可以先作为统一查询接口后的 AOT 后端，Grid 替换应在 AOT 结果和同语义基线之后进行；
- 不同粒度应通过 Fine Cell + 粗粒度聚合元数据实现，避免各模块再次独立建桶。
