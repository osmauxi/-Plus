# 玩家同步一轮测试

## 阅读前的术语与代码名说明

本文在术语第一次出现时使用“英文（中文解释）”。后续为避免重复，只保留英文简称。

| 术语 | 含义 |
|---|---|
| Host（主机） | 同一进程同时承担 Server 和本地 Client 的节点 |
| Client（客户端） | 采集本地输入、进行预测并接收权威状态的节点 |
| Server（服务器） | 校验输入并产生最终权威玩家状态的节点 |
| Owner（对象拥有者） | 有权为某个网络玩家提交输入的 Client |
| Observer（观察者） | 观看其他玩家，只消费快照并插值表现的 Client |
| Tick（固定模拟步） | 固定频率推进的一次网络模拟序号；30 Hz 表示每秒 30 Tick |
| Snapshot（状态快照） | Server 发给 Client 的某个 Tick 玩家状态 |
| Full Snapshot（完整快照） | 不依赖其他快照即可还原完整玩家状态的关键帧 |
| Delta Snapshot（增量快照） | 只保存相对某个完整快照变化量的小型快照 |
| Baseline（基准快照） | 解码 Delta 时必须持有的那份 Full Snapshot |
| Exact（精确匹配输入） | 输入原始 Tick 与下一 Server Tick 完全相同 |
| RetimedLate（迟到重定时输入） | 已迟到但在安全窗口内，被映射到下一 Server Tick 的最新输入 |
| Reuse / Reused（沿用输入） | 缺包时短暂继续使用上一份输入 |
| Neutral（中立输入） | 不移动、不瞄准、不冲刺的安全输入 |
| Rollback（回滚重演） | Owner 恢复权威旧状态，再重演其后的本地输入 |
| Hard Resync（硬同步） | 无法普通回滚时，直接跳到 Server 权威状态 |
| Pipeline（传输管线） | 消息采用的可靠性、顺序性和发送通道组合 |
| Payload（应用数据净荷） | 玩家同步代码实际序列化的数据，不含底层协议头 |
| RTT（往返延迟） | 数据从本端到对端再返回所需时间 |
| P95 / P99 | 95% / 99% 样本不超过的耗时，用于观察多数帧和尾部尖峰 |
| GC（垃圾回收分配） | 每帧产生的托管内存分配，过高可能触发卡顿 |
| NGO（Netcode for GameObjects） | Unity 的 GameObject 网络同步框架，负责连接、所有权和网络对象生命周期 |
| UTP（Unity Transport） | NGO 下方实际收发数据并提供网络管线的传输层 |
| NetworkObject（网络对象） | 由 NGO 分配唯一编号并在多端 Spawn/Despawn 的对象 |
| Spawn / Despawn（网络生成 / 销毁） | 让网络对象在各端出现或被移除的生命周期操作 |
| Actor（测试玩家实体） | 测试中实际带 Owner、输入和同步组件的网络玩家 |
| Harness（测试编排器） | 自动启动双端、驱动用例、采集指标和写结果的组件 |
| Editor / Clone（编辑器 / 克隆工程） | 主 Unity Editor 与 ParrelSync 创建的第二个测试 Editor |
| JSON（结构化文本数据） | 本轮保存每档 Host/Client 原始指标的结果格式 |
| FPS / VSync（帧率 / 垂直同步） | 每秒渲染帧数，以及将帧率限制到显示器刷新节奏的选项 |
| UDP | UTP 底层使用的无连接网络传输协议 |
| HybridCLR / IL2CPP | Unity 热更新运行方案 / 将托管代码转换成本地代码的构建后端 |
| EditMode（编辑器测试模式） | 不启动完整游戏流程，直接验证算法和组件逻辑的测试模式 |

## 结论

当前玩家同步链路已经可运行、可自动化测试。

- Baseline（无弱网基准档）：Host、Client 均通过。
- Typical（常见弱网档，80 ms 延迟、20 ms 抖动、2% 丢包）：Host、Client 均通过。
- Adverse（压力弱网档，180 ms 延迟、60 ms 抖动、10% 丢包）：Host 通过输入连续性门槛；Client 因 20 秒内发生 2 次 Hard Resync（硬同步），未通过“Hard Resync 必须为 0”的严格稳定性门槛。
- 三档均完成双玩家动态 Spawn（网络生成）、Owner 输入上行、服务器权威模拟、Owner 校正、Observer 插值和快照下行；没有断线、无效输入或未来 Tick 攻击数据。
- 常见弱网档发现并修复了“输入 Tick 一旦迟到便长期落后”的重大逻辑问题。修复后，同参数的服务器中性 Tick 从 313 降到 80，Owner 回滚从 151 降到 14。

当前状态可概括为：正常网络与常见弱网可用；极端弱网下链路仍持续工作，但偶发 Hard Resync（硬同步）和 Delta 缺 Baseline（增量快照缺少解码基准）仍需优化。

## 脚本逻辑问题与修复

### 1. 未存储净化后的输入

`PlayerServerAuthority.PushInput` 原来会校验并生成 `sanitized`，但环形缓冲写入的是原始 `input`。这会让超长移动向量、未归一化瞄准方向和未定义按钮位进入权威模拟。

已修复为只存储 `sanitized`，并增加回归测试验证：

- 移动向量限制到单位圆；
- Aim 方向归一化；
- 未定义按钮位被清除。

### 2. 延迟后输入 Tick 长期过期

修复前 Typical 首次诊断中：

| 指标 | 修复前 | 修复后 |
|---|---:|---:|
| Exact Tick（精确输入步数） | 86 | 0 |
| Retimed Late Tick（迟到重定时输入步数） | 0 | 282 |
| Reused Tick（沿用上一输入步数） | 53 | 90 |
| Neutral Tick（中立输入步数） | 313 | 80 |
| Neutral（中立输入）比例 | 约 69.2% | 约 17.7% |
| Owner Rollback（拥有者回滚） | 151 | 14 |
| Hard Resync（硬同步） | 0 | 0 |

根因是 Client 与 Server Tick 基本等速推进；网络延迟一旦耗尽 Client 初始领先量，之后每个输入到达时都已被 Server 处理。三份历史冗余能抗丢包，但不能恢复持续迟到。

修复策略为受限的服务器迟到输入重定时：

- 默认最多重定时迟到 12 Tick（30 Hz 下 400 ms）的最新输入；
- 只接受客户端 Tick 单调更新的最新迟到输入，旧冗余包不能覆盖它；
- 下一权威 Tick 没有 Exact 输入时，优先执行 `RetimedLate`；
- Exact 仍优先于 RetimedLate，之后才是最多 3 Tick 的输入沿用，最后回中立；
- 超窗迟到、非法输入、过远未来 Tick 仍拒绝。

`ServerOutdatedInputs` 在修复后仍会很高，因为它统计“原始 Tick 已迟到”的包，其中包括已被安全重定时救回的最新输入和冗余历史包。判断稳定性应结合 Retimed/Reuse/Neutral，而不能单看 Outdated 总数。

## 轻量纯 C# 时钟专项回归

### 实现范围

`PlayerSimulationClock` 当前只实现：

- `TickRate`（每秒固定模拟步数）；
- `TickDeltaTime`（单个模拟步的秒数）；
- `CurrentTick`（当前固定步编号）；
- `Reset`（在 Spawn、Warp、Hard Resync 时重新对齐）；
- `AdvanceOneTick`（由外部驱动推进一个 Tick，并支持 `uint` 回绕）。

Controller 在每次 NGO Tick 到达时先推进 Clock（时钟），再把同一个 Tick 交给 Prediction（预测）或 ServerAuthority（服务器权威）。本轮没有加入独立 `Update` 累加器、Catch-up（追帧）或 Drift Correction（漂移校正）。

## 稳定性解读

### Baseline（无弱网基准档）

- 0 Rollback（回滚）、0 Hard Resync（硬同步）、0 Delta Baseline 丢弃（增量快照缺基准而丢弃）。
- 39 个 Neutral Tick 主要对应确定性输入脚本中的静止区间和心跳间隔，不是网络故障。
- 作为链路正确性和性能基准可接受。

### Typical（常见弱网档）

- 修复后权威输入连续性恢复，Neutral（中立输入）比例 17.7%，明显低于 35% 门槛。
- 14 次 Rollback（回滚）、0 Hard Resync（硬同步），Owner 可通过普通回滚恢复。
- 28 个 Delta（增量快照）因缺少匹配 Full Baseline（完整基准快照）被丢弃，说明 Reliable Full（可靠发送的完整快照）与 Unreliable Delta（不可靠发送的增量快照）跨 Pipeline（传输管线）的到达/丢失问题已经可观测。
- 作为当前常见弱网目标可接受，但快照 Baseline 协议仍应优化。

### Adverse（压力弱网档）

- 链路没有断开，输入、快照和观察者插值持续运行；Host Neutral（中立输入）比例仍控制在 15.5%。
- Client 出现 40 次 Rollback（回滚）和 2 次 Hard Resync（硬同步），未通过严格门槛，可能对应可见瞬移或状态跳变。
- 88 个 Delta（增量快照）因 Baseline（基准快照）不可用而丢弃，Snapshot（状态快照）有效到达密度显著下降。
- 该档位是当前系统极限，不应标记为稳定通过。

## 测量限制

1. 测试为同机双 Editor，不等价于 Development Player、真机或跨地域网络；Editor 本身会影响 GC 和最大帧耗时。
2. 尝试构建独立测试 Player 时，HybridCLR/IL2CPP 会从 Player 中移除 `HotFix.Gameplay`，而测试程序集直接引用它，UnityLinker 无法解析；因此独立 Player 构建没有作为有效测试数据。该问题属于测试构建基础设施，不是同步链路运行错误。
3. UTP `GetCurrentRtt`（读取 Transport 当前 RTT 估算值的方法）在本轮显示 Baseline 182 ms、Typical 277 ms、Adverse 500 ms。Baseline 存在估算器初值/Editor 开销，绝对值不应视为真实 localhost RTT；相对变化可以证明 NetworkSimulator 参数已进入 UTP。
4. `RemotePresentationStallSamples`（远端表现位置本帧未变化的采样数）同时包含网络缓冲耗尽和输入脚本主动静止帧，不能单独当作网络卡顿率。
5. 每轮结果写入后，后关的一端可能记录一次 UTP Socket receive failed；它发生在结果落盘后的测试退出阶段，不在采样窗口内。正式 Host 轮次结束时 Unity Console Error 为 0。
