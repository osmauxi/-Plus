# 玩家同步系统本轮修改介绍

## 术语与改动对象说明

| 术语 | 含义 |
|---|---|
| Host（主机） | 同时运行 Server 与本地 Client 的节点 |
| Client（客户端） | 采集输入、进行预测并接收权威状态的节点 |
| Owner（对象拥有者） | 有权为某个玩家网络对象提交输入的 Client |
| Observer（观察者） | 只接收并表现其他玩家快照的 Client |
| Tick（固定模拟步） | 固定频率推进的一次玩家模拟序号 |
| Snapshot（状态快照） | Server 在某 Tick 下发的玩家状态 |
| Full / Delta Snapshot（完整 / 增量快照） | Full 可独立还原；Delta 依赖 Baseline 才能还原 |
| Baseline（基准快照） | 解码 Delta 所依赖的 Full Snapshot |
| Exact（精确输入） | 输入原始 Tick 与下一 Server Tick 完全匹配 |
| RetimedLate（迟到重定时输入） | 安全窗口内最新迟到输入被映射到下一 Server Tick |
| ReusedPrevious / Reuse（沿用上一输入） | 短时缺包时有限次数继续使用上一输入 |
| Neutral（中立输入） | 不移动、不瞄准、不冲刺的安全输入 |
| Rollback / Replay（回滚 / 重演） | 恢复权威旧状态并执行后续未确认输入 |
| Hard Resync（硬同步） | 无法普通回滚时直接跳到 Server 权威状态 |
| Payload（应用数据净荷） | 同步代码序列化的字节，不含底层协议头 |
| RTT（往返延迟） | 数据从本端到对端再返回的估算时间 |
| GC（垃圾回收分配） | 运行期间产生的托管内存分配 |
| NetworkSimulator（网络模拟器） | 为 Transport 注入延迟、抖动和丢包的测试组件 |
| NGO（Netcode for GameObjects） | Unity 的连接、所有权、网络对象和 Tick 框架 |
| UTP（Unity Transport） | NGO 下方实际收发数据并提供网络管线的传输层 |
| NetworkObject（网络对象） | 由 NGO 管理、拥有唯一网络编号和 Owner 的对象 |
| Spawn（网络生成） | 让 NetworkObject 在 Server 与各 Client 上出现 |
| Pipeline（传输管线） | 消息采用的可靠性、顺序性和发送通道组合 |
| Editor / Clone（编辑器 / 克隆工程） | 主 Unity Editor 与 ParrelSync 创建的第二测试 Editor |
| Harness（测试编排器） | 自动建立双端、施加弱网、采集指标并写结果的组件 |
| EditMode（编辑器测试模式） | 不启动完整游戏运行时、直接验证算法和组件逻辑的测试模式 |
| asmdef（程序集定义） | Unity 用来划分脚本程序集及声明依赖的配置文件 |
| JSON（结构化文本数据） | 本轮保存 Host/Client 原始测试指标的结果格式 |
| HybridCLR / IL2CPP | Unity 热更新运行方案 / 将托管代码转换为本地代码的构建后端 |
| per-client（按客户端分别维护） | 每个 Client 拥有独立状态，而不是所有 Client 共用一份 |
| AOI（关注区域） | 只向某 Client 同步附近或与其相关对象的策略 |
| Baseline / Typical / Adverse | 无弱网基准档 / 常见弱网档 / 压力弱网档 |

本轮主要改动对象：

| 代码名 | 作用 |
|---|---|
| `PlayerSyncConfig` | 保存 Tick、输入容错、校正、发送与插值参数 |
| `PlayerInputCommand` | 一条带 Tick 的移动、瞄准和按钮输入结构体 |
| `PlayerServerAuthority` | Server 侧接收输入、选择本 Tick 输入并执行权威模拟 |
| `PlayerSyncTransport` | 负责输入/快照序列化、发送、接收和端点路由 |
| `PlayerSyncController` | 按 Owner、Server、Observer 身份驱动整条同步链路 |
| `TrySanitize` | 检查非法数值并输出安全输入副本的方法 |
| `WithTick` | 复制输入并替换其 Tick 的方法 |
| `ResolveNextInput` | 按 Exact、RetimedLate、Reuse、Neutral 优先级选择下一输入的方法 |
| `PlayerSyncNetworkTestHarness` | 建立双 Editor 网络链路、施加弱网并采集结果的场景组件 |
| `PlayerSyncNetworkTestActor` | 驱动一个测试玩家输入并汇总其同步指标的组件 |
| `PlayerSyncEditModeTestAutomation` | 自动运行 EditMode 回归并协调测试流程的 Editor 脚本 |

## 修改结论

本轮测试确实触发了同步系统修改。

修改分为三部分：

1. 修复 Server（服务器）使用未净化输入的权威安全问题；
2. 修复常见弱网下输入 Tick（固定模拟步）持续迟到、权威模拟大量回到 Neutral（中立输入）的问题；
3. 增加双 Editor NetworkSimulator（网络模拟器）测试链路和可观测指标，使同步系统可以重复实测。

没有在本轮继续修改 Snapshot Baseline 和 Hard Resync 协议。它们已经通过测试确认，是下一轮优先事项。

## 修改前后行为对比

| 项目 | 修改前 | 修改后 |
|---|---|---|
| 输入净化 | `TrySanitize`（输入安全净化方法）成功后仍可能存储原始输入 | Buffer（缓冲）、迟到输入和模拟只使用 `sanitized`（净化后的输入） |
| 迟到输入 | 已处理 Tick 一律作为 Outdated（过期输入）丢弃 | 窗口内最新迟到输入可安全重定时到下一权威 Tick |
| 旧冗余 | 可能与最新迟到输入竞争 | 只接受 Client Tick 单调更新的最新迟到输入 |
| Server 输入优先级 | Exact（精确输入）后主要依靠 Hold（沿用）/Neutral（中立） | `Exact（精确） > RetimedLate（迟到重定时） > ReusedPrevious（沿用） > Neutral（中立）` |
| 高延迟连续输入 | 输入长期落后，持续回中立 | 常见弱网下大部分 Tick 由 RetimedLate 连续供给 |
| 可观测性 | 只能粗略看收发与回滚 | 增加 Payload（应用数据净荷）、Exact、Retimed、Reuse、Neutral 等指标 |
| 当前场景测试 | NetworkSimulator 没有真实同步流量 | 现有 GameObject 可启动 Host/Client、生成双玩家并写结果 |

Typical 同参数实测变化：

| 指标 | 修改前 | 修改后 |
|---|---:|---:|
| Exact Tick（精确匹配输入步数） | 86 | 0 |
| Retimed Late Tick（迟到重定时输入步数） | 0 | 282 |
| Reused Tick（沿用上一输入步数） | 53 | 90 |
| Neutral Tick（中立输入步数） | 313 | 80 |
| Neutral（中立输入）比例 | 约 69.2% | 约 17.7% |
| Owner Rollback（拥有者回滚） | 151 | 14 |
| Hard Resync（硬同步） | 0 | 0 |

Exact 变为 0 不是退化。80 ms 单向延迟条件下，Client 输入抵达时原始 Tick 已经处理完；修改后的有效执行来源是受限 `RetimedLate`。

## 一、生产同步逻辑修改

### 1. Server 只保存净化后的输入

文件：`Middle/PlayerServerAuthority.cs`

修改前：

- `PushInput` 调用 `TrySanitize(out sanitized)`；
- 校验通过后，部分路径仍把原始 `input` 写入输入历史；
- 超长 Move、未归一化 Aim 和未知 Buttons 位可能进入权威模拟。

修改后：

- 所有 Buffer 写入、Pending Late 保存和后续模拟统一使用 `sanitized`；
- 非法数值仍直接拒绝；
- 原始 Client 输入不再跨越权威边界。

这项修改不改变消息格式，只修正 Server 内部实际使用的数据对象。

### 2. 增加迟到输入重定时配置

文件：`Config/PlayerSyncConfig.cs`

新增配置：

```text
MaxLateInputRetimingTicks = 12
```

30 Hz 下默认代表约 400 ms。配置含义是“最新 Client 输入已经迟到时，Server 允许把它安全映射到下一权威 Tick 的最大迟到范围”。

同时增加 Validate 约束：该值必须小于 History Capacity，避免时间窗口超过历史结构的安全范围。

调节影响：

- 值更大：能承受更高 RTT，但旧意图允许生效的时间更长；
- 值更小：时间语义更严格，但弱网下更容易进入 Hold/Neutral；
- 设为 0：关闭迟到重定时，恢复严格 Exact/Outdated 行为。

### 3. 增加受限 RetimedLate 路径

文件：`Middle/PlayerServerAuthority.cs`

新增状态：

- `_pendingLateInput`：等待下一权威 Tick 消费的最新迟到输入；
- `_pendingLateSourceTick`：该输入的原始 Client Tick；
- `_latestObservedClientTick`：Server 已观察到的最新 Client Tick；
- `_hasPendingLateInput`、`_hasLatestObservedClientTick`：显式状态标记。

迟到输入只有同时满足以下条件才会进入 Pending：

1. 原始 Tick 已不新于 `_lastProcessedTick`；
2. 迟到距离不超过 `MaxLateInputRetimingTicks`；
3. Client Tick 比此前观察到的 Tick 更新；
4. 输入已经通过数值净化；
5. 不是包内更旧的冗余输入。

权威下一 Tick 的解析顺序修改为：

```text
Exact
  > RetimedLate
  > ReusedPrevious（最多 MaxInputHoldTicks）
  > Neutral
```

关键语义：

- Exact 永远拥有最高优先级；
- RetimedLate 只在没有 Exact 时生效；
- RetimedLate 消费时才使用 `WithTick(nextTick)`，保留原始 Tick 用于新旧判断；
- 一份 Pending 只消费一次；
- 旧冗余不会覆盖更新的 Pending；
- Reset/Warp 会清空全部 Pending 和时间观测状态。

### 4. 增加 Authority 输入解析指标

文件：

- `Middle/PlayerServerAuthority.cs`
- `Upper/PlayerSyncController.cs`

新增或向上暴露：

- `ExactInputTickCount`（实际执行精确匹配输入的 Tick 数）；
- `RetimedLateAcceptedInputCount`（被接受为候选的最新迟到输入数）；
- `RetimedLateInputTickCount`（实际执行迟到重定时输入的 Tick 数）；
- `ReusedInputTickCount`（实际沿用上一输入的 Tick 数）；
- `NeutralInputTickCount`（实际执行中立输入的 Tick 数）；
- `LastInputResolveResult`（最近一次权威输入最终来自哪种来源）。

这些指标解决了原来只能看到 `OutdatedInputCount`、无法判断 Server 最终执行了什么输入的问题。

需要注意：`OutdatedInputCount` 仍记录“原始 Tick 到达时已经迟到”，其中可能包含被 RetimedLate 救回的最新输入和包内历史冗余。因此修改后 Outdated 较高并不等于权威输入失败率较高。

### 5. 增加传输层 Payload 与消息计数

文件：`Lower/PlayerSyncTransport.cs`

新增指标：

- `InputPayloadBytesSent`（累计发送的输入应用层字节）；
- `SnapshotPayloadBytesSent`（累计发送的快照应用层字节）；
- `InputMessageSendCount`（已发送输入消息数量）；
- `SnapshotMessageSendCount`（已发送状态快照消息数量）；
- `DroppedDeltaWithoutBaselineCount`（因缺少基准快照而丢弃的 Delta 数）。

计数在写入自定义消息后、发送前累加，并在 `Shutdown` 清零。

口径限制：Payload 只包含 `FastBufferWriter.Length`，不包含 UDP、Unity Transport、NGO Named Message 和链路层头部。它适合做版本之间的相对比较，不等于实际网卡流量。

## 五、兼容性与风险说明

### 网络协议兼容性

本轮生产逻辑修改没有改变 `PlayerInputCommand` 或 Snapshot 的序列化字段布局。输入重定时发生在 Server 收包后的内部解析阶段，因此不要求 Client/Server 增加新的线上字段。

### 行为变化

高延迟下，Server 会更倾向执行 Client 最新意图，而不是因为原始 Tick 过期立即回中立。这是预期变化。

代价是窗口内的迟到输入可能在新的权威 Tick 生效。当前通过 12 Tick 上限和 Client Tick 单调性约束风险；上线前应根据目标地区 RTT 重新标定该值。

### 指标变化

修改后不能用 `OutdatedInputCount` 单独判断失败。推荐同时观察：

```text
ExactInputTickCount                 精确匹配输入执行次数
RetimedLateInputTickCount           迟到重定时输入执行次数
ReusedInputTickCount                沿用上一输入执行次数
NeutralInputTickCount               中立输入执行次数
HardResyncCount                     Owner 硬同步次数
DroppedDeltaWithoutBaselineCount    因缺基准快照而丢弃的 Delta 数
```

### 场景影响

Harness 挂在现有测试场景，但以临时配置文件作为启用开关。配置文件不存在时自动禁用，不改变普通离线玩家测试流程。

### 尚未解决的协议风险

本轮没有修改：

- Full/Delta 的 per-client Baseline 确认；
- Adverse 下 Hard Resync 原因分类与缓解；
- Observer 自适应 Jitter Buffer；
- 多玩家批处理、量化与 AOI；
- NGO TickRate 的强制单一来源；
- HybridCLR 独立 Player 压测入口。

## 七、回退与调参入口

如果需要只关闭迟到重定时，可将 `PlayerSyncConfig.MaxLateInputRetimingTicks` 对应序列化值设为 0；其余 Sanitize、未来 Tick 限制、输入 Hold 和 Neutral Heartbeat 仍然保留。

不建议回退净化输入修复，因为它属于权威输入安全边界。

如果需要从场景移除自动压测入口，应只移除 `PlayerSyncNetworkTestHarness`，保留原有 NetworkSimulator 时需确认是否仍有其他测试脚本使用。当前配置文件已经删除，通常无需为了普通 Play 而移除 Harness。

## 最终判断

本轮修改把玩家同步从“本地可运行，但持续延迟下权威输入大量失效”推进到“Baseline 和常见弱网可稳定完成完整同步链路”。

下一轮不应继续围绕输入重定时反复调参，而应优先解决 Delta Baseline 确认和 Hard Resync 原因分类；这两项已经是测试数据明确暴露的主要剩余问题。

## 八、后续追加：Motor 等脚本纯 C# 化

### 修改目标与边界

本次把 `PlayerMotor`（底层运动器）、`PlayerLocomotionController`（移动玩法控制器）、`PlayerSimulation`（预测与权威共用的模拟门面）从 `MonoBehaviour`（Unity 挂载组件基类）改为普通 C# 类，并按层级由 `PlayerSyncController`（玩家同步总控组件）唯一持有。

该纯 C# 模拟栈阶段把时钟问题留作 TODO（待办）；后续已按本文第九节加入轻量 `PlayerSimulationClock`。主循环仍订阅 `NetworkManager.NetworkTickSystem.Tick`（NGO 网络固定步事件），但 Tick 编号与单步时长不再由 Prediction 或 ServerAuthority 各自计算。

### 新持有链

```text
PlayerSyncController
  -> PlayerSimulation
      -> PlayerLocomotionController
          -> PlayerMotor
              -> IPlayerCharacterBody
                  -> CharacterControllerPlayerBody
                      -> Transform + CharacterController
```

- `IPlayerCharacterBody`（玩家身体接口）只暴露姿态、方向、碰撞移动、传送和坐标转换能力；
- `CharacterControllerPlayerBody`（CharacterController 身体适配器）把接口调用落到 Unity `Transform` 与 `CharacterController`；
- `PlayerMotor` 通过构造函数取得身体接口和 `PlayerMovementConfig`（移动参数结构体）；
- `PlayerLocomotionController` 通过构造函数取得 Motor 与 `PlayerStaminaConfig`（体力参数结构体）；
- `PlayerSimulation` 只持有 Locomotion，并通过它完成模拟、状态捕获、恢复与 Warp（强制传送）；
- `PlayerSyncController.Awake`（总控初始化方法）成为唯一 Composition Root（组合根，即创建并连接整棵对象依赖的入口）。

### 场景与 Prefab 迁移

生产玩家 Prefab 和网络测试玩家 Prefab 已删除三份旧算法组件挂载，并把原有移动/体力序列化值迁移到 `PlayerSyncController`。`PlayerLocomotionTest` 单机场景改由 `PlayerLocomotionTestDriver`（离线移动测试驱动脚本）构造同一套纯 C# 链，同时保留场景原来的加速度、瞄准速度和冲刺速度覆盖值。

调用入口也统一完成迁移：

- `LocalPlayerLocomotionDriver` 不再查找 Locomotion 组件，只把输入提交给 SyncController；
- `PlayerSpawnController` 不再回退查找 Motor 组件，优先调用 `PlayerSyncController.ResetAfterWarp`（传送后同时重置模拟与同步历史的方法）；
- SyncController 提供 MotionState（运动状态）、ControlState（控制状态）、StaminaState（体力状态）和 `SetLifeState`（写入生命状态）等只读/受控门面，避免上层反向取得底层对象。

### 为什么不把 CharacterController 也变成纯 C#

`CharacterController` 是 Unity 的碰撞移动组件，必须存在于 GameObject。此次把它包在身体适配器之后，使算法层不再直接依赖 Unity 组件 API（应用程序接口），但真正的场景碰撞仍由它执行。这样既保留引擎能力，又让对象所有权和测试边界清晰。

## 九、后续追加：轻量纯 C# 时钟模块

### 新增对象

新增 `Middle/PlayerSimulationClock.cs`。它是普通 C# 类，由 `PlayerSyncController.Awake`（同步总控初始化方法）构造和唯一持有：

```text
PlayerSyncController
  ├─ PlayerSimulationClock
  ├─ PlayerSimulation -> Locomotion -> Motor -> Body
  ├─ PlayerPrediction（Owner 时创建，共用 Clock）
  └─ PlayerServerAuthority（Server 时创建，共用 Clock）
```

当前时钟只负责：

```text
TickRate             每秒固定模拟步数
TickDeltaTime        单个模拟步对应的秒数
CurrentTick          当前已经派发的 Tick
Reset                重新对齐到指定 Tick
AdvanceOneTick       推进并返回下一个 Tick
```

没有加入时间累加器、Catch-up（追帧）、Drift Correction（漂移校正）、Pause（暂停）或 Time Scale（时间缩放）。这符合当前同步模块规模，也为二轮重构保留清晰入口。

### 调用链变化

修改前：

```text
NGO Tick
  -> Prediction 自增自己的 CurrentTick
  -> ServerAuthority 自增自己的 LastProcessedTick
```

修改后：

```text
NGO NetworkTickSystem.Tick（当前外部驱动信号）
  -> PlayerSyncController.HandleNetworkTick
      -> PlayerSimulationClock.AdvanceOneTick
          -> 将同一个 Tick 传给 Prediction 或 ServerAuthority
```

Prediction 的 `Predict`（执行一个本地预测步的方法）现在必须消费 Clock 已派发的 Tick；ServerAuthority 的 `SimulateNextTick`（执行一个权威模拟步的方法）会校验该 Tick 同时满足“Clock 当前 Tick”和“上一已完成 Tick + 1”。这样可以尽早发现重复推进或跳 Tick，而不是让错误进入历史缓冲。

`PlayerSyncConfig.TickDeltaTime` 已移除，Prediction 和 ServerAuthority 均使用 `PlayerSimulationClock.TickDeltaTime`，避免单步时长存在两个运行时来源。`InputSendRate`（输入发送频率）和 `SnapshotSendRate`（快照发送频率）仍在模拟 Tick 上使用原有间隔/Budget（发送额度）算法，协议和发送语义不变。

### 重置规则

- Spawn（网络生成）：以 Owner LocalTime（拥有者本地网络时间）或 ServerTime（服务器网络时间）设置起点；
- Hard Resync（硬同步）：Prediction 将 Clock 与预测历史一起重置到权威 Tick；
- Warp（强制传送）：SyncController 在清理模拟和网络历史前先重置 Clock；
- Despawn（网络销毁）：取消 NGO Tick 订阅并把 Clock 清零。

### 测试结果

- 编译：0 Error（错误）、0 Warning（警告）；
- EditMode：12/12 Passed（通过），同步专项 9/9；
- 新增 `SimulationClock_AdvancesResetsAndWraps`（时钟推进、重置、步长和回绕测试）；
- 新增 `Prediction_ConsumesTickFromSimulationClock`（预测消费统一 Tick 测试）；
- 单机场景运行无 Error；
- 四次 12 秒 NetworkSimulator（网络模拟器）样本均完成完整同步链路，Host 全部通过；Client 因分别发生 3、4、1、2 次 Hard Resync，未通过“必须为 0”的严格门槛。

因此本次修改可以确认“时钟抽象与同步链路已经接通”，但不能宣称“独立时钟问题已经解决”。当前 NGO 仍是 Driver（驱动源）；二轮重构应围绕独立累加器、受限追帧、漂移观测和 Hard Resync 原因分类继续展开。
