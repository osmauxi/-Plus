# 网络大包、分片与分组分频优化说明

## 1. 结论先行

当前 10024 怪物基线中，每次表现发布发送的是完整怪物状态快照，逻辑大小约为 **61,405 B（约 60 KiB）**，频率约为 **15 Hz**，因此发送量约为 **900 KiB/s**。

这已经不是“普通小消息”，不能按单个 UDP/UTP 数据包理解。它必须经过传输层拆分、排队和重组；当前代码还将表现流标记为 `FullSnapshot`，映射到 `ReliableFragmentedSequenced`，因此它是“高频可靠分片完整快照”。

网络层优化不只有“减少 CPU”一个目标，至少同时包含：

1. 减少序列化、复制、解码和本地应用 CPU；
2. 减少总带宽；
3. 减少底层分片、可靠队列和重传压力；
4. 降低单帧网络峰值，减少 Host 长帧和 Client 状态延迟。

只把一个 60 KiB 快照切成几个小组，可能只会降低单帧峰值，不一定减少总字节数；只有分频、增量和字段拆分才会稳定降低带宽。

## 2. 什么大小算“大包”

网络包需要区分三个概念：

| 层级 | 含义 | 当前应如何理解 |
|---|---|---|
| 逻辑消息 | 业务一次 `SendPresentation` 写出的完整数据 | 约 61 KiB |
| Transport Payload | UTP/Unity Transport 允许一次传输处理的有效负载 | 受 Transport 配置和头部影响 |
| IP/UDP 数据包 | 真正经过网络设备传输的单个包 | 通常受 MTU 限制，不能把 60 KiB 当成一个包 |

经验上可以这样理解：

| 逻辑消息大小 | 风险判断 |
|---:|---|
| 小于约 1.2～1.4 KiB | 通常有机会落在单个互联网 UDP 包内，但仍应以实际 Transport 配置为准 |
| 1.4～6 KiB | 很可能需要 Transport 层处理拆分或受到配置限制 |
| 大于 6 KiB | 已经不应按单包设计，必须确认分片、队列和重组行为 |
| 60 KiB 以上 | 明确属于大消息；应当主动设计分组/增量，不应依赖可靠分片兜底 |

Unity 官方文档对 Transport 的说明也指出，典型 MTU 约为 1400 字节，较大的消息需要允许分片；分片会增加延迟和内存压力。[Unity Transport 分片说明](https://docs.unity3d.com/es/2018.4/ScriptReference/Networking.ChannelOption.AllowFragmentation.html)

Unity Transport 2.x 还提供最大消息大小配置，默认值面向约 1400 字节级别的网络包，而不是把大业务消息当成单个网络包发送。[Unity Transport 2.x 配置说明](https://docs.unity3d.com/jp/2023.2/Manual/WhatsNew20232.html)

## 3. 当前项目的具体大小计算

当前 `MonsterNetworkCodec` 每个表现状态包含：

- 4 B：量化位置和朝向；
- 1 B：攻击序列；
- 1 B：受击序列。

10024 只怪物全部激活时：

```text
Header       = 8 B
ActiveMask   = ceil(10024 / 8) = 1253 B
MonsterState = 10024 × 6 = 60144 B
总大小       = 61405 B
```

当前项目配置中还可以看到：

```text
UnityTransport m_MaxPayloadSize = 6144
```

代码中的 `MonsterNetworkTransport.MaxPayloadBytes = 2 * 1024 * 1024` 只是业务层允许 `FastBufferWriter` 通过的上限，不是 MTU，也不是 Transport 单包上限。它只能说明“业务代码允许构造最多 2 MiB 的消息”，不能说明网络可以无分片发送 2 MiB。

因此 61,405 B 远超过 6,144 B 的配置量级。仅按 6,144 B 估算，至少需要：

```text
ceil(61405 / 6144) = 10 个 Transport Payload 单元
```

这只是下限，不等于实际 IP 包数量。实际数量还会受到 UTP 头部、可靠性头部、MTU、统计层和发送队列影响。

报告中的 Host 发送速率为约 `903.49 KiB/s`，而 449 次 Publish / 30 秒约为 15 Hz：

```text
61405 B × 14.97 Hz ≈ 899 KiB/s
```

这说明报告里的总字节数与“每 2 Tick 发送一个完整 60 KiB 快照”是吻合的。

报告同时显示约 `59.36 条消息/s`，约为逻辑 Publish 频率的 4 倍。这个值不能直接解释为“业务每秒调用了 59 次 SendPresentation”，它可能是：

- 分片后的传输统计；
- 多个接收目标的重复计数；
- 统计层记录口径与 `NetworkTransportStats` 不一致。

下一轮必须同时记录逻辑发送次数、`writer.Length`、按消息名统计的次数，以及底层分片/包数量，不能只看一个“消息/s”。

## 4. 当前整包中哪些字段最值得拆

60 KiB 快照中各部分大小约为：

| 字段 | 大小 | 占比 |
|---|---:|---:|
| 位置 + 朝向 | 10024 × 4 = 40096 B | 65.3% |
| 攻击/受击序列 | 10024 × 2 = 20048 B | 32.7% |
| ActiveMask + Header | 1261 B | 2.1% |

因此：

- 只删除 ActiveMask，收益很小；
- 攻击/受击序列如果不是每只怪物每帧都变化，应该改成事件或 Dirty 字段；
- 位置/朝向是最大部分，需要通过频率分层、兴趣范围、增量编码或更紧凑量化处理。

攻击/受击序列的实际收益必须先测 Dirty 比例。不能默认它们一定稀疏，也不能在没有数据时直接承诺可以节省 32.7%。

## 5. 当前代码中的两个关键事实

### 5.1 表现流实际是可靠分片

`MonsterNetworkTransport` 的注释写着“Presentation 高频不可靠”，但发送时使用的是：

```csharp
NetworkDeliveryClass.FullSnapshot
```

而 `NetworkMessageTransport` 将其映射为：

```csharp
NetworkDelivery.ReliableFragmentedSequenced
```

所以当前实际语义是：

```text
高频 + 完整快照 + 可靠 + 分片 + 有序
```

这不是普通的轻量表现流。网络发生拥塞或丢包时，旧的完整快照可能因为分片重传阻塞后续状态。

更合理的目标是：

```text
位置姿态：DeltaSnapshot / UnreliableSequenced
攻击、受击、Spawn、Despawn：可靠事件
周期性恢复：低频 FullSnapshot 或分组 Keyframe
```

### 5.2 Host 本地也重复应用了一遍网络快照

Host 当前路径是：

```text
MonsterWorld
  -> CaptureFrame
  -> MonsterPresentationFrame
  -> Replica.Apply
  -> MonsterViewWorld.ApplyReplica
  -> SendPresentation
```

这意味着 Host 为了本地表现走了一次“打包后再解包”的网络模拟路径。基线中：

```text
Monster.Replication.Publish     ≈ 3.693 ms/frame
Monster.Replication.ApplyLocal   ≈ 2.239 ms/frame
```

`ApplyLocal` 约占 Publish 的 60.6%，是网络重构时必须单独拆出的 CPU 成本。

## 6. 网络层优化如何看到成效

网络优化必须同时看四组指标。

### 6.1 业务逻辑层

```text
LogicalPublishCount/s
GroupSendCount/s
每组更新怪物数
DirtyPoseCount
DirtyAttackCount
DirtyHitCount
LifecycleEventCount
```

用于确认到底是“少发了逻辑数据”，还是只是把一个完整包切成了多个小包。

### 6.2 字节与分片层

```text
LogicalPayloadBytes/s
TransportPayloadBytes/s
FullSnapshotBytes/s
DeltaSnapshotBytes/s
EventBytes/s
FragmentCount/s
PacketCount/s
RetransmitCount/s
SendQueuePeak
```

其中 `LogicalPayloadBytes/s` 反映业务编码结果，`TransportPayloadBytes/s` 反映真正交给传输层的数据量。两者必须分别记录。

### 6.3 CPU 层

Host：

```text
Monster.Replication.Publish
Monster.Replication.Capture
Monster.Presentation.Serialize
Monster.Replication.ApplyLocal
Monster.Presentation.Apply
Monster.Network.SendPresentation
Monster.Network.SendPresentation.Transport
```

Client：

```text
Monster.Network.ReceivePresentation
Monster.Presentation.Decode
Monster.Replication.ReceiveApply
Monster.Presentation.Apply
```

不要只看网络带宽下降。可能出现：

- 带宽下降，但 Delta 编码更重，CPU 上升；
- 总字节不变，但分组后每帧峰值下降，P95 改善；
- Host CPU 下降，但 Client View 仍然每帧遍历 10024 个 Slot，Client 帧率不变。

### 6.4 游戏体验与一致性

```text
StaleFrameCount
DroppedGroupCount
MissingGroupCount
InterpolationGap
LifecycleMismatch
ReplicaActiveCount 与 AuthorityActiveCount 差值
```

表现流即使允许丢包，也不能允许 Spawn、Despawn、攻击事件和受击事件丢失。

## 7. 分组分频重构的可量化路径

### 阶段 A：只分组，不减少总字节

将怪物分成稳定组，保持每只怪物的更新频率和总字节基本不变，只把一个 60 KiB 快照拆成多个逻辑组，并通过 Tick 相位错开发送。

目标：

- Replication P95 下降；
- Host 长帧减少；
- SendQueue 峰值下降；
- 总字节保持在基线 ±5% 内。

这一阶段验证的是“平滑峰值”，不是带宽优化。

### 阶段 B：引入频率层级

使用 Gameplay Tick 的整数分频：

```text
高优先级：15Hz，每 2 Tick
普通组：10Hz，每 3 Tick
低优先级：5Hz，每 6 Tick
```

优先级依据：

- 与玩家距离；
- 是否在视野或战斗范围内；
- 是否攻击、受击或刚生成；
- 是否处于快速移动状态。

这一阶段才会真正减少总字节数和序列化次数。

### 阶段 C：拆分生命周期和事件

```text
Spawn/Despawn：可靠事件
Attack/Hit：可靠事件或序列化事件
Pose：不可靠有序增量流
Keyframe：低频恢复帧
```

ActiveMask 不再随每个完整表现帧发送，Replica 维护自己的生命周期状态。

### 阶段 D：Host Authority 直连表现层

Host 不再通过 `Replica.Apply` 处理自己的网络帧，而是：

```text
MonsterWorld -> Host View
MonsterWorld -> Remote Group Encoder
```

这一步主要减少 CPU，不一定减少网络字节。

## 8. 阶段性验收标准

### 分组但不降频

- 总逻辑字节变化不超过 ±5%；
- Replication P95 和最大单帧下降；
- 不增加 Stale/Missing Group；
- Host 本地表现与远端表现一致。

### 分组 + 分频

- `LogicalPayloadBytes/s` 明显下降；
- `Serialize`、`Capture`、`ReceiveApply` 的平均和 P95 同步下降；
- Host Main Thread P95 下降；
- Client 插值间隔不出现明显断层。

### 事件拆分 + Authority 直连

- Host `ApplyLocal` 大幅下降或消失；
- Host `Publish` 不再包含本地 Replica 全量解码；
- 事件可靠性保持不变；
- GC Alloc 不增加。
