# 网络玩家同步问题与实现经验

## 1. 文档定位

这是一份可以脱离具体项目阅读的网络玩家同步经验文档。示例使用接近 Unity/C# 的伪代码，但原则同样适用于其他引擎。

本文讨论的基本架构是：

- Server Authority（服务器权威）：服务器决定最终状态；
- Local Prediction（本地预测）：本地 Owner 立即预测自己的输入；
- Reconciliation（权威校正）：Owner 收到权威状态后校正并重放未确认输入；
- Snapshot Interpolation（快照插值）：非 Owner 玩家使用快照缓冲插值；
- Fixed Tick（固定模拟步）：输入、模拟和历史都使用固定 Tick 序号。

常用英文术语速查：

| 术语 | 含义 |
|---|---|
| Host（主机） | 同时承担 Server 和本地 Client 的进程 |
| Client（客户端） | 提交输入、进行本地预测并接收权威状态的节点 |
| Owner（对象拥有者） | 有权为某个网络对象提交输入的 Client |
| Observer（观察者） | 观看其他玩家、只消费快照表现的 Client |
| Tick（固定模拟步） | 固定频率推进的一次模拟序号 |
| Snapshot（状态快照） | Server 在某个 Tick 产生并下发的玩家状态 |
| Full Snapshot（完整快照） | 不依赖其他快照即可还原状态的关键帧 |
| Delta Snapshot（增量快照） | 只保存相对某个完整快照变化量的数据 |
| Baseline（基准快照） | 解码 Delta 所必需的 Full Snapshot |
| Exact（精确输入） | 原始输入 Tick 与下一权威 Tick 完全匹配 |
| RetimedLate（迟到重定时输入） | 窗口内最新迟到输入被映射到下一权威 Tick |
| ReusedPrevious / Hold（沿用上一输入） | 短时缺包时有限次数继续执行上一输入 |
| Neutral（中立输入） | 不移动、不瞄准、不冲刺的安全输入 |
| Rollback / Replay（回滚 / 重演） | 恢复旧权威状态，再执行后续未确认输入 |
| Hard Resync（硬同步） | 无法普通回滚时直接跳到权威状态 |
| Pipeline（传输管线） | 消息使用的可靠性、顺序性和发送通道组合 |
| Payload（应用数据净荷） | 业务代码序列化的数据，不含底层协议头 |
| RTT（往返延迟） | 数据从本端到对端再返回所需时间 |
| Jitter Buffer（抖动缓冲） | 用一段快照历史吸收网络到达时间波动 |
| Ring Buffer（环形缓冲） | 固定容量、满后覆盖最旧槽位的历史容器 |
| Warp（强制传送） | 复活、换层或 Server 强制改变玩家位置的事件 |
| Transport（传输层） | 实际负责序列化、发送、接收和消息管线的网络层 |
| Network Simulator（网络模拟器） | 为 Transport 注入可重复延迟、抖动、丢包或乱序的测试工具 |
| Ack（确认消息） | 接收方明确告诉发送方某份数据已经成功持有 |
| AOI（关注区域） | 只同步某 Client 附近或相关对象的可见性策略 |
| GC（垃圾回收分配） | 托管内存分配与回收，过高可能产生运行时卡顿 |
| P50 / P95 / P99 | 50% / 95% / 99% 样本不超过的分位值，用来观察常态和尾部尖峰 |
| Dedicated Server（专用服务器） | 只运行 Server、不同时承担本地 Client 的服务器进程 |
| Clone（克隆测试工程） | 用同一项目副本启动第二个 Editor/进程进行跨端测试 |
| Baseline / Typical / Adverse | 无弱网基准档 / 常见弱网档 / 压力弱网档 |

每个问题都按以下结构说明：

1. 什么时候发生；
2. 常见错误代码；
3. 代码实际如何执行；
4. 为什么产生问题；
5. 推荐实现；
6. 应该怎样测试。

文末附带设计检查表和弱网测试矩阵。本项目本轮测试数据只放在最后作为案例，不是理解正文的前提。

## 2. 通用数据模型

后文示例统一使用以下简化类型：

```csharp
[Flags]
public enum InputButtons : byte
{
    None   = 0,
    Aim    = 1 << 0,
    Sprint = 1 << 1,
}

public struct InputCommand
{
    public uint Tick;
    public Vector2 Move;
    public Vector2 Aim;
    public InputButtons Buttons;
}

public struct PlayerState
{
    public uint Tick;
    public Vector3 Position;
    public Quaternion Rotation;
    public Vector3 Velocity;
    public float Stamina;
    public int ControlState;
}

public enum InputSource
{
    Exact,
    RetimedLate,
    ReusedPrevious,
    Neutral,
}
```

这些示例代码名的作用：

| 代码名 | 作用 |
|---|---|
| `InputButtons` | 用位标记保存瞄准、冲刺等按钮状态的枚举 |
| `InputCommand` | 保存某 Tick 移动、瞄准和按钮输入的结构体 |
| `PlayerState` | 保存可用于快照、恢复和回滚的玩家状态结构体 |
| `InputSource` | 标记权威 Tick 最终使用 Exact、RetimedLate、Reused 或 Neutral 中哪种输入 |
| `TrySanitize` | 检查非法数值并输出范围安全输入的方法 |
| `PushInput` / `PushUntrusted` | 把 Client 输入送入 Server 权威输入解析器的方法 |
| `ResolveNext` / `ResolveNextInput` | 为下一 Server Tick 按优先级选择输入的方法 |
| `Predict` / `Simulate` | 分别表示本地预测和推进一次固定步模拟 |
| `CaptureState` / `RestoreState` | 捕获完整运行状态、或恢复到指定历史状态的方法 |
| `Reconcile` | 比较预测与权威状态并决定确认、回滚或硬同步的方法 |
| `WithTick` | 复制输入内容并替换 Tick 的辅助方法 |
| `TickMath` | 处理 `uint` Tick 回绕比较和距离计算的工具类 |

代码块中的其他方法名属于教学伪代码；其作用会在代码块前后直接说明，并不要求项目中存在同名实现。

术语说明：

- Exact（精确输入）：输入原始 Tick 与下一权威 Tick 完全相同；
- RetimedLate（迟到重定时输入）：输入已经迟到，但满足安全条件，被映射到下一权威 Tick；
- ReusedPrevious（沿用上一输入）：短时缺包时沿用上一份输入；
- Neutral（中立输入）：不移动、不瞄准、不冲刺的中立输入；
- Full Snapshot（完整快照）：可以独立还原完整状态的关键帧；
- Delta Snapshot（增量快照）：依赖某个 Full Baseline 的增量；
- Hard Resync（硬同步）：无法普通回滚时，直接把预测端跳到权威状态。

## 3. 场景存在 Network Simulator，但没有真实网络流量

### 发生条件

测试场景中已经挂载延迟、抖动和丢包模拟组件，但玩家仍由本地脚本直接驱动 Transform 或移动控制器，没有真正启动 Host/Client，也没有数据经过 Transport。

### 常见错误代码

```csharp
void Update()
{
    Vector2 move = ReadKeyboard();
    localPlayer.Move(move);       // 直接修改本地玩家
}

void Start()
{
    networkSimulator.DelayMs = 100;
    networkSimulator.PacketLoss = 5;
}
```

代码看起来同时具备“玩家移动”和“网络模拟器”，但二者没有任何调用关系。`localPlayer.Move` 没有序列化、发送、接收过程，因此延迟和丢包参数不会影响它。

### 为什么容易误判

- Play Mode 正常启动；
- 玩家能移动；
- Inspector 能看到模拟器参数；
- Console 没有错误。

这些都只能证明离线移动和组件挂载正常，不能证明同步链路正常。

### 推荐实现

测试入口至少要建立一条真实的闭环：

```csharp
async Task StartNetworkCase(NetworkProfile profile)
{
    NetworkManager host = await StartHost();
    await WaitUntil(() => host.IsListening);

    NetworkManager client = await StartClient(profile);
    await WaitUntil(() => client.IsConnectedClient);

    SpawnOwnedPlayer(host.LocalClientId);
    SpawnOwnedPlayer(client.LocalClientId);

    await RunDeterministicInputSequence();

    Assert.Greater(clientMetrics.InputPacketsSent, 0);
    Assert.Greater(serverMetrics.InputPacketsReceived, 0);
    Assert.Greater(serverMetrics.SnapshotsSent, 0);
    Assert.Greater(clientMetrics.SnapshotsReceived, 0);
    Assert.IsTrue(clientMetrics.NetworkSimulatorActive);
}
```

这段代码的重要点不是 API 名称，而是证据链：连接、所有权、输入上行、权威执行、快照下行必须同时成立。

### 测试方法

同一输入序列分别运行 0 ms 和 100 ms 延迟。除了模拟器报告 Active，还应看到 RTT、回滚次数或快照到达间隔发生合理变化。如果所有网络指标完全不变，模拟参数可能没有进入实际 Pipeline。

## 4. 输入已经净化，但权威模拟仍使用原始值

### 发生条件

服务器接收不可信 Client 输入时，调用了校验函数，却在校验后把原始变量写入 Buffer。

### 错误代码

```csharp
bool PushInput(InputCommand input)
{
    if (!TrySanitize(input, out InputCommand sanitized))
        return false;

    inputBuffer.Store(input.Tick, input); // 错：仍保存 input
    return true;
}
```

`TrySanitize` 的返回值只说明数据可以被修正。`sanitized` 才是修正结果。上面的代码虽然执行了校验，却把校验结果丢掉了。

例如 Client 发送：

```text
Move    = (3, 4)，长度为 5
Aim     = (12, 0)，未归一化
Buttons = 255，包含未定义位
```

如果模拟层直接使用原始 Move，它可能得到 5 倍移动意图；未定义按钮位也可能在未来枚举扩展后意外变成有效能力。

### 推荐实现

```csharp
static bool TrySanitize(InputCommand raw, out InputCommand clean)
{
    clean = raw;

    if (!IsFinite(raw.Move) || !IsFinite(raw.Aim))
        return false;

    clean.Move = Vector2.ClampMagnitude(raw.Move, 1f);
    clean.Aim = raw.Aim.sqrMagnitude > 0.0001f
        ? raw.Aim.normalized
        : Vector2.zero;

    const InputButtons allowed = InputButtons.Aim | InputButtons.Sprint;
    clean.Buttons &= allowed;
    return true;
}

bool PushInput(InputCommand raw)
{
    if (!TrySanitize(raw, out InputCommand clean))
        return false;

    inputBuffer.Store(clean.Tick, clean); // 后续只有 clean
    return true;
}
```

推荐再缩小变量作用域，避免后续误用 `raw`：

```csharp
if (!TryReadAndSanitize(reader, out InputCommand input))
    return;

StoreTrustedInput(input);
```

进入 `StoreTrustedInput` 的变量在类型语义上已经是可信输入。

### 测试方法

```csharp
[Test]
public void ServerSimulatesSanitizedInput()
{
    InputCommand raw = new()
    {
        Tick = 10,
        Move = new Vector2(3, 4),
        Aim = new Vector2(12, 0),
        Buttons = (InputButtons)255,
    };

    server.PushInput(raw);
    InputCommand used = server.ResolveNextInput();

    Assert.AreEqual(1f, used.Move.magnitude, 0.0001f);
    Assert.AreEqual(Vector2.right, used.Aim);
    Assert.AreEqual(InputButtons.Aim | InputButtons.Sprint, used.Buttons);
}
```

测试必须检查“最终被模拟的值”，只断言 `TrySanitize` 自身返回正确还不够。

## 5. Server 只接受 Exact Tick，持续延迟会让输入永久过期

### 发生条件

Client 和 Server 都以相同频率推进 Tick，Server 只在 `input.Tick == nextServerTick` 时使用输入，已处理 Tick 一律丢弃。

### 错误代码

```csharp
void Receive(InputCommand input)
{
    if (input.Tick <= lastProcessedTick)
        return;

    futureInputs[input.Tick] = input;
}

InputCommand ResolveNext()
{
    uint next = lastProcessedTick + 1;
    return futureInputs.TryGetValue(next, out InputCommand exact)
        ? exact
        : InputCommand.Neutral(next);
}
```

假设双方是 30 Hz，单向网络延迟相当于 3 Tick：

```text
Client 生成 Tick 100
经过网络 3 Tick 后抵达
此时 Server 已处理到 Tick 102
Tick 100 被判定为过期

下一次 Client 生成 101
抵达时 Server 已处理到 103
Tick 101 仍然过期
```

双方频率相同意味着这个差值会稳定存在，不会自动追上。链路仍在收包，但 Server 实际长期使用 Neutral。

### 可选解决方案

#### 方案 A：Client 发送未来输入

```csharp
uint estimatedServerTick = clock.EstimateServerTick();
uint leadTicks = clock.EstimatedOneWayDelayTicks + safetyMargin;
command.Tick = estimatedServerTick + leadTicks;
```

优点是 Server 仍能执行 Exact；缺点是需要可靠的时钟估计，领先过多会增加输入延迟和安全风险。

#### 方案 B：Server 延迟模拟，建立输入缓冲

```csharp
uint simulationTick = networkTick - inputBufferDelayTicks;
Simulate(simulationTick, inputs[simulationTick]);
```

优点是时间语义清晰；缺点是服务器游戏逻辑整体落后真实时间，需要系统级设计。

#### 方案 C：受限迟到输入重定时

```csharp
bool TryAcceptLate(InputCommand input)
{
    uint lateBy = TickDistance(input.Tick, lastProcessedTick);

    if (lateBy > maxRetimingTicks)
        return false;

    if (hasLatestClientTick && !TickMath.IsNewer(input.Tick, latestClientTick))
        return false;

    pendingLate = input;          // 暂时保留原 Tick
    latestClientTick = input.Tick;
    hasPendingLate = true;
    return true;
}
```

重定时适合动作输入和当前意图同步，但不适合必须在原始时间点结算的事件，例如命中判定、交易和技能冷却完成。这些事件需要 Lag Compensation 或权威事件协议。

### 测试方法

让 Client 与 Server 同频推进，在测试中固定延迟 3 Tick，连续发送 300 Tick 移动输入。验证 Server 的有效输入比例不能随着时间下降到接近 0，并分别统计 Exact、Retimed、Reuse、Neutral，而不是只统计收包数。

## 6. 输入冗余能抗丢包，但不能替代延迟策略

### 发生条件

每个输入包携带当前 Tick 和前两个 Tick，希望同时解决丢包与延迟。

### 常见代码

```csharp
packet.Commands = new[]
{
    history[currentTick - 2],
    history[currentTick - 1],
    history[currentTick],
};

SendUnreliableSequenced(packet);
```

如果 Tick 100 的包丢失，而 Tick 101 到达时 Server 还没模拟 100，那么历史冗余可以补回 100。这是冗余的正确用途。

如果单向延迟已经是 4 Tick，Tick 100、99、98 抵达时 Server 可能已经处理到 103。三份输入全部过期。把冗余增加到 10 份只会携带更多过期数据。

### 正确组合

```csharp
foreach (InputCommand command in packet.CommandsOldToNew)
{
    if (command.Tick == nextServerTick)
        exactBuffer.Store(command);
    else if (TickMath.IsNewer(command.Tick, lastProcessedTick))
        futureBuffer.Store(command);
    else
        TryAcceptNewestLate(command);
}
```

这里有三种不同职责：

- 冗余：让丢失的旧包有机会再次出现；
- Future Buffer：保存尚未执行的输入；
- Late Strategy：处理已经错过原 Tick 的最新意图。

### 测试方法

必须把网络条件拆开测试：

- 0 延迟、10% 随机丢包：验证冗余；
- 100 ms 延迟、0 丢包：验证时间策略；
- 100 ms 延迟、10% 丢包：验证二者组合。

如果只测试“延迟+丢包”一个档位，无法知道改善来自哪种机制。

## 7. 无条件重定时迟到输入会执行过期操作

### 发生条件

为修复持续迟到，Server 把每个旧输入都直接改成下一 Tick。

### 错误代码

```csharp
if (input.Tick <= lastProcessedTick)
{
    input.Tick = lastProcessedTick + 1;
    pending = input;
}
```

设玩家先按右，再按左：

```text
Tick 100：Right
Tick 101：Left
```

由于乱序，101 先到、100 后到。错误代码会先保存 Left，随后被更旧的 Right 覆盖。下一权威 Tick 执行 Right，角色产生方向回跳。

更严重的情况是一个 1 秒前的 Sprint 输入在网络恢复后突然生效。

### 推荐实现

```csharp
bool TryQueueLate(InputCommand clean)
{
    if (TickMath.IsNewer(clean.Tick, lastProcessedTick))
        return false; // 这不是迟到输入

    uint lateBy = TickMath.Distance(clean.Tick, lastProcessedTick);
    if (lateBy > maxLateTicks)
        return false;

    if (hasLatestClientTick &&
        !TickMath.IsNewer(clean.Tick, latestClientTick))
        return false; // 旧包或冗余不能覆盖新意图

    pendingLate = clean;
    pendingLateSourceTick = clean.Tick;
    latestClientTick = clean.Tick;
    hasPendingLate = true;
    return true;
}
```

注意 Pending 中暂时保存原始 Tick。只有实际消费时才映射：

```csharp
InputCommand ConsumeLate(uint nextServerTick)
{
    InputCommand result = pendingLate;
    result.Tick = nextServerTick;
    hasPendingLate = false;
    return result;
}
```

如果接收时就覆盖 Tick，将失去比较原始新旧顺序的依据。

### 测试方法

1. 先送 Tick 101，再送 Tick 100，最终必须执行 101 的意图；
2. 送入超出窗口的旧输入，必须拒绝；
3. 同一包按旧到新处理，Pending 最终必须是最新 Tick；
4. 消费一次后 Pending 必须清空，不能重复执行。

## 8. Exact、Retimed、Hold 和 Neutral 没有明确优先级

### 发生条件

Server 在同一权威 Tick 前同时持有 Exact 输入、迟到输入和上一帧输入，但代码用多个互不排他的 `if` 处理。

### 错误代码

```csharp
InputCommand result = previous;

if (hasExact)
    result = exact;

if (hasPendingLate)
    result = pendingLate; // 覆盖了更新且时间更准确的 Exact

if (missingCount > maxHold)
    result = Neutral();   // 甚至可能再次覆盖
```

这种代码的行为依赖语句顺序，新增一个条件就可能悄悄改变协议语义。

### 推荐实现

```csharp
ResolvedInput ResolveNext(uint nextTick)
{
    if (exactBuffer.TryTake(nextTick, out InputCommand exact))
    {
        DropPendingLateIfNotNewerThan(exact.Tick);
        missingStreak = 0;
        return new(exact, InputSource.Exact);
    }

    if (hasPendingLate)
    {
        InputCommand late = ConsumeLate(nextTick);
        missingStreak = 0;
        return new(late, InputSource.RetimedLate);
    }

    missingStreak++;
    if (hasPrevious && missingStreak <= maxHoldTicks)
        return new(previous.WithTick(nextTick), InputSource.ReusedPrevious);

    return new(InputCommand.Neutral(nextTick), InputSource.Neutral);
}
```

这里用互斥的提前返回把协议优先级写进控制流：

```text
Exact > RetimedLate > ReusedPrevious > Neutral
```

每个返回值携带 `InputSource`，便于指标和日志记录。不要在返回后再从输入内容猜测来源，因为“真正的 Neutral”和“玩家主动发送中立输入”在数值上可能相同。

### 测试方法

为四种来源构造组合测试，尤其要验证：

- Exact 与 Pending Late 同时存在时选择 Exact；
- Pending Late 消费后下一 Tick 不会再次使用；
- Hold 超过上限后必定进入 Neutral；
- 新 Exact 到来后 Missing Streak 清零。

## 9. 无限沿用上一输入会形成网络卡键

### 发生条件

Server 缺输入时永久复用最后输入，同时 Client 在静止时完全停止发包。

### 错误代码

```csharp
InputCommand ResolveNext()
{
    return buffer.TryTake(nextTick, out InputCommand input)
        ? input
        : lastInput; // 永远沿用
}

void SendInput(InputCommand input)
{
    if (input.IsNeutral)
        return; // 静止永远不发

    Send(input);
}
```

如果玩家松开 W 的中立包丢失，Server 最后看到的仍是向前移动，角色会一直走。对 Sprint、蓄力和持续施法同样危险。

### 推荐实现

```csharp
InputCommand ResolveMissing(uint nextTick)
{
    missingStreak++;

    if (hasLastInput && missingStreak <= maxHoldTicks)
        return lastInput.WithTick(nextTick);

    return InputCommand.Neutral(nextTick);
}

bool ShouldSend(InputCommand current, uint tick)
{
    if (MeaningfullyChanged(current, lastSent))
        return true;

    if (!current.IsNeutral)
        return tick - lastSentTick >= activeSendInterval;

    return tick - lastSentTick >= idleHeartbeatInterval;
}
```

有限 Hold 负责掩盖很短的缺包，Neutral Heartbeat 负责最终纠正松键状态。

### 参数取舍

- `maxHoldTicks` 太大：松键响应延迟；
- 太小：轻微丢包就顿挫；
- Heartbeat 太慢：卡键恢复慢；
- 太快：空闲带宽增加。

### 测试方法

让最后一个“松键”包丢失，验证 Server 最迟在 `maxHoldTicks + heartbeat` 的可接受窗口内回到 Neutral，而不是永久移动。

## 10. 缺少身份、结构、数值和时间四层验证

### 发生条件

Server 收到 Client 自定义消息后，只按消息中的 `playerId` 路由，没有校验发送者是否拥有该玩家，也没有限制数组长度和 Tick 范围。

### 错误代码

```csharp
void OnInputMessage(ulong sender, Reader reader)
{
    ulong playerId = reader.ReadUInt64();
    int count = reader.ReadInt32();

    for (int i = 0; i < count; i++)
        players[playerId].Push(reader.Read<InputCommand>());
}
```

可能产生：

- Client 伪造其他玩家的 `playerId`；
- `count` 极大，导致异常分配或长循环；
- NaN 进入物理计算；
- 未来 Tick 挤占有限 Ring Buffer；
- Reader 数据不足时异常中断整个 Handler。

### 推荐实现

```csharp
void OnInputMessage(ulong sender, Reader reader)
{
    try
    {
        ulong playerId = reader.ReadUInt64();
        byte count = reader.ReadByte();

        if (count is < 1 or > MaxRedundancy)
            return;

        if (!endpoints.TryGetValue(playerId, out Endpoint endpoint))
            return;

        if (endpoint.OwnerClientId != sender)
            return;

        for (int i = 0; i < count; i++)
        {
            InputCommand raw = reader.Read<InputCommand>();
            if (!TrySanitize(raw, out InputCommand clean))
                continue;

            if (IsTooFarInFuture(clean.Tick, endpoint.LastProcessedTick))
                continue;

            endpoint.PushTrusted(clean);
        }
    }
    catch (ReadException exception)
    {
        LogMalformedPacket(sender, exception);
    }
}
```

四层边界分别是：

1. 身份：发送者只能操作自己的对象；
2. 结构：数量、长度和反序列化必须有上限；
3. 数值：有限数、范围和枚举位必须净化；
4. 时间：未来与迟到 Tick 都必须有窗口。

### 测试方法

使用错误 Owner、Count=0、Count 超限、NaN、Infinity、未知按钮位、超远未来 Tick、超窗旧 Tick 分别构造数据。每一种都要验证不会进入模拟，并有独立计数方便审计。

## 11. 在渲染帧中分配同步 Tick

### 发生条件

输入采样和固定模拟没有分层，`Update` 每执行一次就把网络 Tick 加一。

### 错误代码

```csharp
void Update()
{
    currentTick++;
    InputCommand input = ReadInput().WithTick(currentTick);
    Predict(input, Time.deltaTime);
    Send(input);
}
```

120 FPS 的 Client 每秒生成 120 Tick，30 FPS Client 每秒只生成 30 Tick，而 Server 可能固定运行 30 Tick。Tick 不再表示固定时长，历史回放和误差比较失去共同时间轴。

### 推荐实现

```csharp
InputCommand latestInput;

void Update()
{
    latestInput = ReadInputWithoutTick(); // 高频采样事实
}

void OnNetworkTick()
{
    currentTick++;
    InputCommand command = latestInput.WithTick(currentTick);
    PlayerState predicted = Simulate(command, fixedTickDelta);
    inputHistory.Store(command);
    stateHistory.Store(predicted);
    MaybeSend(command);
}
```

渲染帧只负责更新“此刻按了什么”，固定网络 Tick 决定“这个输入属于哪个模拟步骤”。

### 测试方法

分别锁定 30、60、120 FPS 运行相同真实时间，断言生成的同步 Tick 数基本一致，最终模拟距离也应在允许误差内一致。

## 12. Host 同时运行 Owner Prediction 和 Server Authority

### 发生条件

Listen Server/Host 同时具有 Client、Server 和本地 Owner 身份。代码分别判断 `IsOwner` 与 `IsServer`，导致两个分支都执行。

### 错误代码

```csharp
void OnTick()
{
    if (IsOwner)
        PredictLocalInput();

    if (IsServer)
        SimulateAuthority();
}
```

Host Owner 会在同一个 Tick 对同一个移动组件执行两次模拟。可能表现为移动加倍、体力消耗加倍、碰撞顺序异常，且 Dedicated Server 和 Remote Client 无法复现。

### 推荐实现

```csharp
enum SyncRole
{
    ServerAuthority,
    RemoteOwnerPrediction,
    RemoteObserver,
}

SyncRole ResolveRole()
{
    if (IsServer)
        return SyncRole.ServerAuthority;

    if (IsOwner)
        return SyncRole.RemoteOwnerPrediction;

    return SyncRole.RemoteObserver;
}

void OnTick()
{
    switch (role)
    {
        case SyncRole.ServerAuthority:
            SimulateAuthority();
            break;
        case SyncRole.RemoteOwnerPrediction:
            PredictLocalInput();
            break;
        case SyncRole.RemoteObserver:
            break;
    }
}
```

Server 仍要为所有玩家创建 Authority，但 Host 本地玩家不应在同一 Simulation 上额外预测一遍。

### 测试方法

分别运行 Dedicated Server、Host 和 Remote Client。记录每个 NetworkObject 每 Tick 的 `Simulate` 调用次数，任何对象在一个角色路径中都应恰好一次。

## 13. 网络服务未初始化就 Spawn 玩家

### 发生条件

NetworkManager 已经创建，但自定义消息 Handler、路由表或 Gameplay Network Runtime 尚未初始化，玩家 NetworkObject 就开始 Spawn。

### 错误代码

```csharp
void StartGame()
{
    networkManager.StartHost();
    SpawnPlayers();
    syncTransport.Initialize();
}
```

玩家的 `OnNetworkSpawn` 先执行，尝试注册同步端点时 Transport 为空。之后即使 Transport 初始化成功，已经 Spawn 的玩家也不会自动重跑注册逻辑。

### 推荐实现

```csharp
async Task StartGame()
{
    await networkManager.StartAndWaitForListening();

    await gameplayNetworkRuntime.InitializeAsync();

    isGameplayNetworkReady = true;

void OnPlayerNetworkSpawn(PlayerEndpoint player)
{

}
```

关键服务应该以显式状态机表示：

```text
Stopped -> TransportListening -> HandlersRegistered -> GameplayReady -> PlayersSpawned
```

不要用“某个 MonoBehaviour 的 Start 应该更早”作为生命周期保证。

## 14. 权威快照领先预测端，或预测历史已经缺失

### 发生条件

Owner 收到 Server Snapshot 时出现以下任一情况：

- `serverState.Tick > localCurrentTick`；
- Server Tick 虽不领先，但对应的预测状态已被 Ring Buffer 覆盖；
- 状态存在，但重放所需的某些输入已经缺失；
- Spawn、重连或 Warp 后双方历史起点不同。

### 两种常见错误处理

#### 错误 A：所有异常都直接 Hard Resync

```csharp
void Reconcile(PlayerState serverState)
{
    if (!stateHistory.TryGet(serverState.Tick, out PlayerState predicted))
    {
        Restore(serverState);
        inputHistory.Clear();
        stateHistory.Clear();
        currentTick = serverState.Tick;
        return;
    }

    // 普通回滚……
}
```

短暂领先 1 Tick、刚 Spawn 尚未建立历史等可恢复情况也会被当成硬错误，造成不必要的跳变。

#### 错误 B：所有 Ahead Snapshot 都忽略

```csharp
if (TickMath.IsNewer(serverState.Tick, currentTick))
    return;
```

如果根因是持续时钟漂移，之后的每个 Snapshot 都会领先并被忽略，Owner 永远失去权威校正。

### 推荐实现：先分类，再决定策略

```csharp
public enum ReconcileResult
{
    IgnoredOldSnapshot,
    Confirmed,
    RolledBack,
    DeferredSmallAhead,
    HardResyncServerAhead,
    HardResyncStateMissing,
    HardResyncInputMissing,
}

ReconcileResult Reconcile(PlayerState server)
{
    if (!TickMath.IsNewer(server.Tick, lastConfirmedTick))
        return ReconcileResult.IgnoredOldSnapshot;

    if (TickMath.IsNewer(server.Tick, currentTick))
    {
        uint ahead = TickMath.Distance(currentTick, server.Tick);

        if (ahead <= maxDeferredAheadTicks && CanAdvancePrediction(ahead))
        {
            QueueForNextLocalTicks(server);
            return ReconcileResult.DeferredSmallAhead;
        }

        HardRestore(server);
        return ReconcileResult.HardResyncServerAhead;
    }

    if (!stateHistory.TryGet(server.Tick, out PlayerState predicted))
    {
        HardRestore(server);
        return ReconcileResult.HardResyncStateMissing;
    }

    if (!NeedsCorrection(predicted, server))
    {
        lastConfirmedTick = server.Tick;
        return ReconcileResult.Confirmed;
    }

    if (!HasReplayInputs(server.Tick + 1, currentTick))
    {
        HardRestore(server);
        return ReconcileResult.HardResyncInputMissing;
    }

    Restore(server);
    ReplayInputs(server.Tick + 1, currentTick);
    lastConfirmedTick = server.Tick;
    return ReconcileResult.RolledBack;
}
```

`DeferredSmallAhead` 不是必需方案。也可以做受限 Catch-up Simulation，但必须有最大等待/追赶上限，否则会把持续漂移隐藏在队列中。

### 为什么要分类计数

“Hard Resync 发生了 10 次”无法指导修复：

- Server Ahead 需要检查时钟和 Tick 推进；
- State Missing 需要检查历史容量或快照延迟；
- Input Missing 需要检查输入历史写入和回收；
- Spawn/Reset 不一致需要检查生命周期。

### 测试方法

分别构造领先 1 Tick、领先 20 Tick、状态历史缺失、输入历史缺失和正常同 Tick 误差。断言每种情况返回独立枚举，并验证 Hard Restore 后 Tick、状态和历史起点一致。

## 15. 共用同一模拟函数，不代表物理完全确定

### 发生条件

Client Prediction 和 Server Authority 调用相同的 `Simulate` 函数，但底层包含 CharacterController、碰撞查询、动态障碍物或浮点运算。

### 错误认知对应的代码

```csharp
PlayerState Simulate(InputCommand input)
{
    characterController.Move(input.Move * speed * tickDelta);
    return CaptureState();
}

// Client 和 Server 调了同一个函数，所以认为永远相等：
Debug.Assert(clientState == serverState);
```

即便调用同一函数，两端也可能拥有不同的碰撞世界时刻：移动平台位置不同、动态刚体更新顺序不同、查询结果顺序不同。浮点误差也会经过速度积分逐步放大。

### 推荐实现

第一层是让纯游戏规则共享：

```csharp
PlayerState Simulate(PlayerState state, InputCommand input, float dt)
{
    MovementIntent intent = BuildIntent(state, input);
    CollisionResult collision = collisionWorld.Move(state, intent, dt);
    return ApplyCollisionResult(state, intent, collision, dt);
}
```

第二层是保存可完整恢复的状态：

```csharp
PlayerState CaptureState(uint tick)
{
    return new PlayerState
    {
        Tick = tick,
        Position = transform.position,
        Rotation = transform.rotation,
        Velocity = motor.Velocity,
        Stamina = stamina.Value,
        ControlState = stateMachine.CurrentId,
    };
}

void RestoreState(PlayerState state)
{
    transform.SetPositionAndRotation(state.Position, state.Rotation);
    motor.Velocity = state.Velocity;
    stamina.Value = state.Stamina;
    stateMachine.Force(state.ControlState);
}
```

第三层是用阈值而不是位级相等判断连续状态：

```csharp
bool NeedsCorrection(PlayerState predicted, PlayerState server)
{
    return Vector3.Distance(predicted.Position, server.Position) > positionThreshold
        || Quaternion.Angle(predicted.Rotation, server.Rotation) > rotationThreshold
        || Vector3.Distance(predicted.Velocity, server.Velocity) > velocityThreshold
        || Math.Abs(predicted.Stamina - server.Stamina) > staminaThreshold
        || predicted.ControlState != server.ControlState;
}
```

离散状态通常要求严格一致，连续值使用经过玩法验证的阈值。

### 测试方法

除了空旷平地，还要覆盖坡面、台阶、墙角、移动平台、动态障碍和多人碰撞。记录误差分布的 P50/P95/P99，再设置阈值；不能只凭手感选一个数。

## 16. 直接比较 `uint` Tick 会在回绕后反转新旧关系

### 发生条件

Tick 使用 `uint`，运行足够长后从 `4,294,967,295` 回到 `0`。

### 错误代码

```csharp
bool IsNewer(uint a, uint b) => a > b;
```

当 `b = 4,294,967,294`、`a = 1` 时，`a > b` 为 false，但从 Tick 序列看，1 明明是回绕后的新 Tick。

### 推荐实现

在任何一次比较跨度不超过半个 `uint` 范围的前提下，可以使用有符号差值：

```csharp
public static class TickMath
{
    public static bool IsNewer(uint candidate, uint reference)
    {
        return unchecked((int)(candidate - reference)) > 0;
    }

    public static bool IsNewerOrEqual(uint candidate, uint reference)
    {
        return candidate == reference || IsNewer(candidate, reference);
    }

    public static uint ForwardDistance(uint from, uint to)
    {
        return unchecked(to - from);
    }
}
```

环形历史也不能用普通排序：

```csharp
snapshots.Sort((x, y) =>
{
    if (x.Tick == y.Tick) return 0;
    return TickMath.IsNewer(x.Tick, y.Tick) ? 1 : -1;
});
```

更推荐按到达时验证单调性并写入固定 Ring Buffer，避免频繁排序。

### 使用约束

有符号差值方法假设任意需要比较的两个 Tick 距离小于 `2^31`。网络同步历史通常只有数百或数千 Tick，满足该条件；如果系统允许离线数年后再比较旧 Tick，就需要 epoch 或更宽时间戳。

### 测试方法

```csharp
[Test]
public void TickComparisonWorksAcrossWrap()
{
    uint before = uint.MaxValue - 1;
    uint after = 1;

    Assert.IsTrue(TickMath.IsNewer(after, before));
    Assert.AreEqual(3u, TickMath.ForwardDistance(before, after));
}
```

输入、Snapshot、LastConfirmed、插值顺序和未来边界都要复用同一个 TickMath，禁止每个模块自行实现比较。

## 17. Full 和 Delta 使用不同 Pipeline，却假设 Baseline 一定先到

### 发生条件

Server 定期发送 Full Snapshot，中间发送依赖该 Full 的 Delta。Full 使用可靠有序 Pipeline，Delta 使用不可靠有序 Pipeline。

### 错误协议

```csharp
if (shouldSendKeyframe)
{
    baseline = currentState;
    SendReliable(Full(baseline));
}
else
{
    SendUnreliable(Delta(baseline, currentState));
}
```

Client：

```csharp
void OnDelta(DeltaPacket packet)
{
    if (packet.BaselineTick != localBaseline.Tick)
        return;

    Apply(Decode(localBaseline, packet));
}
```

Reliable 只保证 Full 最终到达，不保证它比另一条 Unreliable Pipeline 上的 Delta 更早到达。Full 正在重传时，多个 Delta 可能先到并全部被丢弃。

另一个问题是 Server 的 `baseline` 通常按玩家全局保存，但不同 Client 的网络状态不同：Client A 已拥有新 Full，Client B 可能仍只有旧 Full。

### 推荐方案 A：每 Client Baseline Ack

Server 为每个接收者维护状态：

```csharp
sealed class ClientSnapshotState
{
    public uint AckedBaselineTick;
    public bool HasAckedBaseline;
    public PlayerState AckedBaseline;
}

void SendSnapshot(ulong clientId, PlayerState current)
{
    ClientSnapshotState link = links[clientId];

    if (!link.HasAckedBaseline || ShouldRefreshBaseline(link, current))
    {
        SendReliable(clientId, Full(current));
        pendingFullByClient[clientId] = current;
        return;
    }

    DeltaPacket delta = EncodeDelta(link.AckedBaseline, current);
    SendUnreliable(clientId, delta);
}

void OnBaselineAck(ulong clientId, uint baselineTick)
{
    if (!pendingFullByClient.TryGetValue(clientId, out PlayerState full))
        return;

    if (full.Tick != baselineTick)
        return;

    links[clientId].AckedBaseline = full;
    links[clientId].AckedBaselineTick = full.Tick;
    links[clientId].HasAckedBaseline = true;
}
```

Server 只有收到 Ack 后，才认为该 Client 可以解码对应 Delta。

### 推荐方案 B：同一有序 Pipeline

```csharp
SendUnreliableSequenced(FullOrDelta(packet));
```

Full 与 Delta 共用序列，可以避免跨 Pipeline 重排，但 Full 本身也可能丢失。Client 仍需要在缺 Baseline 时请求 Full，Server 也应周期性重发关键帧。

### 客户端缺 Baseline 时不要静默丢弃

```csharp
void OnDelta(DeltaPacket packet)
{
    if (!baselines.TryGetValue(packet.BaselineTick, out PlayerState baseline))
    {
        metrics.DeltaWithoutBaseline++;
        RequestFullSnapshot(packet.ObjectId);
        return;
    }

    Apply(Decode(baseline, packet));
}
```

请求必须节流，避免每个无 Baseline Delta 都发送一次请求。

### 测试方法

构造以下到达顺序：

```text
Delta(B=100) -> Delta(B=100) -> Full(100)
Full(100) -> Delta(B=100) -> Full(110) -> Delta(B=100)
Client A Ack(100)，Client B 未 Ack
```

验证协议不会错误解码，不会无限静默丢弃，并能在有限时间内恢复到可解码状态。

## 18. Observer 使用固定插值延迟，抖动超过窗口就停顿

### 发生条件

远端玩家只保存最近两个 Snapshot，并固定在最新状态后 100 ms 插值。网络抖动偶尔超过 100 ms，且系统没有外推。

### 错误或过度简化的代码

```csharp
void Update()
{
    float t = (Time.time - previous.ArrivalTime) /
              (latest.ArrivalTime - previous.ArrivalTime);
    transform.position = Vector3.Lerp(previous.Position, latest.Position, t);
}
```

这里混用了本地到达时间和 Server 状态时间。`t > 1` 后 Lerp 会到达 Latest，随后停住等待新包。到达间隔一抖动，远端玩家就表现为走走停停。

### 推荐实现：基于 Server Tick 的 Jitter Buffer

```csharp
sealed class SnapshotInterpolator
{
    readonly Deque<PlayerState> buffer = new();
    double renderTick;
    double interpolationDelayTicks = 3;

    public void Push(PlayerState state)
    {
        if (buffer.Count > 0 &&
            !TickMath.IsNewer(state.Tick, buffer.Back.Tick))
            return;

        buffer.PushBack(state);
        RecordArrivalInterval(state.Tick);
    }

    public bool TrySample(double latestServerTick, out PlayerState result)
    {
        double target = latestServerTick - interpolationDelayTicks;
        renderTick = Math.Min(renderTick + RenderDeltaTicks(), target);

        RemoveSnapshotsOlderThanRequiredPair(renderTick);

        if (!TryGetBracketingStates(renderTick, out PlayerState a, out PlayerState b))
            return TryLimitedExtrapolation(renderTick, out result);

        float t = InverseLerpTick(a.Tick, b.Tick, renderTick);
        result = Interpolate(a, b, t);
        return true;
    }
}
```

自适应延迟可以基于到达间隔统计：

```csharp
double desiredDelay = Clamp(
    Percentile(arrivalJitterTicks, 95) + safetyTicks,
    minDelayTicks,
    maxDelayTicks);

interpolationDelayTicks = SmoothDamp(
    interpolationDelayTicks,
    desiredDelay,
    adaptationSpeed);
```

延迟增加应较快，减少应较慢，避免缓冲目标来回摆动。

### 受限外推

```csharp
bool TryLimitedExtrapolation(double renderTick, out PlayerState state)
{
    PlayerState latest = buffer.Back;
    double aheadTicks = renderTick - latest.Tick;

    if (aheadTicks < 0 || aheadTicks > maxExtrapolationTicks)
    {
        state = latest;
        return false;
    }

    state = latest;
    state.Position += latest.Velocity * (float)(aheadTicks * tickDelta);
    return true;
}
```

外推必须限制时间、速度和最大位移；否则丢包时角色可能穿墙或偏离很远。

### 测试方法

给定一组可重复的快照到达时间，统计：

- Buffer 触底次数；
- 插值延迟 P50/P95；
- 每帧表现位移的 P95/Max；
- 外推次数和最大距离。

“视觉上还行”不能替代这些指标。

## 19. Warp 只修改 Transform，没有重置同步历史

### 发生条件

复活、换层、回城或管理员传送时，业务代码直接写位置，但预测、权威和插值仍保留传送前历史。

### 错误代码

```csharp
void Teleport(Vector3 position)
{
    transform.position = position;
}
```

下一帧可能发生：

- Owner 用旧输入从旧状态继续 Replay，把玩家拉回；
- Observer 在旧位置与新位置之间插值；
- Server 继续沿用传送前的移动输入；
- 新 Delta 仍引用传送前 Baseline；
- 速度未清零，传送后继续滑动。

### 推荐实现：原子式重置

```csharp
void ResetAfterWarp(Vector3 position, Quaternion rotation, uint resetTick)
{
    PlayerState reset = CaptureState(resetTick);
    reset.Position = position;
    reset.Rotation = rotation;
    reset.Velocity = Vector3.zero;

    simulation.Restore(reset);

    prediction.Reset(reset);
    authority.Reset(reset);
    interpolation.Reset(reset);

    latestLocalInput = InputCommand.Neutral(resetTick);
    inputHistory.Clear();
    stateHistory.Clear();

    hasSnapshotBaseline = false;
    deltaCountSinceFull = 0;
    snapshotSendBudget = 0;
}
```

重置必须在一个统一入口中完成。让复活、换层和传送各自清一部分状态，很容易遗漏新加入的缓存。

网络协议还应明确 Warp Snapshot 是可靠事件还是带 Teleport 标记的 Full Snapshot，不能依赖“位置差大于某阈值”永远正确猜测。

### 测试方法

在 Owner 正在移动、Server 正在 Hold、Observer Buffer 非空、Delta Baseline 有效的时刻触发 Warp。验证下一帧不会回拉、旧输入不会继续执行、Observer 不跨地图插值、第一份新快照可以独立还原。

## 20. 网络 TickRate 和模拟 TickRate 有两个真相来源

### 发生条件

NetworkManager 配置为 30 Hz，玩家同步配置被改成 60 Hz，代码只打印 Warning 后继续运行。

### 错误结构

```csharp
int networkTickRate = networkConfig.TickRate; // 30
int simulationTickRate = playerConfig.TickRate; // 60

void OnNetworkTick()
{
    Simulate(1f / simulationTickRate);
}
```

回调每秒执行 30 次，但每次只积分 `1/60` 秒，角色实际速度减半。与此同时：

- 心跳 Tick 换算错误；
- 插值延迟秒数与 Tick 数不一致；
- Snapshot Budget 产生不规则节奏；
- 历史容量代表的真实秒数改变。

### 推荐方案 A：单一配置派生

```csharp
void ApplyNetworkConfiguration(GameSyncConfig config)
{
    networkConfig.TickRate = config.TickRate;
    playerSimulation.TickDelta = 1f / config.TickRate;
    snapshotScheduler.Configure(config.TickRate, config.SnapshotRate);
    interpolation.Configure(config.TickRate, config.DelaySeconds);
}
```

### 推荐方案 B：启动时强校验

```csharp
void ValidateConfiguration()
{
    if (networkConfig.TickRate != playerConfig.TickRate)
        throw new InvalidOperationException(
            $"TickRate mismatch: network={networkConfig.TickRate}, " +
            $"player={playerConfig.TickRate}");
}
```

开发阶段应快速失败，而不是继续生成难以解释的移动误差。

### 非整除发送频率

30 Hz 模拟发送 20 Hz Snapshot 时，不应简单使用 `interval = 30 / 20 = 1`，否则会变成 30 Hz。应使用整数 Budget：

```csharp
snapshotBudget += snapshotRate;
if (snapshotBudget >= simulationTickRate)
{
    snapshotBudget -= simulationTickRate;
    SendSnapshot();
}
```

30 个模拟 Tick 内正好触发 20 次，且没有浮点累积漂移。

### 测试方法

运行固定 10 秒，验证模拟 Tick 数、输入包数和 Snapshot 数都落在预期范围；配置不一致时验证启动直接失败。

## 21. 指标没有区分“收到什么”和“最终执行什么”

### 发生条件

Server 只有 `receivedCount`、`outdatedCount`，Client 只有 `snapshotCount`。当问题发生时无法知道输入最终来自 Exact、重定时、沿用还是中立。

### 不足的指标代码

```csharp
receivedInputs++;

if (input.Tick <= lastProcessedTick)
    outdatedInputs++;
```

如果迟到输入后来被安全重定时，`outdatedInputs` 仍会增加。只看它会误判为失败；反过来，收包数很高也不能证明 Server 真正在执行玩家意图。

### 推荐指标分层

```csharp
struct InputMetrics
{
    // 接收层
    public long PacketsReceived;
    public long CommandsReceived;
    public long InvalidStructure;
    public long InvalidOwner;
    public long InvalidValue;
    public long TooFarFuture;
    public long ArrivedLate;

    // 接受层
    public long AcceptedExactBuffer;
    public long AcceptedRetimedLate;
    public long DuplicateOrOlder;

    // 执行层
    public long ExecutedExact;
    public long ExecutedRetimedLate;
    public long ExecutedReused;
    public long ExecutedNeutral;
}
```

每个权威 Tick 恰好增加一个执行层计数：

```csharp
ResolvedInput resolved = ResolveNext();
metrics.Increment(resolved.Source);
Simulate(resolved.Command);
```

报告比例时必须明确分母：

```csharp
double neutralRatio = metrics.ExecutedNeutral /
    (double)(metrics.ExecutedExact
           + metrics.ExecutedRetimedLate
           + metrics.ExecutedReused
           + metrics.ExecutedNeutral);
```

### 其他常见口径陷阱

- Payload 字节通常不含 UDP/Transport/协议头；
- 同机 Editor RTT 不等于真实公网 RTT；
- 平均帧耗时会隐藏尖峰，应记录 P95/P99/Max；
- Observer 位移为 0 既可能是缓冲耗尽，也可能是玩家主动静止；
- 测试退出后的 Socket 错误不应混入正式采样窗口。

### 测试方法

为每个指标制造唯一触发条件，确认它只增加预期计数。报告中同时保存原始计数、比例公式、采样时长和网络配置。

## 22. 两玩家测试通过，不代表多人规模性能安全

### 发生条件

每个玩家每个 Snapshot 都创建临时 Writer，并给每个 Client 单独发送；没有批处理、量化和 AOI。

### 容易扩大的代码

```csharp
foreach (Player player in players)
{
    foreach (Client client in clients)
    {
        using FastBufferWriter writer = new(512, Allocator.Temp);
        writer.Write(player.State);
        Send(client, writer);
    }
}
```

玩家数为 N、Client 数为 M 时，序列化和发送次数接近 N×M。2×2 看起来很轻，32×32 已经是 1024 条发送路径/快照周期。

### 推荐优化顺序

#### 1. 先做 AOI

```csharp
foreach (Client client in clients)
{
    IReadOnlyList<Player> visible = interest.QueryVisiblePlayers(client);
    SendBatch(client, visible);
}
```

不相关的玩家不应进入序列化阶段。

#### 2. 按 Client 批量序列化

```csharp
void SendBatch(Client client, IReadOnlyList<Player> players)
{
    PooledWriter writer = writerPool.Rent();
    writer.WriteVarUInt((uint)players.Count);

    foreach (Player player in players)
        WriteQuantizedSnapshot(writer, player.State);

    transport.Send(client.Id, writer);
    writerPool.Return(writer);
}
```

#### 3. 量化连续值

```csharp
ushort QuantizePosition(float value, float min, float max)
{
    float normalized = Mathf.InverseLerp(min, max, value);
    return (ushort)Mathf.RoundToInt(normalized * ushort.MaxValue);
}
```

量化范围必须与关卡空间和误差预算对应，越界时应回退到 Full/高精度格式，不能静默截断。

#### 4. 避免每包临时分配

Writer Pool 能减少托管和原生临时分配，但必须保证发送完成前缓冲不会被复用。具体生命周期取决于 Transport 是否立即复制数据。

### 测试方法

按 2、8、16、32 玩家阶梯测量：

- Server 主线程 P50/P95/P99；
- GC/帧和临时分配；
- 每秒消息数、应用层字节和实际网卡字节；
- 每 Client 可见玩家数量；
- Snapshot 构建次数与发送次数。

性能结论必须说明玩家数、接收者数和 AOI 密度。

## 23. 输入发送的“变化检测”遗漏了玩法字段

### 发生条件

Client 为节省带宽，只在输入明显变化时立即发送，但 `MeaningfullyChanged` 只比较 Move，没有比较 Aim、Sprint 或其他离散动作。

### 错误代码

```csharp
bool MeaningfullyChanged(InputCommand current, InputCommand previous)
{
    return Vector2.Distance(current.Move, previous.Move) > 0.1f;
}
```

玩家站着不动，只把瞄准方向从右转向左。Move 没变，代码不会立即发包；如果空闲 Heartbeat 是 1 秒，Server 最长 1 秒后才知道朝向变化。对于射击、格挡方向或锁定目标，这是明显操作延迟。

### 推荐实现

```csharp
bool MeaningfullyChanged(InputCommand current, InputCommand previous)
{
    bool moveStateChanged = current.Move.sqrMagnitude > 0.0001f
                         != previous.Move.sqrMagnitude > 0.0001f;

    bool moveDirectionChanged =
        Vector2.Distance(current.Move, previous.Move) > moveThreshold;

    bool aimStateChanged = current.Aim.sqrMagnitude > 0.0001f
                        != previous.Aim.sqrMagnitude > 0.0001f;

    bool aimDirectionChanged =
        Vector2.Distance(current.Aim, previous.Aim) > aimThreshold;

    bool buttonsChanged = current.Buttons != previous.Buttons;

    return moveStateChanged
        || moveDirectionChanged
        || aimStateChanged
        || aimDirectionChanged
        || buttonsChanged;
}
```

如果输入包含一次性事件，例如 JumpPressed，不应只依赖“当前状态与上一状态不同”。事件最好有独立序号或边沿位：

```csharp
public struct InputCommand
{
    public uint Tick;
    public Vector2 Move;
    public Vector2 Aim;
    public InputButtons HeldButtons;
    public InputButtons PressedThisTick;
    public ushort ActionSequence;
}
```

持续状态可以被后续输入覆盖，一次性事件必须能去重且不能被合并丢失。

### 测试方法

Move 保持不变，分别只改变 Aim、Sprint、AimHeld 和一次性动作序号，验证都能触发立即发送；微小摇杆噪声则不应突破阈值导致包量暴涨。

## 24. 双进程/双 Editor 测试存在启动竞态

### 发生条件

Host 和 Client 由两个进程自动启动。Client 在 Host 尚未 Listening 时尝试连接，或者读到上一次测试遗留的 ready 文件。

### 错误代码

```csharp
// Host 进程
EnterPlayMode();
StartHost();

// Client 进程，几乎同时执行
EnterPlayMode();
StartClient();
```

Editor 的脚本导入、域重载和场景加载耗时不稳定。偶尔成功不能证明流程正确。

另一个常见错误：

```csharp
if (networkManager.IsClient)
    RunClientCase();
else
    RunHostCase();
```

Host 同时满足 `IsClient == true` 和 `IsServer == true`，会误走 Client 分支。

### 推荐实现：带本轮令牌的握手

```csharp
record TestConfig(string RunId, int Port, NetworkProfile Profile);

async Task RunHost(TestConfig config)
{
    await StartHost(config.Port);
    await WaitUntil(() => networkManager.IsListening);

    WriteReadyAtomically(new ReadyFile
    {
        RunId = config.RunId,
        Port = config.Port,
    });

    await WaitForClientConnection();
    await RunMeasurementWindow();
}

async Task RunClient(TestConfig config)
{
    ReadyFile ready = await WaitForReadyFile(
        file => file.RunId == config.RunId && file.Port == config.Port,
        timeout: TimeSpan.FromSeconds(60));

    await StartClient(ready.Port);
    await WaitUntil(() => networkManager.IsConnectedClient);
    await NextFrame();
    await RunMeasurementWindow();
}
```

`RunId` 可以是 GUID 或配置文件的内容哈希。写 ready 文件时应采用临时文件加原子替换，避免 Client 读到半个 JSON。

身份分支应显式判断：

```csharp
if (networkManager.IsHost)
    RunHostRole();
else if (networkManager.IsClient)
    RunRemoteClientRole();
else if (networkManager.IsServer)
    RunDedicatedServerRole();
```

### 为什么连接后还要等一帧

很多网络框架在“连接完成事件”触发的同一帧还在更新 Spawn 表、场景事件或消息 Handler。把测试玩家 Spawn 放到下一帧能避免生命周期回调互相嵌套。正式游戏可以使用更明确的 `GameplayReady` 协议替代“下一帧”。

### 测试方法

连续自动运行 20 次，并随机给 Host 启动增加 0～5 秒延迟。每一轮都必须只接受当前 RunId，不能依赖旧 ready 文件，也不能出现 Client 偶发首连失败。

## 25. 克隆工程的旧缓存会制造与源码无关的编译错误

### 发生条件

主工程已经删除某个 Package 或程序集，Clone/副本工程的 Library 仍保存旧 Assembly Definition、编译产物或 Package 缓存。

### 错误处理方式

看到 Clone 报“找不到旧 Package 类型”后，直接把旧 Package 重新加回主工程：

```text
Clone 报错 -> 修改正式 manifest -> 恢复已经删除的依赖
```

这会让测试环境的陈旧状态反向污染正式依赖。

### 推荐诊断代码

测试启动器可以先比较决定编译图的文件哈希：

```csharp
string ComputeDependencyFingerprint(string projectPath)
{
    string manifest = ReadAllText(projectPath + "/Packages/manifest.json");
    string lockFile = ReadAllText(projectPath + "/Packages/packages-lock.json");
    string asmdefs = HashFiles(projectPath + "/Assets", "*.asmdef");
    return Sha256(manifest + lockFile + asmdefs);
}

void ValidateClone(string source, string clone)
{
    string expected = ComputeDependencyFingerprint(source);
    string actual = ReadSavedFingerprint(clone);

    if (expected != actual)
        throw new CloneRequiresReimportException(expected, actual);
}
```

自动化层收到该异常后，可以停止 Clone、删除明确的 Clone Library 并重新导入。目标必须解析成指定 Clone 的绝对路径，不能对工作区根目录做递归删除。

### 判断顺序

1. 主工程 manifest 是否仍引用该包；
2. packages-lock 是否一致；
3. 包目录是否实际存在；
4. Clone 的 manifest/lock 是否同步；
5. 清理 Clone Library 后是否仍复现；
6. 最后才判断为源码或依赖声明问题。

### 测试方法

修改一次包清单后启动 Clone，验证指纹不一致能在进入 Play 前被明确报告，而不是在编译阶段出现大量无关类型错误。

## 26. 测试拆除阶段的 Socket 错误污染稳定性结论

### 发生条件

双端测试完成后，一端立即关闭 Transport，另一端仍在网络轮询或发送最后一个包，于是记录 Connection Reset、Socket receive failed 等错误。

### 错误代码

```csharp
void FinishTest()
{
    networkManager.Shutdown();
    WriteResult(metrics); // 采样边界在关闭之后
}
```

错误日志与正式测量混在一起，报告可能把正常退出误判为运行期断线。

### 推荐实现：明确采样状态机

```csharp
enum TestPhase
{
    Connecting,
    Warmup,
    Measuring,
    ResultWritten,
    GracefulShutdown,
    Finished,
}

async Task FinishTest()
{
    phase = TestPhase.ResultWritten;
    MetricsSnapshot final = metrics.Freeze();
    await WriteResultAtomically(final);

    SendTestFinishedControlMessage();
    await WaitForPeerFinishedOrTimeout(TimeSpan.FromSeconds(1));

    phase = TestPhase.GracefulShutdown;
    networkManager.Shutdown();
    phase = TestPhase.Finished;
}

void OnNetworkError(NetworkError error)
{
    if (phase <= TestPhase.Measuring)
        metrics.RuntimeNetworkErrors++;
    else
        metrics.TeardownNetworkErrors++;
}
```

结果必须先冻结再关闭网络。拆除错误仍应保留在单独字段中，不能简单吞掉，因为过多拆除错误也可能说明关闭协议有问题。

### 测试方法

分别让 Host 先关、Client 先关、双方协商后关。验证正式测量错误计数不受退出顺序影响，且拆除错误有独立记录。

## 27. 通用失败文案会把正确数据指向错误根因

### 发生条件

测试通过条件由多个布尔表达式组成，失败时统一输出“缺少输入、快照或玩家链路”。实际失败可能只是 Hard Resync 超限。

### 错误代码

```csharp
bool passed = actorCount >= 2
           && inputPackets > 0
           && snapshots > 0
           && hardResync == 0;

string failure = passed
    ? ""
    : "缺少输入、快照或双玩家链路证据";
```

即使 Actor、输入和快照全部正常，只因 `hardResync == 2` 失败，文案仍指向不存在的链路问题。

### 推荐实现

```csharp
List<string> failures = new();

Require(actorCount >= 2,
    $"ActorCount expected>=2 actual={actorCount}", failures);

Require(inputPackets > 0,
    $"InputPackets expected>0 actual={inputPackets}", failures);

Require(ownerSnapshots > 0,
    $"OwnerSnapshots expected>0 actual={ownerSnapshots}", failures);

Require(observerSnapshots > 0,
    $"ObserverSnapshots expected>0 actual={observerSnapshots}", failures);

Require(hardResync == 0,
    $"HardResync expected=0 actual={hardResync}", failures);

result.Passed = failures.Count == 0;
result.Failures = failures;
```

最好输出结构化断言：

```json
{
  "name": "HardResync",
  "expected": "0",
  "actual": "2",
  "passed": false
}
```

结构化数据便于 CI 聚合，不需要解析自然语言。

### 测试方法

让每个通过条件单独失败一次，断言 Failure 列表只包含对应原因；多个条件同时失败时应全部报告，而不是只显示第一个。

## 28. 测试程序集跨越热更新/裁剪边界，Editor 能跑但 Player 构建失败

### 发生条件

Unity Editor 中的测试程序集直接引用热更新 Gameplay 程序集。构建 IL2CPP/HybridCLR Player 时，热更新程序集不以普通 Player Assembly 形式参与链接，Linker 无法解析测试程序集引用。

### 容易出问题的程序集关系

```text
NetworkLoadTests.dll
        |
        v
HotUpdate.Gameplay.dll

Editor：两个 DLL 都在 ScriptAssemblies 中，可以运行
Player：Gameplay 由热更新加载，Linker 阶段找不到普通引用
```

代码层常见表现：

```csharp
// 编进 Player 的测试程序集直接引用热更新类型
using HotUpdate.Gameplay.Player.Sync;

public class StandaloneSyncLoadTest : MonoBehaviour
{
    PlayerSyncController controller;
}
```

### 推荐方案 A：测试代码也进入热更新加载路径

```text
Bootstrap Player
    -> 初始化 HybridCLR
    -> 加载 HotUpdate.Gameplay
    -> 加载 HotUpdate.NetworkTests
    -> 通过约定入口启动测试
```

测试程序集与被测程序集使用相同加载机制。

### 推荐方案 B：使用不引用热更新类型的桥接协议

Player 主程序集只定义稳定接口和数据：

```csharp
public interface INetworkTestEntry
{
    Task<TestResult> RunAsync(TestConfig config);
}
```

热更新程序集实现接口：

```csharp
public sealed class PlayerSyncTestEntry : INetworkTestEntry
{
    public Task<TestResult> RunAsync(TestConfig config)
    {
        // 这里可以访问热更新 Gameplay 类型
    }
}
```

Bootstrap 通过反射或注册表获取实现，主 Player 不直接静态引用热更新 Gameplay。

### 推荐方案 C：将纯算法抽到稳定共享程序集

TickMath、RingBuffer、序列化格式和纯状态模拟可以放到 Player 与热更新都能引用的共享 Runtime Assembly。场景、MonoBehaviour 和业务系统仍留在热更新层。

### 测试方法

Editor Test、Development Player Build、目标平台启动应是三个独立门槛。不能因为 Editor 双进程实测通过，就默认 IL2CPP/HybridCLR Player 同样可构建。

## 29. 一套可复用的输入权威实现

下面把前述输入问题组合成一份完整骨架，便于独立理解各个保护之间的关系。

```csharp
public sealed class ServerInputResolver
{
    readonly TickRingBuffer<InputCommand> futureInputs;
    readonly int maxFutureTicks;
    readonly int maxLateTicks;
    readonly int maxHoldTicks;

    uint lastProcessedTick;
    uint latestObservedClientTick;
    bool hasLatestObservedClientTick;

    InputCommand pendingLate;
    bool hasPendingLate;

    InputCommand previous;
    bool hasPrevious;
    int missingStreak;

    public bool PushUntrusted(InputCommand raw)
    {
        if (!TrySanitize(raw, out InputCommand input))
            return false;

        if (!TickMath.IsNewer(input.Tick, lastProcessedTick))
            return TryPushLate(input);

        uint ahead = TickMath.ForwardDistance(lastProcessedTick, input.Tick);
        if (ahead > maxFutureTicks)
            return false;

        if (futureInputs.Contains(input.Tick))
            return false;

        if (hasLatestObservedClientTick &&
            !TickMath.IsNewer(input.Tick, latestObservedClientTick))
            return false;

        futureInputs.Store(input.Tick, input);
        latestObservedClientTick = input.Tick;
        hasLatestObservedClientTick = true;
        return true;
    }

    bool TryPushLate(InputCommand input)
    {
        uint lateBy = TickMath.ForwardDistance(input.Tick, lastProcessedTick);

        if (maxLateTicks <= 0 || lateBy > maxLateTicks)
            return false;

        if (hasLatestObservedClientTick &&
            !TickMath.IsNewer(input.Tick, latestObservedClientTick))
            return false;

        pendingLate = input;
        hasPendingLate = true;
        latestObservedClientTick = input.Tick;
        hasLatestObservedClientTick = true;
        return true;
    }

    public ResolvedInput ResolveNext()
    {
        uint next = unchecked(lastProcessedTick + 1);

        if (futureInputs.TryTake(next, out InputCommand exact))
            return Commit(exact, InputSource.Exact, resetMissing: true);

        if (hasPendingLate)
        {
            InputCommand late = pendingLate.WithTick(next);
            hasPendingLate = false;
            return Commit(late, InputSource.RetimedLate, resetMissing: true);
        }

        missingStreak++;
        if (hasPrevious && missingStreak <= maxHoldTicks)
        {
            InputCommand reused = previous.WithTick(next);
            return Commit(reused, InputSource.ReusedPrevious, resetMissing: false);
        }

        InputCommand neutral = InputCommand.Neutral(next);
        return Commit(neutral, InputSource.Neutral, resetMissing: false);
    }

    ResolvedInput Commit(
        InputCommand input,
        InputSource source,
        bool resetMissing)
    {
        if (resetMissing)
            missingStreak = 0;

        lastProcessedTick = input.Tick;
        previous = input;
        hasPrevious = true;
        return new ResolvedInput(input, source);
    }
}
```

这份骨架仍不是所有游戏的最终答案。它适合“最新移动意图”类输入。攻击命中、拾取、交易等不可简单重定时的命令，应走独立的权威事件协议。

## 30. 一套可复用的预测回滚骨架

```csharp
public sealed class ClientPredictor
{
    readonly TickRingBuffer<InputCommand> inputHistory;
    readonly TickRingBuffer<PlayerState> stateHistory;

    uint currentTick;
    uint lastConfirmedTick;

    public PlayerState Predict(InputCommand sampledInput)
    {
        currentTick = unchecked(currentTick + 1);
        InputCommand input = sampledInput.WithTick(currentTick);

        inputHistory.Store(currentTick, input);
        PlayerState state = simulation.Simulate(input, fixedDelta);
        stateHistory.Store(currentTick, state);
        return state;
    }

    public ReconcileResult Reconcile(PlayerState server)
    {
        if (!TickMath.IsNewer(server.Tick, lastConfirmedTick))
            return ReconcileResult.IgnoredOldSnapshot;

        if (TickMath.IsNewer(server.Tick, currentTick))
            return HardRestore(server, ReconcileResult.HardResyncServerAhead);

        if (!stateHistory.TryGet(server.Tick, out PlayerState predicted))
            return HardRestore(server, ReconcileResult.HardResyncStateMissing);

        if (!NeedsCorrection(predicted, server))
        {
            lastConfirmedTick = server.Tick;
            return ReconcileResult.Confirmed;
        }

        simulation.Restore(server);

        uint tick = unchecked(server.Tick + 1);
        while (TickMath.IsNewerOrEqual(currentTick, tick))
        {
            if (!inputHistory.TryGet(tick, out InputCommand input))
                return HardRestore(server, ReconcileResult.HardResyncInputMissing);

            PlayerState replayed = simulation.Simulate(input, fixedDelta);
            stateHistory.Store(tick, replayed);
            tick = unchecked(tick + 1);
        }

        lastConfirmedTick = server.Tick;
        return ReconcileResult.RolledBack;
    }
}
```

生产实现还需要限制最大 Replay Tick 数，避免单帧重放过多造成卡顿。可以把超长重放分帧或直接 Hard Resync，但必须记录原因。

## 35. 最终经验

玩家同步最难排查的情况通常不是完全断线，而是“包一直在收发，但各端对 Tick、所有权、Baseline 或历史生命周期的理解已经不同”。这种错误在本地零延迟下可能几乎不可见，在持续 RTT、跨 Pipeline 重排、Host 身份重叠或 Warp 时才会放大。

可靠的同步实现应同时具备六个边界：

```text
身份边界：谁能操作哪个对象
结构边界：消息数量与长度是否受限
数值边界：输入和状态是否合法
时间边界：Tick 如何对齐、迟到和回绕如何处理
历史边界：预测、回滚、Baseline、Warp 何时失效
观测边界：系统最终执行了什么，而不仅是收到了什么
```

只有把这些边界写进代码、指标和自动化弱网测试，才能把“当前场景里看起来能动”提升为“同步协议在已声明条件下可验证地工作”。

## 36. 问题：把每一层模拟都写成 MonoBehaviour 会让“组件能运行”替代“依赖一定正确”

### 适用范围

这个问题不限于某套同步脚本。只要一个状态模拟由多个 Unity `MonoBehaviour`（必须挂在 GameObject 上、由 Unity 管理生命周期的脚本组件）串联，并且这些层本质上只是算法和运行状态，就会遇到相同风险。常见于玩家移动、技能状态机、车辆模拟、预测回滚和 AI 决策链。

### 容易出现问题的写法

下面的简化代码把 Motor（底层运动器）、Locomotion（移动玩法控制器）和 Simulation（统一模拟入口）全部做成组件：

```csharp
public sealed class Motor : MonoBehaviour
{
    [SerializeField] private MovementConfig _config;
}

public sealed class Locomotion : MonoBehaviour
{
    private Motor _motor;

    private void Awake()
    {
        _motor = GetComponent<Motor>();
    }
}

public sealed class Simulation : MonoBehaviour
{
    private Locomotion _locomotion;

    private void Awake()
    {
        _locomotion = GetComponent<Locomotion>();
    }
}
```

这段代码表面上利用 `GetComponent<T>`（从当前 GameObject 查找指定组件的方法）自动连线，实际把正确性转移给了场景和 Prefab（预制体）作者：

1. 少挂任意一层，错误要到 `Awake`（Unity 对象初始化回调）甚至第一次 Tick（固定模拟步）才暴露；
2. 重复挂载一层时，不同调用者可能取得不同实例，状态历史与实际移动对象分裂；
3. 每层都可以拥有自己的序列化配置，复制 Prefab 或场景覆盖参数后容易出现“看起来相同，实际配置不同”；
4. `Awake`、`OnEnable`、`Start`（Unity 生命周期回调）的先后关系变成隐式依赖。即使当前恰好能跑，脚本执行顺序、对象激活方式或组件新增都可能改变行为；
5. 单元测试必须创建 GameObject、添加全部组件并触发 Unity 生命周期，无法直接构造一个隔离的算法对象；
6. 预测端和服务器端如果各自通过组件查找拼装，很难证明二者消费的是同一套模拟实现与配置。

`RequireComponent`（声明脚本依赖另一个组件的 Unity 特性）只能缓解“编辑器中新添加组件时漏挂”的一部分问题。它不能表达多层对象的唯一所有权，不能阻止已有 Prefab 中的重复组件，也不能保证配置与运行状态的恢复顺序。

### 为什么同步系统尤其容易受影响

普通本地移动只要最终位置看起来正确即可；预测同步还必须在同一个 Tick 上捕获和恢复完整状态。假设回滚只恢复 Transform（位置和旋转），却没有恢复 Motor 的速度、Locomotion 的冲刺状态和体力：

```csharp
transform.SetPositionAndRotation(serverPosition, serverRotation);
// velocity、controlState、stamina 仍是未来状态
ReplayInputs();
```

Replay（重演历史输入）会从一个混合了“过去姿态”和“未来内部状态”的起点开始。平地匀速时可能暂时看不出，以下情况会快速放大：

- 冲刺刚开始或刚结束；
- 制动、转向和重力正在累积；
- 体力刚好跨过可冲刺阈值；
- 角色接触坡面、台阶或动态碰撞体；
- 网络抖动导致连续多次 Rollback（回滚）。

结果通常不是立刻断线，而是位置反复被校正、速度抖动、体力跳变，最终在历史不可用时触发 Hard Resync（硬同步）。

### 更稳妥的结构：组合根 + 纯 C# 持有链

保留一个 Composition Root（组合根，即负责创建并连接对象的最上层入口）作为 Unity/网络生命周期边界，其余算法层用构造函数声明必需依赖：

```csharp
public interface ICharacterBody
{
    Vector3 Position { get; }
    Quaternion Rotation { get; }
    void Move(Vector3 displacement);
    void SetPose(Vector3 position, Quaternion rotation);
}

public sealed class Motor
{
    private readonly ICharacterBody _body;
    private readonly MovementConfig _config;

    public Motor(ICharacterBody body, MovementConfig config)
    {
        _body = body ?? throw new ArgumentNullException(nameof(body));
        _config = config;
    }
}

public sealed class Locomotion
{
    private readonly Motor _motor;

    public Locomotion(Motor motor)
    {
        _motor = motor ?? throw new ArgumentNullException(nameof(motor));
    }
}

public sealed class Simulation
{
    private readonly Locomotion _locomotion;

    public Simulation(Locomotion locomotion)
    {
        _locomotion = locomotion ?? throw new ArgumentNullException(nameof(locomotion));
    }
}

public sealed class SyncRoot : NetworkBehaviour
{
    private Simulation _simulation;

    private void Awake()
    {
        ICharacterBody body = new CharacterControllerBody(transform,
            GetComponent<CharacterController>());
        Motor motor = new(body, _movementConfig);
        Locomotion locomotion = new(motor);
        _simulation = new Simulation(locomotion);
    }
}
```

这里的关键不是“类越少越好”，而是依赖从上到下只有一个方向：组合根拥有 Simulation，Simulation 拥有 Locomotion，Locomotion 拥有 Motor。构造完成后不会出现半初始化对象；少依赖会立刻在构造阶段暴露，而不是到网络运行中才报空引用。

`ICharacterBody`（角色身体接口）是纯算法和 Unity 世界之间的边界。生产环境可用 `CharacterControllerBody`（CharacterController 身体适配器），单元测试可换成内存中的 Fake Body（测试替身身体），从而不必依赖场景碰撞组件就能验证加速度、重力、状态捕获和恢复。

### 配置应该放在哪里

当组合根是唯一装配入口时，序列化配置也应集中在组合根或单独的配置资产中，再通过构造函数向下传递。不要让同一含义的速度、加速度、体力上限同时散落在多层组件中。

配置迁移时必须逐项保存已有 Prefab/Scene Override（预制体/场景覆盖值）。纯 C# 化最常见的回归并不是算法写错，而是把原来已调好的场景覆盖值恢复成代码默认值。因此迁移后应同时验证：

```text
结构：旧算法组件已经全部移除，没有重复实例
数值：生产 Prefab、测试 Prefab、测试 Scene 的配置与迁移前一致
引用：场景和 Prefab 没有 Missing Script（缺失脚本）
行为：离线移动、预测、权威和插值仍走同一模拟入口
```

### 哪些对象不应该强行纯 C# 化

与 Unity 或 NGO 生命周期直接绑定的边界对象通常应继续保留组件身份，例如：

- 接收 `OnNetworkSpawn/OnNetworkDespawn`（网络生成/销毁回调）的网络总控；
- 真正执行碰撞移动的 `CharacterController`；
- 每渲染帧读取设备输入或驱动相机的场景入口；
- 只负责把 Inspector（检视面板）配置交给纯 C# 对象的组合根。

判断标准是：这个类型是否需要被 Unity 独立发现、挂载和回调。如果只是被另一层唯一持有、提供确定的计算和状态，就更适合普通 C# 类；如果它代表场景身份或引擎生命周期边界，则保留组件更清晰。

### 验证清单

- [ ] 纯模拟类型不继承 `MonoBehaviour`，也不依赖 `GetComponent`；
- [ ] 所有必需依赖通过构造函数传入并判空；
- [ ] 只有一个组合根负责创建完整对象图；
- [ ] 捕获与恢复覆盖姿态、速度、离散控制状态和资源值；
- [ ] Warp（强制传送）同时清理模拟状态和网络历史；
- [ ] 原 Prefab/Scene 的调参值逐项迁移并通过序列化检查；
- [ ] 测试显式断言纯模拟类型不是 Unity 组件；
- [ ] 编译、缺失引用、离线 Play、跨端网络回归均通过。

## 37. 问题：直接把框架 Tick 回调当作整个同步时钟，会把时间语义锁死在框架里

### 典型写法

很多同步系统最初会直接在框架回调里推进业务模块：

```csharp
private void OnNetworkTick()
{
    if (isServer)
        serverAuthority.SimulateNextTick();
    else if (isOwner)
        prediction.Predict(currentInput);
}
```

这种写法在模拟频率与框架频率完全一致时可以运行，但没有一个明确对象回答以下问题：

```text
当前业务 Tick 是多少？
单步 deltaTime 从哪里计算？
Prediction 与 Authority 谁负责递增？
Hard Resync 后哪个计数器需要重置？
Warp、重连、暂停后时间轴从哪里重新开始？
将来换成独立固定步时，哪些模块需要修改？
```

结果往往是 Prediction（预测）、ServerAuthority（服务器权威）和 Controller（总控）各自保存或推导一份 Tick。只要其中一处多执行一次、漏执行一次或重置顺序不同，输入历史、状态历史和 Snapshot（状态快照）就会使用不同时间轴。

### “驱动信号”和“业务时钟”不是同一个概念

框架事件负责告诉代码“现在可以做一次更新”，它是 Driver（驱动源）。业务时钟负责定义“这次更新是第几个 Tick、单步多长”，它是状态和规则。

```text
Driver：NetworkTick、Update、FixedUpdate、测试循环、服务器任务调度器
Clock：TickRate、TickDeltaTime、CurrentTick、Reset、Advance
```

把二者分开后，可以先继续使用现有网络框架驱动，而不让 Prediction 和 Authority 依赖框架 API（应用程序接口）：

```csharp
public sealed class SimulationClock
{
    public int TickRate { get; }
    public float TickDeltaTime { get; }
    public uint CurrentTick { get; private set; }

    public SimulationClock(int tickRate)
    {
        if (tickRate <= 0)
            throw new ArgumentOutOfRangeException(nameof(tickRate));

        TickRate = tickRate;
        TickDeltaTime = 1f / tickRate;
    }

    public void Reset(uint tick = 0)
    {
        CurrentTick = tick;
    }

    public uint AdvanceOneTick()
    {
        CurrentTick = unchecked(CurrentTick + 1u);
        return CurrentTick;
    }
}

private void OnNetworkTick()
{
    uint tick = _clock.AdvanceOneTick();

    if (isServer)
        _authority.SimulateNextTick(tick);
    else if (isOwner)
        _prediction.Predict(currentInput, tick);
}
```

Clock（时钟）不订阅事件，也不读取 Unity `Time`。它只是一个可测试的状态对象；Controller 决定当前使用哪种 Driver。

### 为什么 Tick 应由上层派发

下面的写法仍然存在两个时间源：

```csharp
prediction.Predict();        // 内部 currentTick++
authority.SimulateNextTick(); // 内部 lastTick++
```

更安全的方式是由组合根先生成 Tick，再显式交给当前身份模块：

```csharp
uint tick = clock.AdvanceOneTick();
prediction.Predict(input, tick);
```

接收方还应校验 Tick：

```csharp
if (tick != clock.CurrentTick)
    throw new InvalidOperationException("消费的不是时钟当前 Tick");
```

服务器权威模块通常仍需要保存 `LastProcessedTick`（最后已完成的 Tick）。这不等于创造第二个时钟：Clock 的 `CurrentTick` 表示上层当前派发的步，`LastProcessedTick` 表示服务器已经成功完成模拟的步。两者在模拟执行期间可以短暂相差 1，执行结束后必须相等。

### 重置必须覆盖时钟

任何清理时间轴的操作都必须同时重置 Clock：

- Spawn（网络生成）建立初始 Tick；
- Hard Resync（硬同步）跳到权威 Tick；
- Warp（强制传送）清理旧位置时间轴；
- Reconnect（重连）不能沿用上次会话 Tick；
- Despawn（网络销毁）清除订阅和时钟状态。

如果只清历史、不清时钟，新的输入会继续使用旧会话的巨大 Tick；如果只清时钟、不清历史，环形缓冲中相同槽位可能把旧状态误认为当前状态。

### 轻量时钟不能解决什么

把 Tick 封装为纯 C# 类只是建立升级边界，不会自动解决两个进程之间的时钟差：

```text
它不会从一帧 deltaTime 计算需要补跑几步；
不会在卡顿后 Catch-up（追帧）；
不会估算 Client 与 Server Drift（时钟漂移）；
不会让 60 Hz 业务模拟凭空运行在 30 Hz 外部回调上；
不会决定 Snapshot 和 Input 的发送频率。
```

如果外部 Driver 仍是 30 Hz，那么每次回调只 `AdvanceOneTick`，业务模拟上限仍是 30 Hz。要真正解耦，应在后续版本给 Clock 增加时间累加器，并由渲染帧或统一进程级调度器输入单调时间：

```text
elapsed time
  -> accumulator
      -> 0..N 个固定 Tick
          -> max catch-up 限制
              -> 逐步漂移校正
```

不要在第一次抽象时同时加入全部功能。先建立单一 Tick 来源并保持线上语义不变，更容易通过回归证明重构没有改变协议行为。

### 多玩家场景注意事项

每个玩家 Controller 持有一个时钟适合当前“每个网络玩家拥有独立预测/权威历史”的结构，但所有同进程玩家必须接收同一种驱动信号和相同 TickRate。若二轮重构加入独立累加器，应评估改为进程级共享 Scheduler（调度器）向多个玩家时钟派发 Tick，避免大量玩家各自执行浮点累加后出现边界差异。

### 验证清单

- [ ] Clock 是普通 C# 类，不引用 Unity、NGO 或静态 `Time`；
- [ ] TickRate 非法值在构造时立即拒绝；
- [ ] TickDeltaTime 只由 Clock 计算；
- [ ] Controller 是唯一推进 Tick 的对象；
- [ ] Prediction 与 Authority 消费显式 Tick，不再自行递增；
- [ ] Server 校验派发 Tick 连续且与 Clock 一致；
- [ ] Spawn、Hard Resync、Warp、Despawn 都重置 Clock；
- [ ] `uint.MaxValue -> 0` 的回绕有自动化测试；
- [ ] 单元测试与跨进程网络回归分别执行；
- [ ] 文档明确区分“已抽象时钟”和“已实现独立时钟”。
