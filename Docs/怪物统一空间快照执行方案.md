# 怪物统一空间快照执行方案

## 1. 目标和边界

本方案用于第二阶段优化：在四叉树完成 AOT 迁移并重新量化之后，合并当前 Density 与 Separation 的重复空间采集和建桶过程。

执行顺序固定为：

```text
当前代码 + 四叉树 HotUpdate 基线
  -> 四叉树纯内核 AOT
  -> 重新量化
  -> Density/Separation 统一空间快照
  -> 再次量化
```

本方案第一阶段只合并：

- `MonsterNavigationDensitySystem` 的 Slot→导航 Cell 计数；
- `MonsterSeparationSystem` 的 Position/Active 采集和分离桶归属；
- 这两者之间的一次性空间事实准备。

本方案第一阶段不合并：

- 四叉树节点、叶节点和 Query 栈；
- `RuntimeNavigationGrid` 的静态拓扑、动态障碍和 Navigation Cost；
- `MultiSourceFlowField` 的路径成本、方向和堆；
- Separation 的距离计算、重叠方向和分离力输出；
- Density 的 Influence、平滑和 Density Cost 输出；
- Weapon 的窄相、伤害、穿透、链式 visited；
- 子弹 Collider/GameObject 生命周期。

核心原则是：

> 统一的是“怪物当前属于哪个空间单元”这份事实，不是把所有空间算法合成一个类。

## 2. 当前代码的重复路径

相关文件：

```text
Assets/_HotUpdate/Scripts/GameProcess/Monster/Simulation/MonsterSimulation.cs
Assets/_HotUpdate/Scripts/GameProcess/Monster/SeparationSystem/MonsterSeparationSystem.cs
Assets/_HotUpdate/Scripts/GameProcess/Map/Spatial/MonsterNavigationDensitySystem.cs
Assets/_AOT/Scripts/Core/Navigation/SeparationKernel.cs
Assets/_AOT/Scripts/Core/Navigation/DensityKernel.cs
Assets/_HotUpdate/Scripts/GameProcess/Map/Spatial/RoomSpatialUtility.cs
```

当前 `MonsterSimulation.Tick()` 的顺序是：

```text
DensityUpdate
  -> 遍历 MonsterWorld 全部 Slot
  -> IsActive
  -> roomRoot.InverseTransformPoint
  -> WorldToCell
  -> DensityKernel._monsterCounts[cell]++

SeparationBuild
  -> HotUpdate 遍历全部 Slot
  -> 复制 _positions 和 _activeSlots
  -> AOT SeparationKernel 再遍历 _activeSlots
  -> 计算 bucket、写 _bucketHeads 和 _next
  -> 计算邻桶成对分离力

EntityTick
  -> 使用分离力，更新 MonsterWorld.Position
```

Density 和 Separation 都在实体移动前读取位置，因此可以安全共享一份“预移动空间快照”。不能把移动后的 QuadTree 查询直接复用这份预移动快照，否则 Combat 阶段会读取旧位置。

## 3. 当前 5012 档的可量化目标

以 `20261026-162947-530d99d1` 5012 Host 首次重复为参考，30 秒内约有：

```text
Monster Simulation Tick       791 次
Density Capture               131 次
Separation Capture            791 次
Separation BuildBuckets       791 次
QuadTree Build                533 次
```

当前 Density/Separation 的空间准备相当于：

```text
791 × 5012       Separation Capture
791 × 5012       Separation BuildBuckets
131 × 5012       Density Capture
```

统一快照后目标是：

```text
791 × 5012       OccupancySnapshot.Build
```

因此空间准备阶段预计减少约：

```text
922 个 5012 规模遍历单元
约 462 万次 Slot 访问
约 53.8% 的空间准备全量遍历
```

这不是整帧 FPS 承诺。`EntityTick`、Separation 成对计算和 QuadTree Build 仍然存在，必须在统一快照完成后重新量化。

## 4. 第一阶段数据布局

### 4.1 新增空间快照对象

建议新增：

```text
Assets/_HotUpdate/Scripts/GameProcess/Monster/Spatial/MonsterOccupancySnapshot.cs
Assets/_HotUpdate/Scripts/GameProcess/Monster/Spatial/MonsterOccupancySnapshot.cs.meta
```

第一阶段由 `MonsterRoomRuntime` 持有：

```csharp
private readonly MonsterOccupancySnapshot _occupancySnapshot;
```

这样房间拥有空间事实，Density 和 Separation 只是消费者，不再各自拥有一份 Slot→空间桶的事实。

### 4.2 Fine Cell：服务 Density

房间导航 Cell 当前是 70×70、CellSize=1 米，因此第一阶段直接沿用导航 Cell 的坐标体系：

```text
fineWidth  = 70
fineHeight = 70
fineCount  = 4900
```

快照维护：

```text
int[] _fineCellCounts   // 4900
```

第一阶段只需要 Density 的计数，不立即建立 Fine Cell 的 Slot 链。这样不会为了未来查询接口提前增加 `fineHead`、`fineNextSlot` 等数组。

每次 Build 开始时清零 `_fineCellCounts`，活跃 Slot 计算出 Fine Cell 后累加。

### 4.3 Coarse Bucket：服务 Separation

当前 Separation 半径为 3 米，桶边长也是 3 米。保持当前桶语义，避免第一阶段同时改变邻居候选数量：

```text
coarseBucketSize = 3m
coarseWidth  = ceil(roomWidth / 3)
coarseHeight = ceil(roomHeight / 3)
```

当前 70 米房间约为 24×24、576 个桶。快照维护：

```text
int[] _bucketHeads           // 每个 Coarse Bucket 的链表头
int[] _activeBuckets         // 本次有怪物的桶
int[] _nextSlot              // Coarse Bucket 内的 Slot 链
int   _activeBucketCount
```

`_neighborBucketIndices` 可以先继续由 `SeparationKernel` 持有，因为它是静态邻接查表，不是每 Tick 的实体空间事实。后续如果范围查询也需要 Coarse 邻接，再将它移动到快照服务。

### 4.4 共享输入缓冲

为了让 AOT Separation Kernel 和 HotFix 快照都使用同一批位置数据，快照维护：

```text
Vector2[] _positions    // 按稳定 Slot 编号
int[]     _activeSlots  // 当前活跃 Slot 列表
int       _activeCount
```

这两份数组从 `MonsterSeparationSystem` 移到 `MonsterOccupancySnapshot`，不再由 Separation 单独维护。

第一阶段不把 `MonsterWorld` 的 `MonsterMotionData[]` 移到 AOT，也不改 `MonsterWorld` 的 SoA 布局。这样可以先完成空间职责收拢，避免把实体数据容器和 AOT 程序集边界一起重构。

## 5. Snapshot.Build 的具体运行逻辑

### 5.1 Build 时机

快照必须在实体移动前建立：

```text
MonsterRoomRuntime.Tick
  -> 更新动态障碍
  -> 捕获玩家目标
  -> _occupancySnapshot.Build(World)
  -> _simulation.Tick(World, ..., _occupancySnapshot)
       -> Density 读取快照
       -> Separation 读取快照
       -> EntityTick 使用 Separation 输出并移动 World
  -> _spatialIndex.Invalidate()
```

这样 Density 和 Separation 读取同一个 Tick 起点的位置。

Combat 阶段发生在实体移动之后：

```text
CombatSimulation
  -> QuadTree 第一次查询时按当前 World 懒 Build
  -> Projectile / Range / Lightning 使用 QuadTree
```

第一阶段不让 Combat 查询读取 `MonsterOccupancySnapshot`，因为它是预移动快照。

### 5.2 单次 Slot 循环

`Build(World)` 的逻辑应保持为一轮 Slot 访问：

```csharp
for (int slot = 0; slot < world.SlotCount; slot++)
{
    if (!world.Meta[slot].IsActive)
        continue;

    Vector2 position = world.Motion[slot].Position;
    _positions[slot] = position;
    _activeSlots[_activeCount++] = slot;

    if (TryGetFineCell(position, out int fineCell))
        _fineCellCounts[fineCell]++;

    int bucket = GetCoarseBucket(position);
    if (bucket < 0)
        continue;

    if (_bucketHeads[bucket] < 0)
        _activeBuckets[_activeBucketCount++] = bucket;

    _nextSlot[slot] = _bucketHeads[bucket];
    _bucketHeads[bucket] = slot;
}
```

关键点：

- `Position` 只从 `MonsterWorld` 读取一次；
- `IsActive` 只判断一次；
- Fine Cell 计数和 Coarse Bucket 插入在同一轮完成；
- `_nextSlot` 只写入当前活跃 Slot，不需要每 Tick 清空整个 Slot 数组；
- `_fineCellCounts` 和 `_bucketHeads` 只清空各自固定空间范围；
- 不在 Build 中创建 List、LINQ、闭包或临时数组。

### 5.3 Room 坐标转换

当前 Density 每个 Slot 调用 `roomRoot.InverseTransformPoint`。快照应在房间创建时缓存：

```text
Matrix4x4 _worldToRoom
Vector2   _roomWorldMin
Vector2   _roomWorldMax
```

Build 时使用缓存矩阵计算 Fine Cell，使用与当前 Separation 相同的世界 Bounds 计算 Coarse Bucket。

房间运行期间默认 `roomRoot` 不移动。若房间 Transform 允许移动，必须在快照中增加 Bounds/矩阵版本检测；检测到变化时整体验证并重建，不能继续使用旧矩阵。

第一阶段应先验证房间确实是静态 Transform，再启用缓存；如果无法保证静态，保留当前转换语义，先只合并扫描次数。

## 6. 消费方改动

### 6.1 Density

修改：

```text
Assets/_HotUpdate/Scripts/GameProcess/Map/Spatial/MonsterNavigationDensitySystem.cs
Assets/_AOT/Scripts/Core/Navigation/DensityKernel.cs
```

当前接口：

```csharp
Update(MonsterWorld world, RuntimeNavigationGrid grid, uint tick, float groundY)
```

改为：

```csharp
Update(
    MonsterOccupancySnapshot snapshot,
    RuntimeNavigationGrid grid,
    uint tick)
```

删除：

- `MonsterNavigationDensitySystem._roomRoot`；
- `BuildMonsterCounts()`；
- `DensityKernel._monsterCounts`；
- 每次 Density Update 的 `MonsterWorld` 全量 Slot 扫描。

`DensityKernel` 继续保留：

```text
_influence
_smoothedCost
_outputCost
_kernelX / _kernelY / _kernelWeight
```

第一阶段先让 `DensityKernel.Build()` 接收 `snapshot.FineCellCounts`，不要同时改 Density 算法。确认结果稳定后，再考虑让 `_outputCost` 和 `RuntimeNavigationGrid._densityCost` 共用一份输出缓冲。

### 6.2 Separation

修改：

```text
Assets/_HotUpdate/Scripts/GameProcess/Monster/SeparationSystem/MonsterSeparationSystem.cs
Assets/_AOT/Scripts/Core/Navigation/SeparationKernel.cs
```

`MonsterSeparationSystem` 删除：

```text
_positions
_activeSlots
_activeCount
EnsureCaptureCapacity()
```

改为：

```csharp
public void Build(MonsterOccupancySnapshot snapshot)
{
    _kernel.CalculateFromSnapshot(snapshot);
}
```

`SeparationKernel` 删除每次 Build 的 `BuildBuckets()`，保留：

- `_separation` 输出；
- NeighborBuckets 查表；
- `CalculatePairs`；
- 距离、重叠和强度公式。

新增一个只读快照入口：

```csharp
public void CalculateFromSnapshot(MonsterOccupancySnapshot snapshot)
```

如果 AOT_Core 不能引用 HotFix 类型，则不要让 Kernel 接收 `MonsterOccupancySnapshot` 类型，而是接收其数组视图：

```csharp
CalculateFromBuckets(
    Vector2[] positions,
    int[] bucketHeads,
    int[] activeBuckets,
    int activeBucketCount,
    int[] nextSlot,
    int slotCount);
```

这样 AOT 内核只接收数组和标量，不产生程序集反向依赖。

### 6.3 MonsterSimulation 和 MonsterRoomRuntime

`MonsterRoomRuntime` 新增快照生命周期：

```text
构造时创建
BeginRoom 时 Clear/Invalidate
Tick 前 Build
Spawn 后标记 Dirty
EndRoom 时 Clear
```

`MonsterSimulation.Tick` 新增快照参数，内部只读：

```text
_densitySystem.Update(snapshot, _navigationGrid, tick)
_separation.Build(snapshot)
```

`MonsterSimulation` 不拥有快照，避免 Simulation 成为第二个空间事实所有者。

## 7. Active、死亡、击退和 Spawn 语义

第一阶段快照只服务 WorldSimulation 前的 Density/Separation，所以同 Tick Combat 造成的变化不回写到本次快照：

```text
本 Tick 开始：Build 预移动快照
本 Tick 中段：EntityTick 移动怪物
Combat：QuadTree 读取移动后的 World
下 Tick 开始：重新 Build 快照
```

需要保持的规则：

- Spawn 在下一次 WorldSimulation 前必须进入快照；
- Combat 杀死的怪物不会继续参与下一 Tick 的 Density/Separation；
- Push 造成的位置变化在下一 Tick 快照中体现；
- `MonsterOccupancySnapshot` 不作为 Combat 命中事实来源，因此不需要处理 Combat 内即时 Remove/Relocate；
- 四叉树继续由 `DamageMonster`、`PushMonster` 维护当前 Tick 的命中一致性。

如果以后希望范围伤害直接使用固定 Grid，则必须另建“后移动 Combat Snapshot”或增量覆盖层，不能直接复用这里的预移动快照。

## 8. 不应在第一阶段做的事情

为了保证可量化，第一阶段禁止同时做以下改动：

- 不把 QuadTree 改成 Grid；
- 不把 Projectile 从 Query API 改成直接读 Cell 链；
- 不把 FlowField 的导航数组放入 OccupancySnapshot；
- 不改变 Density 更新间隔 6 Tick；
- 不改变 Separation 半径和 Coarse Bucket 尺寸；
- 不引入 Job/Burst/NativeArray；
- 不做增量迁移和双缓冲快照；
- 不删除子弹 Collider/GameObject；
- 不新增大量诊断 Marker；
- 不同时修改 MonsterWorld 的 Slot 复用策略。

这些都可以作为后续独立实验，但会破坏本阶段的 A/B 归因。

## 9. 实施步骤

### S0：四叉树 AOT 后的第二轮基线

先保存 AOT 后但尚未统一快照的 5012 Host/Client 结果：

- QuadTree Build/Query；
- Density Capture/Kernel；
- Separation Capture/Kernel；
- EntityTick；
- FlowField；
- Main Thread、Active CPU、Tick 补跑和 GC；
- 候选数、访问节点数和命中结果。

该轮是统一快照的唯一分母。

S0 已于 2026-10-28 冻结：RunId `20261027-161455-47937465`，对照源码提交 `157d818`。5012 Host 三次前台轮的加权结果为：QuadTree Build `0.4947 ms/次`、Query `0.00083 ms/次`、Density Capture `1.506 ms/次`、Density Kernel `0.058 ms/次`、Separation Capture `0.382 ms/次`、Separation Kernel `0.684 ms/次`、EntityTick `9.945 ms/次`、Host Main Thread `10.578 ms/帧`、GC Alloc `1669 B/帧`。每次 Query 平均访问 `17.92` 个节点并返回 `0.52` 个候选。完整 A0/A1 口径、构建指纹和有效性限制见《怪物四叉树核心 AOT 迁移执行方案》。

该 S0 足以作为统一快照的架构量化分母；正式自动回归前仍应在生成物提交后补一轮干净工作区确认样本，避免 `gitDirty=true` 和 Catalog 指纹策略影响报表的自动兼容判断。

### S1：添加快照类但不接入

实现：

- 容量扩展；
- Fine Cell Count；
- Coarse Bucket Head/Active/Next；
- Position/ActiveSlot 复用数组；
- Clear/Build/Debug 统计。

## 10. 量化验收条件

### 10.1 遍历次数

5012 Host 同口径 30 秒采样，目标为：

| 项目 | 统一前 | 统一后目标 |
|---|---:|---:|
| Density 全量 World Capture | 约 131 次 | 0 次 |
| Separation HotFix Capture | 约 791 次 | 0 次 |
| Separation AOT BuildBuckets | 约 791 次 | 0 次 |
| OccupancySnapshot.Build | 0 | 约 791 次 |
| EntityTick | 约 791 次 | 不变 |
| QuadTree Build | AOT 后基线值 | 不因本阶段改变 |

实际应该看到：空间准备从三段全量扫描变成一段全量扫描，而不是增加一段新的 Snapshot 扫描后保留旧 Density/Separation 扫描。

### 10.2 正确性

- Fine Cell Count 逐格差异为 0；
- Coarse Bucket 的 Slot 集合逐桶差异为 0；
- Separation 输出向量最大误差不超过浮点比较阈值；
- FlowField Source、Cost、Direction 与统一前一致；
- QuadTree 候选集合与统一前一致；
- 死亡、击退、Spawn 后的下一 Tick 行为一致；
- 不出现重复 Slot、幽灵 Slot 或漏掉活跃 Slot。

### 10.3 性能

重点观察：

| Marker/指标 | 预期 |
|---|---|
| `Monster.Density.Capture` | 调用数降为 0 或不再包含 World 全量循环 |
| `Monster.Separation.Capture` | 调用数降为 0 |
| `Monster.Separation.Kernel` | 只剩桶内/邻桶成对计算，不能出现结果回归 |
| `Monster.Simulation.DensityUpdate` | 更新帧峰值下降或不回归 |
| `Monster.Simulation.SeparationBuild` | 不回归；目标是减少重复采集成本 |
| `Monster.Simulation.EntityTick` | 与 AOT 后基线近似一致 |
| `Monster.SpatialIndex.Build` | 与 AOT 后基线近似一致 |
| GC Alloc | 不增加 |
| Host P95/P99 | 不恶化 |

如果 Snapshot.Build 本身成为新的主要热点，下一步只允许把 Snapshot.Build 的纯数组循环迁入 `AOT_Core`，不改变其数据协议和调用时机。

## 11. 后续扩展，而不是本阶段默认内容

统一快照稳定后，可以按以下顺序扩展：

1. 加入 Fine Cell 的 `cellHead / cellOfSlot / nextSlot`，让范围查询有固定 Grid 后端；
2. 在同一 Build 中生成 `coarseCellCount`，替代额外的 Density 聚合；
3. 让 QuadTree 只复用统一快照的 Position/Active 输入，但保留自己的 Node/Leaf 链；
4. 用同一个房间查询接口对比 QuadTree AOT 与 Grid AOT；
5. 在后移动阶段增加独立 Combat Snapshot 或增量迁移；
6. 最后再评估是否删除子弹 Collider/GameObject。

这些扩展必须逐项量化，不能和 S2/S3 合并为一次大改。

## 12. 回滚方案和交付物

建议拆成：

```text
1. occupancy-snapshot-core：新增快照与 parity 测试
2. occupancy-density-consumer：Density 改读 CellCount
3. occupancy-separation-consumer：Separation 改读共享桶
4. occupancy-cleanup：删除旧的独立扫描和桶构建
```

任何一步失败都可以回滚到四叉树 AOT 后的稳定基线，不影响四叉树 AOT 结果。

最终应保存：

- 四叉树 AOT 后基线报告；
- 统一快照 S2 报告；
- 统一快照 S3 报告；
- `Density.Capture`、`Separation.Capture`、`Separation.Kernel` 的调用数与耗时；
- Fine Cell/Coarse Bucket parity 结果；
- Host/Client 5012 的完整帧和 Tick 补跑统计；
- 任何新建数组的容量、元素类型和生命周期说明。

只有这份统一快照 A/B 完成后，才决定是否继续把四叉树替换为 Grid 查询后端。
